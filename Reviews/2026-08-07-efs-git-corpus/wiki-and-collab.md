# EFS Git — the wiki workflow, guest reads, and the minimal collaboration objects

**Status:** deep-dive candidate model, 2026-08-07. The product half: how a normal person edits a Wikipedia-style page whose revision engine is Git, what an anonymous reader gets, and the smallest proposal/review object set that must exist before any forge ambition.

## 1. The user vocabulary and what each verb actually does

| User verb | Under the hood | User never sees |
|---|---|---|
| **Edit** | open working copy from local materialized tree (OPFS) | clone, checkout, staging |
| **Preview** | render working copy (render service, untrusted-document lane) | — |
| **Save draft** | journal write (Tier B; autosave); optionally a local commit at coherent boundaries | commit plumbing; the editor decides commit granularity |
| **Propose changes** | local commit(s) → closure upload → proposal claim + proposer-namespace ref | branches, refspecs |
| **Publish** (trusted editor) | local commit → closure upload → ref transaction (ADVANCE) | push, CAS |
| **History** | `git log` over the canonical branch, rendered as revision list with edit summaries (= commit messages) | reflog, DAG unless they ask |
| **Compare** | `git diff` rev A..B, word-level prose rendering | — |
| **Restore** | new revert commit + ADVANCE (never force; H-10) | reset, rebase |

Edit summaries are commit messages, entered in the same field Wikipedia puts them. One page-save = one commit by default; a multi-page edit session = one commit touching several files (atomic, trace T4). The house content style is **normalized CommonMark (mdformat-class canonical form, enforced at save) + one-sentence-per-line (semantic line breaks)**: normalization makes hashes stable under editor round-trips and kills formatting-noise diffs; sentence-per-line makes stock merge operate at *sentence* granularity — the honest unit, verified in E9b: concurrent edits to the **same or adjacent** sentences conflict (Git's 3-way merge conflicts on adjacent changed lines with no separating context); edits separated by at least one untouched sentence merge cleanly. Still far finer than paragraph granularity ([prior-art/markdown-merge-and-collab](./prior-art/markdown-merge-and-collab.md) §3; [prior-art/local-git-experiments](./prior-art/local-git-experiments.md) E9b). This is deliberately the boring core: Wikipedia itself runs on diff3 (`wfMerge()`), and the field's best evaluation (ASE 2024) found clever semantic auto-merge trades visible conflicts for silent corruption; no trustworthy structured Markdown merge ships in 2026. Custom merge drivers don't travel with clones and hosts ignore them — nothing in deterministic replay may depend on one; `merge=union` is banned for prose (silent interleaving).

## 2. Trusted edits vs public proposals

- **Trusted editor** (roster `ADVANCE`): Publish goes straight to the canonical branch. Wikipedia-anon-equivalent friction is a *policy* choice, not architecture: a wiki may grant `ADVANCE` broadly and lean on RESTORE + roster ejection (curation, per C7/B2), or keep `ADVANCE` tight and route everyone through proposals.
- **Anyone else**: Propose changes. The proposal lives entirely under the proposer's own authority (their principal signs their own namespaced ref + proposal claim) — no permission needed, nothing for the repo owner to host. A maintainer's *acceptance* is what touches the canonical branch: merge/rebase locally → ADVANCE transaction + `mergeOf` provenance claim referencing the proposal. **The economics are the honest open problem here**, not the mechanism: a self-paying proposer needs a keypair and funds (fatal friction for a drive-by typo fix against Wikipedia's zero-cost anon edit), while a sponsored proposer voids "proposer pays" as the spam bound — a sponsor needs its own defense (per-principal ceilings, deposits, roster-classed intake, or a gateway-attested free tier at a degraded rung). This reconciliation is a named unknown and falsifier in the main review, and acceptance test 20 must specify who funds the loop. Foreign-format proposals (stock-git `refs/for/*` intake) are **never rewritten**: normalization of a non-house-style proposal happens in the *acceptance merge commit*, preserving the proposer's commit bytes, signature, and `change-id`.
- **Concurrent edits to the same or adjacent sentences** (trace T3): second Publish fails CAS at the gateway fast path → client auto-rebases; clean → retransmit; conflict → **two-versions UI** (theirs/yours per conflicted passage, side-by-side, pick-or-combine), then a merge commit. Never auto-merged silently, never a git conflict-marker file shown. The precedent bar is MediaWiki's TwoColConflict — fixing conflict UX was the German community's #1 technical wish, WMDE shipped the two-column resolver and still judged the surface barely fixable; budget this as the hardest single UI in the wiki. Frequency evidence says it's worth exactly that and no more: same-passage contention concentrates in a <1% controversial-page tail; the bulk of a wiki merges clean ([prior-art/git-backed-wikis](./prior-art/git-backed-wikis.md) §4). An AST/word-level merge assistant may *propose* resolutions interactively; deterministic replay stays ordinary Git bytes (C-7 boundary — assistants advise, curation decides). A future CRDT drafting session (eg-walker/Automerge-class) may terminate in an ordinary signed commit with the event graph retained as an *attested sidecar*, never a precondition for reading history. One cost truth the UI must own: when a race reaches admission (both envelopes admitted, one derives inapplicable), the loser has paid admission + placement and their unmerged content is permanently public under their identity — a **"conflicted publish"** ladder state with explicit fee/permanence disclosure, not a silent retry. The gateway CAS fast path exists precisely to make this rare; its residual frequency is an M5 measurement. Note also that the transplanted "conflicts are rare (<1 % tail)" evidence is a *lower bound* from Wikipedia's seconds-wide online-save windows; offline sessions, admission latency, and fee-driven batching all widen windows here, so M5's dogfood measures conflict rate as an exit criterion rather than assuming Wikipedia's.

## 3. State honesty — the ladder, reused verbatim

Draft (journal) → committed (local Git; still Tier B/C-class local truth) → uploading closure → submitted → authority-admitted → strongly settled: these are the *existing* pending-ladder states with Git words on top, plus one Git-specific terminal state — **conflicted publish** (admitted but inapplicable; fees spent; content permanently public; resolution flow attached). The Files/browser chips apply unchanged: a committed-but-unpublished page renders "saved on this device, not published"; an admitted ref renders venue + basis. Offline editing (trace T6): commits accumulate locally; sync later = one batched publish; a CAS loss on reconnect = the §2 conflict path.

## 4. Anonymous reading (G-GUEST)

Deep links resolve through the existing four-rung guest ladder G0→G1→G2→G3, with **G1 as the default** (LP-5's arm (a)) — and the G1 claims split honestly per view, because LP-5's own doctrine says a hosted endpoint can never prove completeness: a G1 guest verifies **authorship and bytes** for the page shown (ref-claim signature + container digest + commit/tree/blob hashes — kilobytes of proof, no wallet); but **head currency and history-listing completeness remain the endpoint's word at G1** — a stale-but-valid head or an omitted revision in a history view is detectable only by a chain-connected fold read (G2+, or the derived-head attestation convention in the state model). The UI labels the split exactly that way. Absence honesty carries over: a guest is never told a page *doesn't exist*, only "not found via this endpoint" (C-2). **Blocking dependency shared with the whole guest product: AMBIENT/1 (CR-3)** — the wiki adds pressure but no new surface.

## 5. Links

- **Exact citation** = `(repoId, commit, path)` (+ optional line/heading fragment): reproducible forever, rename-immune, carrier-independent — the Citation Link form (H-7).
- **Moving link** = `(repoId, policy-selected ref, path)`: resolves through the reader's accepted policy for that repo; the composer says "readers may see a newer version" — the Path Link form.
- **Page identity**: each wiki page gets an EFS DATA identity PINned to (repo, path); renames write `movedTo` (E11 — Git can't do this). Old links to the pre-move path resolve via redirect (trace T5); citations pinned to (commit, path) never break at all.

## 6. The minimal collaboration object set (what v1 wiki actually needs)

Required for the first wiki (all ordinary claims + DATA bodies; schemas ride the portable-schemas pass):

1. **ProposalV1** — proposer, repoId, target ref, proposal ref/OID (+dual digest), `change-id` where present (the Gerrit/Jujutsu/GitButler cross-tool commit header, so the proposal survives rebases), closure commitment, summary text ref. *Required*: it is the "Propose changes" verb. Intake from stock Git rides the `proc-receive` hook (`refs/for/main` push → proposal object, no ref ever created) — the upstreamed agit-flow mechanism, made for exactly this.
2. **ProposalStatusV1** — maintainer-signed OPEN→ACCEPTED(mergeOf)/DECLINED/WITHDRAWN; cardinality-1 slot per proposal. *Required*: the accept/decline surface.
3. **`mergeOf` provenance row** on the applying ref transaction. *Required*: connects canonical history to its proposal trail.
4. **Proposal discovery path.** Proposers are an open set writing under their own namespaces, so "list all proposals for this repo" is an index-mediated read: proposal claims REF-target the repo's proposal key-anchor, making the adopted target-keyed backlink index (A-3) the enumeration spine — chain-derivable, not gateway-invented. Views over it carry the standard completeness grade; a gateway omitting proposals from its listing is exactly the honesty-labeled incompleteness C-2 governs, and the backlink index is the auditor's recourse.

Explicitly *deferred* (not needed to ship the wiki): threaded review comments, inline code review, patch-revision series (Gerrit-style), issue objects, labels, CI attestations. The wiki's talk-page equivalent v1 = ordinary EFS comment claims targeting the page's DATA identity — machinery that exists today, no forge object required. This is the smallest portable layer the kickoff asked for; everything richer joins the later-forge scope with F3/ForgeFed/COB evidence.

## 6b. Two Wikipedia mechanisms the v1 wiki must carry (evidence-forced additions)

The wiki lane's MediaWiki analysis forces two items the earlier draft under-weighted ([prior-art/git-backed-wikis](./prior-art/git-backed-wikis.md) §4):

1. **Revision hiding is routine, not exceptional — and materially weaker here than its precedent.** Wikipedia's revdel/suppression — a mutable visibility bitfield over immutable revisions, used *as a tool of first resort* for doxxing and libel — is the load-bearing precedent for permanent stores. The EFS analogue ships **day one**: a curation claim class that masks specific revisions/blobs from default rendering (P-17's visible-tombstone arm generalized to wiki revisions), honored by default Views, suppressible only with the LP-8 disclosure floor. The parity gap must be stated wherever this ships: masking ≈ revdel-for-default-rendering; **nothing ≈ suppression** — the bytes remain permanently retrievable by any non-default View, G3 clone, or carrier fetch, and an EFS wiki cannot honor an erasure demand for admitted canonical content. That is why the *prevention* half is part of this requirement, not garnish: pre-publish PII/secret scanning in the editor (the one place it still helps), and accepted-head-gated defaults for PII-risk namespaces. Serving-layer quarantine (threat doc §5) handles the legal tier per operator.
2. **Accepted-head is read-side selection.** Wikipedia's pending-changes ("anonymous readers see the latest *accepted* revision") is precisely a policy-selected head: a wiki may run its canonical branch open-write but point default Views at a reviewer-advanced `refs/heads/accepted` (or a reviewed-revision claim), giving Wikipedia's exact anon-sees-reviewed behavior with zero new machinery — the fold already derives policy-selected refs.

## 7. Agent Skills rider (G-AGENT)

A skills repo is `workspaceClass = skills` with the same machinery plus one object: **SkillReleaseV1** — publisher principal, repoId, release tag, exact commit/tree OID (+dual digest), capability-manifest hash, supersession pointer. Install/update flows through GATE/1 unchanged (owner-pinned plan, closed authorities, STOP-on-revocation, policyMaxAge); the install ledger diffs capability manifests between pinned releases — the "meaningful diff before install" (trace T15) is the existing clientv2 install-ledger surface fed by release claims. Repository popularity never grants execution (A-3's enumeration ≠ endorsement, applied to skills).

## 8. What breaks on phones / at scale (named, not hidden)

- Whole-repo clone in a phone browser is the wrong default; the guest path (§4) reads pages without cloning, and editors materialize **sparse working sets** (current page + deps) from gateway-prepared containers. Full clone remains the power path.
- OPFS eviction: working trees and unpublished commits are Tier B/C journal state with the existing loss-reporting rules; publish-early nudges apply (time-at-risk).
- Very large wikis: shard by namespace (state-model §7); history pagination via commit-graph on the gateway; blame is a gateway-derived view, not client-mandatory.
- Publish latency: closure placement (a byte-market operation) plus admission confirmation sit on the publish path; the UI budget (seconds-class fast-path acknowledgment via the gateway, minutes-class settlement) and its measured reality are M5 exit criteria alongside conflict rate.
- Editing surface: the house style must survive real editors — visual/WYSIWYG tier, paste-from-Word/HTML ingestion, and sentence segmentation are client design work the style depends on; the normalizer profile version is pinned in the repo policy, and any import or profile bump lands as one attributed normalization commit so style noise never mixes with content edits.
- Case-insensitive filesystems: page-slug normalization (NFC + case-fold collision refusal at authoring time) — same class of rule as the path-grammar canon (C2), enforced by the editor, not the kernel.
- Symlinks/modes: wiki profile forbids symlinks and non-regular modes at intake (fsck gate, E8); code repos keep Git semantics with mount-profile projection rules.
