## Verbatim reports

### Reviewer: git-semantics — verdict: HOLDS-WITH-REPAIRS

```text
[FATAL] [state-model.md §4, §6; deep-dive §4 GD-4] The fold cannot enforce fast-forward-ness, so `restoreOnly`/"no force ever" is unenforceable as specified: an authorized `ADVANCE` with a matching `expectedOldOid` but a non-descendant `newOid` applies, achieving force-push semantics on the canonical wiki branch. The fold's stated applicability rule checks only CAS match + intent + policy epoch; ancestry ("newOid descends from expectedOld") requires Git objects, which chain state does not contain — the only difference between ADVANCE and FORCE in the fold is whether CAS matching is skipped. Git itself makes exactly this distinction with objects in hand (`receive.denyNonFastForwards`, update hooks run in the object store); the model silently assumes a check it cannot perform, and T8/GD-4/H-10 all present "no force intent applicable" as if it prevented history rewrite — a hostile roster editor can rewrite the wiki's canonical history via a lying ADVANCE whose fabricated `closureCommitment` the fold cannot audit. Fix: split the guarantee honestly — fold-level heads are CAS-canonical only; ancestry verification is an object-bearing check (gateways/G1+ clients mark non-FF ADVANCE as policy-violation with a defined deterministic tie-break once objects are available), and reword GD-4/H-10 from "never applicable" to "detected, rejectable by verifying readers, displaced closure retained."

[SERIOUS] [state-model.md §4; traces.md T7; candidate-architectures.md B "Security"] The replay-resistance claim fails for FORCE transactions and for ABA histories: a re-submitted old signed FORCE envelope "ignores expectedOldOid matching," so within its policy epoch it always re-applies and rolls the ref back; likewise a replayed ADVANCE re-applies whenever a forceable ref has returned to its old OID (or after delete/recreate). T7 only tests the easy case (expectedOld no longer matches), and the model explicitly allows re-admission of the same signed transaction ("re-admits… attributed to the replayer's submission"), so nothing in the specified fold prevents re-application. The restoreOnly wiki is incidentally safe (heads never recur), but the headline "replay-resistant… CAS" and "replay defeated by admission ordering" are false for the general Git-host profile — the exact rollback-replay class Radicle suffered. Fix: add a one-shot rule to `GIT-REF/1` — each claim/envelope identity applies at most once, at its first ordinal; later identical submissions derive as inapplicable-duplicate (deterministic, chain-state-only), and add FORCE-replay and ABA vectors to the M2 suite.

[SERIOUS] [storage-closure-recovery.md §3 vs state-model.md §4] "The fold surfaces a degraded-availability head" contradicts the fold's determinism keystone: byte availability is not a function of chain state. Whether containers named in `containerRefs` are actually retrievable varies by time and vantage point, so two conforming implementations of a fold that grades availability cannot "derive identically forever," and the M2 two-implementation vector suite could not even be defined over such an input. The claim also conflicts with the same document's admission that placement evidence is probe/receipt-based and time-varying (§1). Fix: restate the layering — the fold derives heads purely from admitted claims (it may deterministically check that closure-commitment *fields are present and well-formed*); availability grading is an explicitly non-deterministic serving/client annotation layered above fold output, per the existing capability-honesty axes.

[SERIOUS] [state-model.md §2, §4] HEAD/symbolic refs and default-branch mutability are unmodeled, and `defaultRefName` is pinned in the immutable genesis object with no mutable override slot. Stock clone behavior depends on the remote HEAD symref (protocol-v2 `ls-refs` `symrefs`), so with nothing fold-derived, every gateway freely chooses what clones check out — a small de facto authority in a design whose thesis is "no gateway in the trust path" — and renaming the default branch (a routine forge operation, cf. master→main) is impossible under the descriptor as drafted. The mutable slots enumerated (`policy`, `describe`, `mirrors`, `checkpoint`) contain no default-ref field, yet acceptance item 4 tests "default-branch selection" and wiki §6b assumes policy-selected default views. Fix: move the default/HEAD selection into `GitRefPlanV1` (epoch-versioned, fold-derived), keep the genesis field as the initial value only, and specify how gateways materialize it as the bare repo's HEAD.

[SERIOUS] [state-model.md §4; primitive-fit-gap.md §1] The fold has no refname well-formedness or directory/file-conflict rules, so it can derive ref sets no Git backend can materialize. Slots are independent per `(repoId, refName)`: claims creating `refs/heads/main/sub` while `refs/heads/main` exists both apply under the fold, but Git forbids D/F-conflicting refnames in every backend and `update-ref --stdin` aborts the whole transaction (the very E5 mechanism the gateway reconciliation relies on) — the gateway then either drops refs or diverges from derived state, both silently. Arbitrary claim-supplied refnames violating `check-ref-format` grammar have the same effect. Fix: `GIT-REF/1` must incorporate refname grammar and a deterministic D/F-conflict applicability rule (e.g., earlier-ordinal holder wins; conflicting later claims derive inapplicable-conflict), with vectors in M2.

[SERIOUS] [state-model.md §4; prototype-plan.md acceptance 4] The ref-claim schema is commit-shaped and mishandles tag refs: `newOidEfsDigest` is defined as "sha256 of the *commit* object bytes," but annotated tag refs point at tag objects (and legally at blobs/trees — git.git's `junio-gpg-pub` tag points at a blob). The `rev-list expectedOld..new` closure recipe assumes committish endpoints and breaks for tag→blob/tree; ADVANCE's implied fast-forward notion is meaningless for tag objects (Git requires force to move an existing tag ref precisely because tags have no ancestry); yet acceptance item 4 requires annotated and lightweight tags to work. Fix: define the dual digest as sha256 of the referenced object's bytes plus a peeled-target field, give tags their own intent/policy semantics (create-once by default, move = FORCE-class), and special-case non-commit tips in the closure recipe.

[SERIOUS] [wiki-and-collab.md §1–§2 vs traces.md T3 vs prototype-plan.md acceptance 16 vs prior-art/markdown-merge-and-collab.md] The load-bearing merge-granularity claim — "only same-sentence edits conflict" — is false as Git behavior, and the corpus contradicts itself three ways about the conflict unit. Git's 3-way merge conflicts on *adjacent* changed lines with no separating context, so concurrent edits to neighboring sentences of one paragraph conflict; the markdown lane's own mechanics section states this ("same or adjacent lines produce conflict markers") and then drops the caveat in its synthesis. Meanwhile E9 tested paragraph-per-line (not sentence-per-line), T3 asserts "same-paragraph → conflict," and acceptance 16 requires a two-versions UI for *any* same-paragraph concurrent edit — directly contradicting §1's promise that different-sentence same-paragraph edits auto-merge. (The deep-dive §1's "Wikipedia runs on the same diff3 Git uses" is also loose: MediaWiki shells out to GNU diff3, Git uses its own xdiff/xdl_merge — behaviorally similar, not "the same.") Fix: correct the claim to "same-or-adjacent-sentence edits conflict," re-run E9 with a sentence-per-line fixture, and reconcile §1, T3, and acceptance 16 to one stated conflict unit.

[SERIOUS] [requirements-ledger.md P-G8; deep-dive §7; prototype-plan.md M3] The stock-push intake ceremony ignores receive-pack's synchronous report-status semantics, and "the `proc-receive`/agit mechanism derisks the server half" is only true for `refs/for/*` proposal intake, not for direct pushes to `refs/heads/*`. A stock client updates its remote-tracking refs on `ok`, so a gateway that intakes a push pending countersign must either lie (report `ok` before the transaction is authoritative — divergence when admission CAS or countersign later fails), block the connection for unbounded countersign latency (HTTP timeouts, broken CI), or report `ng` (stock tooling treats the push as failed); `proc-receive` faces the same trilemma since it too must answer within the session. Fix: specify P-G8 as refs/for-style intake for *all* stock pushes (never report `ok` on a `refs/heads/*` command; report the proposal/pending result via proc-receive `option` lines), reserve direct-publish for EFS-aware clients, and demote the §7 "derisks" claim to proposal intake only.

[MINOR] [primitive-fit-gap.md §1 vs state-model.md §3; requirements-ledger A-7/A-3] Ref slots are "cardinality-1 claims, LWW comparator," so generic kernel readers (mount, mandatory indexes) will present the *newest admitted* claim as the slot's current value — which may be a recorded-but-inapplicable transaction — while the fold derives an older applied head, and no document says how non-profile surfaces avoid showing the wrong head. The state model declares "any single claim" non-canonical but the mount ruling (A-7) projects published state through generic machinery. Fix: state explicitly that ref slots render only through `GIT-REF/1` (generic surfaces must show them as opaque profile data), or shape ref claims so the naive LWW reading is not interpretable as a head.

[MINOR] [threat-and-economics.md §1; storage-closure-recovery.md §6b; deep-dive §1, §2] Two SHA-1 posture overclaims: "dual-digest binding means EFS statements never rest on SHA-1 alone" is false for the graph body — the sha256 covers only the head commit's bytes, whose tree/parent pointers are themselves SHA-1, so everything below the head still rests on SHA-1 (the residual row admits the collision risk, but the mitigation column oversells); and "EFS commits are ISO-standard citations for free" via SWHID holds only for SHA-1 repos — the SWH lane itself flags that SWHID v1.2/ISO 18670 is SHA1-locked, so the claim silently fails for the SHA-256 repos GD-3 makes first-class and Git 3.0 makes default. Fix: reword to "dual digest strengthens the head binding; container digests bind exact bytes; interior-graph SHA-1 risk remains detection-only (SHA-1DC)," and scope the SWHID claim to `objectFormat = sha1`.

Overall verdict: HOLDS-WITH-REPAIRS — the wiki-first recommendation, kernel-zero boundary, and reuse map survive, but the `GIT-REF/1` spec text overclaims in three places (ancestry, replay, availability) that must be repaired before GD-4's ratification language or the M2 vector suite is written.
```

### Reviewer: security-abuse — verdict: BREAKS (as drafted) — all three FATALs repaired

```text
[FATAL] [/Users/james/Code/EFS/planning-efs-git/Reviews/2026-08-07-efs-git-corpus/state-model.md §4 "Atomicity" + main review §1] Envelope batch atomicity does not survive a hostile relayer: the recommended write path lets a gateway submit a *subset* of a multi-ref transaction, and `GitRefClaimV1` carries nothing that lets the fold detect the missing siblings.
`Designs/efsv2/codex-envelope.md` adopted core specifies an EIP-712 `Envelope(author, seq, prev, recordsRoot, count)` with a positional Merkle tree and **single-leaf proofs**, and amendment 2 names "subset submission" as a live adversary capability it had to close *by other means* for listIds. Nothing in the kernel forces all leaves of an envelope to be carried together, and P-G8 puts a gateway in exactly the relaying seat (state-model §5, requirements-ledger P-G8): a hostile or merely partisan gateway takes the user's signed envelope and admits only the ref leaf it prefers. The fold can group claims by `(author, seq)` but has no `count` in per-claim state and no batch commitment in the claim body, so it cannot distinguish "two-ref transaction, one leaf withheld" from "one-ref transaction" — the claim "There is no partial multi-ref state on-chain… structurally absent" is false, and it is load-bearing in §1 ("Envelope batch atomicity gives multi-ref transactions").
**Fix:** add `txnRoot` (or the envelope digest) and `refCount` to every `GitRefClaimV1` body, and make `GIT-REF/1` apply a transaction only when all `refCount` siblings sharing that `txnRoot` are present; record an incomplete group as a named `TRUNCATED-TXN` evidence state, and add "gateway admits a proper subset of a signed multi-ref envelope" to the threat table §2 and acceptance item 3.

[FATAL] [/Users/james/Code/EFS/planning-efs-git/Reviews/2026-08-07-efs-git-corpus/state-model.md §4 "Replay resistance"] Replay resistance binds to the prior ref *value*, not to the prior claim, so a replayed old transaction re-applies whenever `expectedOldOid` recurs — which the design's own supported operations make routine.
`expectedOldOid` is a value, and values recur: branch delete (`newOid = 0`) then re-create replays the original creation claim (`expectedOld = 0`); a `FORCE` branch moved A→B→A re-legitimizes the old A→B claim; lightweight tags moved back do the same — and acceptance items 3/4 explicitly keep delete and tags in scope. Replay of a signed envelope is not merely possible but a *designed feature* of the substrate (`Designs/efsv2/fable-fs-kickoff.md`: `order` is "**not** a nonce… EFS *wants* replay — cross-chain copy is a legal, identity-preserving re-submit"), so the attacker needs no cooperation from the original signer. This makes the claim "strictly stronger than Radicle's post-incident fix (prior-state binding)" wrong in exactly the direction Radicle chose parent-as-nonce to cover, and it contradicts this corpus's own lane verdict (`prior-art/radicle.md` §3: "must bind each snapshot to its **predecessor** — hash-chained head, monotonic counter, or on-chain anchor — from day one").
**Fix:** add `expectedPriorClaimId` (the kernel already exposes `priorClaimId` per slot, `Designs/efsv2/read-lens-spec.md` P8) or a per-`(repoId, refName)` monotone counter to the claim body; the fold applies only if the predecessor pointer equals the currently applied claim, and the vector suite (M2) gains delete→recreate, force-back, and tag-move replay cases.

[FATAL] [/Users/james/Code/EFS/planning-efs-git/Reviews/2026-08-07-efs-git-corpus/state-model.md §2 descriptor + §4 "Ordering"] Nothing pins *which* venue/lane/realm's ordinals the fold consumes, so "the same answer for every reader, forever" is unestablished and cross-venue equivocation is open.
```
