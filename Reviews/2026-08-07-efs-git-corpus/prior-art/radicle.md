# Radicle (Heartwood) — closest prior art for sovereign Git hosting

**Lane:** Radicle (radicle.xyz) as the closest prior art for sovereign Git hosting — researched 2026-08-07

Status legend used throughout: **[shipped]** implemented behavior, **[intent]** documented intent, **[rec]** recommendation of this lane, **[spec]** speculation.

## 0. Snapshot, August 2026

- Current release: **Radicle 1.10.0 "Sunflower", 2026-08-05** (commit `4641c342c689dd9c549af6c0235256fe225b53a7`); work on **Radicle 2.0** has started (master branch now targets 2.x, `releases/1` maintains 1.x) ([homepage](https://radicle.dev/), [1.10.0 notes](https://radicle.dev/2026/08/05/radicle-1.10.0.html)). [shipped]
- The project **moved domains in April 2026**: radicle.xyz → **radicle.dev** (project content) + **radicle.network** (hosted Radicle Explorer / repository content), after radicle.xyz landed on ISP blocklists (Swisscom, Telenor, Virgin Media, ~Oct 2025) apparently because of user content served via the public Explorer ([domain-move post](https://radicle.dev/2026/04/23/domain-move.html)). [shipped]
- In the same post the team states plainly that they **have blocked nodes and repositories on their own seeds** (iris/rosa) "if we felt that they were clearly overstepping boundaries, and we will continue to do so" — per-node content policy is the moderation model, and the team does not regard this as undermining censorship resistance ([domain-move post](https://radicle.dev/2026/04/23/domain-move.html)). [shipped]
- Stack: Rust reference implementation (`radicle-node`, `rad` CLI, remote helper, HTTPD, web UI, TUI), MIT/Apache-2.0, spec in Radicle Improvement Proposals (RIPs) ([protocol guide](https://radicle.dev/guides/protocol)). [shipped]

## 1. Architecture: Heartwood, RID, peer namespaces

- **Node identity**: Ed25519 keypair; Node ID (NID) = public key, encoded as `did:key`. Created offline, no registration. If the key is lost or compromised "one will have to generate a new node identity" — **no node-level key rotation**; multi-device identity sharing is "currently working on" ([protocol guide](https://radicle.dev/guides/protocol), [FAQ](https://radicle.dev/faq)). [shipped / intent]
- **Repository ID (RID)**: deterministically derived from the *initial* identity document — Git `hash-object` (160-bit SHA-1) of the canonical-JSON doc, multibase base58-btc, prefixed `rad:` as a URN (e.g. `rad:z3gqcJUoA1n9HaHKufZs5FCSGazv5`). The doc can change; the RID never does (RIP-2, [protocol guide](https://radicle.dev/guides/protocol)). [shipped]
- **Peer namespaces**: yes, literally `refs/namespaces/<NID>/…`. Storage is one **bare Git repo per RID**; every peer's view (their own and every followed peer's) lives as a namespaced ref tree (`refs/namespaces/<nid>/refs/{heads,tags,rad,cobs}`) sharing **one object database**, so each object is stored once across all views. A peer's namespace is described as their "soft-fork"; the peer is the sole authorized writer of it ([protocol guide — storage layout](https://radicle.dev/guides/protocol)). [shipped]
- **Git URL scheme**: `rad://<RID>/<NID>` addresses a specific peer's namespace; `rad://<RID>` with no NID addresses the repository's *canonical* refs (delegate-agreed state) via the `git-remote-rad` helper ([protocol guide](https://radicle.dev/guides/protocol)). [shipped]
- There is **no shared write access**: "Each user is required to push to their own namespace" ([FAQ](https://radicle.dev/faq)). Canonical state is *synthesized* from namespaces (§3). [shipped]

## 2. Signed refs (sigrefs): mechanism

Per the [March 2026 disclosure](https://radicle.dev/2026/03/30/disclosure-of-vulnerability-in-signed-references.html), which is the most precise public description: [shipped]

- Every time a user changes any ref (push, or any COB operation), Radicle writes a commit under `refs/namespaces/<NID>/refs/rad/sigrefs`. The commit's tree holds two blobs:
  - `refs` — a text snapshot of **all** of that user's refs with target OIDs, in `git show-ref` format (lexicographic), including COB refs;
  - `signature` — a binary **Ed25519 signature over the `refs` blob**, made with the namespace owner's key.
- The sigrefs commit history is the full audit log of a peer's ref changes; fetching accepts **fast-forward-only** advances of this history.
- During fetch, the node verifies each remote namespace's `rad/sigrefs` against that remote's public key; special refs (`rad/id`, `rad/sigrefs`) are fetched first, then data refs fetch exactly the objects listed in the verified sigrefs ([DeepWiki fetch-protocol page](https://deepwiki.com/radicle-dev/heartwood/5.3-fetch-protocol)). [shipped]
- Verification model is explicitly TUF-inspired: given an RID and a clone, anyone can authenticate the whole update history with no trusted third party ([protocol guide](https://radicle.dev/guides/protocol)). [shipped]

## 3. THE SIGNED-REFS REPLAY INCIDENT (Feb–Mar 2026)

Primary source: [Disclosure of Replay Attack Vulnerability in Signed References](https://radicle.dev/2026/03/30/disclosure-of-vulnerability-in-signed-references.html) (2026-03-30). No CVE identifier appears in the disclosure. [shipped]

- **Vulnerability**: the signature covered *only* the `refs` blob — **no nonce, no history binding**. Anyone could take any *older* `refs`+`signature` pair from a victim's sigrefs history and forge a new sigrefs commit as a child of the victim's latest commit. The forged commit propagates and is indistinguishable from an intended change. Attacks are scalable. Named consequences: make a repo appear empty/stale (replay the earliest state), or **pin a repo at a vulnerable state to block dissemination of a security fix**.
- **Timeline**: reported by community member Felix Bargfeldt (Defelo) 2026-02-14; exploit reproduced as E2E test by 2026-02-17; fix released in **1.7.0 (2026-03-18)** without disclosure to allow upgrades; **1.7.1 (2026-03-20)** compatibility fix; **1.8.0 (2026-03-30)** hardening; public disclosure 2026-03-30. All versions before commit `d3bc868e` (in 1.7.0) are vulnerable.
- **Fix**: a nonce inside the signed refs list itself — new internal ref `refs/rad/sigrefs-parent` whose target must equal the **parent commit OID** of the sigrefs commit. Parent-as-nonce was chosen over random nonces because (a) older nodes reject dangling refs, so the target had to resolve to a real object, and (b) verification is O(1) (parent known locally) instead of O(history) duplicate-scanning. Design admitted downside: internal refs are conflated with user-controlled refs in one list, and old versions display the internal ref as if user-created.
- **Prior related fix**: `refs/rad/root` (commit `989edacd`, Radicle 1.1.0, Dec 2024) already tied sigrefs commits to the repository identity root to stop **"graft attacks"**; a later code change (`09f79623`) silently disabled the backfill check, so repos initialized on 1.0.0 lacked `refs/rad/root` — this is what broke 1.7.0's hard error and forced 1.7.1.
- **1.8.0 "feature levels"**: monotonic levels `none < root < parent` detected per namespace; downgrade attacks detected by comparing head level vs. history; auto-migration writes a new parent-level sigrefs entry on node startup; new config `node.fetch.signedReferences.featureLevel.minimum` (default `none`; `root` blocks graft attacks, `parent` blocks graft+replay) plus per-command `--signed-refs-feature-level` escape hatch ([1.8.0 notes](https://radicle.dev/2026/03/30/radicle-1.8.0.html)). The default remaining `none` means **replay protection is opt-in at the fetch boundary** during the transition. [shipped]
- **Network scan**: 2026-03-30 scan of iris/rosa (7,090 / 7,073 repos, 9,212 / 9,174 namespaces): 477 "duplication clusters" in 228 namespaces, max cluster size 24 — but duplicates are necessary-not-sufficient evidence and legitimately arise from push/rollback/push; team concluded **no active malicious exploitation detected**. Legit "restore an earlier state" pushes are now silently *dropped* by replay detection — an acknowledged oddity.
- **Stated future** [intent]: replace bespoke sigrefs with **Git signed pushes / push certificates** (as used by the Linux kernel's transparency logs), supporting both formats for a long cross-compatibility window; removing sigrefs later is an accepted breaking change.

**Lesson for EFS** [rec]: any "signed snapshot of mutable refs" scheme must bind each snapshot to its predecessor (hash-chained head, monotonic counter, or on-chain anchor) from day one; Radicle shipped ~18 months (1.0.0 Sept 2024 → Feb 2026) with a replayable head, and the fix cost three emergency releases plus a permanent compatibility tax (feature levels, opt-in minimums, silently-dropped legitimate rollbacks). EFS's on-chain admission gives a total order for free — use it as the anti-replay backbone rather than reinventing per-peer nonce schemes.

## 4. Canonical refs: delegates, threshold, disagreement

- **Identity document** (canonical JSON, at `refs/rad/id`) holds `delegates` (list of DIDs — currently always `did:key`), `threshold`, and payloads incl. `xyz.radicle.project` (`name`, `description`, `defaultBranch`) ([protocol guide](https://radicle.dev/guides/protocol)). [shipped]
- **Default branch canonicalization**: the canonical head of `defaultBranch` is the commit that a `threshold` of delegates have converged on in their own namespaces; e.g. threshold 2-of-3 → when two delegates' `master` point at the same commit, that commit is canonical ([protocol guide](https://radicle.dev/guides/protocol)). [shipped]
- **Generalized canonical refs (Aug 2025, Radicle 1.3.0 / RIP-4)**: identity payload `xyz.radicle.crefs` defines per-refpattern rules `{allow: [DIDs] | "delegates", threshold: n}` (e.g. `refs/tags/releases/*` with 2-of-3 maintainers), so top-level `refs/tags/...` etc. are synthesized from namespace refs ([Canonical References post](https://radicle.dev/2025/08/12/canonical-references.html)). 1.9.0 added **symbolic** canonical refs ([1.9.0 notes](https://radicle.dev/2026/05/19/radicle-1.9.0.html)). [shipped]
- **Exact quorum algorithm** (from [`crates/radicle/src/git/canonical/quorum.rs`](https://github.com/radicle-dev/heartwood/blob/master/crates/radicle/src/git/canonical/quorum.rs), master @ 2026-08): each allowed key's head is a vote; candidates must reach `threshold` votes; the winner is then computed by walking merge-bases — a candidate that is a *descendant* of the current best extends it; an ancestor is ignored; if the merge base is **neither** candidate (true divergence), the computation returns `CommitQuorumFailure::DivergingCommits` and **no canonical ref is produced/advanced**. Tag rules fail with `DivergingTags` if more than one tag object passes threshold; `NoCandidates` if nothing reaches threshold. [shipped]
- So **on delegate disagreement the canonical ref simply stalls** at its previous value (or never materializes); nothing forks automatically, and there is no built-in resolution ceremony beyond delegates converging their branches. [shipped]

## 5. Identity documents & authority rotation

- The identity document is itself a COB (`xyz.radicle.id`); changes are proposed as **revisions** via `rad id update`, and only existing delegates may create revisions (enforced with clear errors since 1.7.0). Adding rules/delegates "is necessary to reach a majority quorum" of delegates ([Canonical References post](https://radicle.dev/2025/08/12/canonical-references.html), [1.7.0 notes](https://radicle.dev/2026/03/18/radicle-1.7.0.html)). Ownership changes are "signed by previous owners forming a verifiable chain of provenance" ([FAQ](https://radicle.dev/faq)). [shipped]
- **1.10.0 (Aug 2026) reworked identity-revision evaluation** after real-world inconsistencies (including on heartwood itself): revisions now form an explicit parent/child chain (no merges); states are Active / Accepted / Rejected (direct, transitive via rejected parent, or via an accepted sibling) / Redacted; a delegate may not accept two sibling revisions (prevents two revisions both reaching majority and being picked arbitrarily by topological sort). The team **openly documents a remaining unfixed inconsistency**: concurrent `redact` + `accept` produce order-dependent results. A network scan found ~15 of "several thousand" repos whose evaluated identity changed under the new rules ([1.10.0 notes](https://radicle.dev/2026/08/05/radicle-1.10.0.html)). [shipped; the redact/accept gap is acknowledged open work]
- **Hard limits**: identity = device key (`did:key` only); no social/organizational identities yet (LWN notes no group support: [LWN article](https://lwn.net/Articles/966869/)); abandoned-repo takeover is impossible by design — you `rad init` a fork with a **new RID/new root of trust** and re-communicate it ([FAQ](https://radicle.dev/faq)). [shipped]

**Lesson for EFS** [rec]: CRDT-evaluated governance documents are where Radicle keeps finding bugs (two forSchema-style evaluation reworks in one year; an admitted unresolved concurrent-op ambiguity). EFS's KEL/on-chain ordering can make authority-document evaluation *sequential and total*, which removes this entire bug class; keep delegate-set changes strictly ordered on-chain even if content refs stay off-chain.

## 6. COBs (Collaborative Objects)

- Types: `xyz.radicle.issue`, `xyz.radicle.patch`, `xyz.radicle.id`; stored under `refs/cobs/<typename>/<id>`, type names in reverse-DNS (RFC-1035 length limits enforced since 1.7.0); user-definable new types with no network coordination ([protocol guide](https://radicle.dev/guides/protocol), [1.7.0 notes](https://radicle.dev/2026/03/18/radicle-1.7.0.html)). [shipped]
- Data model: each COB is a **DAG of Git commits** (one commit per change, per author); sync = union of graphs (idempotent, CRDT-like); state = deterministic causally-consistent topological reduce from root to tips, with a per-type merge function (simplest: order concurrent ops by commit hash) or surfaced conflict if no merge function is defined. Issues' graphs point at the identity graph; patches' graphs point at both identity and source commits (enables merged-detection) ([protocol guide](https://radicle.dev/guides/protocol)). [shipped]
- Known limitations: append-only and permanent (LWN and its commenters: no real deletion, "no mechanism for proper moderation," permanent records of harmful content, data bloat: [LWN](https://lwn.net/Articles/966869/)); spam model is purely social — don't follow the spammer and their namespace never replicates to you ([FAQ](https://radicle.dev/faq) on abuse; earlier design discussion in [radicle-link RFC-0662](https://github.com/radicle-dev/radicle-link/blob/master/docs/rfc/0662-collaborative-objects.adoc), which also records the ref-advertisement scalability worry: 10k issues ≈ 10k refs ≈ 2.5 MB advertisement under Git protocol v1). [shipped / known-limitation]

## 7. Seeding, gossip, private repos

- Gossip: three message types (Node / Inventory / Refs announcements), all signed+timestamped; refs announcements carry `(NID, sigrefs OID)` pairs per RID and are relayed only to interested nodes. Transport: Noise **XK** (Lightning-style), multiplexed so concurrent Git fetches share the gossip connection. Bootstrap: `iris.radicle.network`, `rosa.radicle.network` (renamed from .xyz in 1.9.0). Tor supported; **I2P added in 1.9.0**; per-stream fetch timeouts tunable for Tor/I2P in 1.10.0 ([protocol guide](https://radicle.dev/guides/protocol), [1.9.0](https://radicle.dev/2026/05/19/radicle-1.9.0.html), [1.10.0](https://radicle.dev/2026/08/05/radicle-1.10.0.html)). [shipped]
- Availability model: a repo exists on the network **only while ≥1 seeder is online**; NAT'd peers depend on seed nodes (hole-punching "under development" — [FAQ](https://radicle.dev/faq)). [shipped / intent]
- **radicle.garden (June 2026)**: paid, always-on hosted seed nodes operated by The Better Internet Foundation (Swiss non-profit; EU-hosted), explicitly framed as the protocol's sustainability path — "non-profit, not a VC-backed startup" ([garden announcement](https://radicle.dev/2026/06/02/announcing-radicle-garden.html)). [shipped]
- **Private repos**: `visibility: {type: "private", allow: [DIDs]}` in the identity doc; privacy = **selective replication only — data is NOT encrypted at rest**; invisible to non-allowed nodes; delegates always have access ([protocol guide](https://radicle.dev/guides/protocol), [FAQ](https://radicle.dev/faq)). [shipped]
- Since 1.9.0 nodes advertise their Radicle version in the gossip user-agent for network telemetry (opt-out via `node.userAgent = null`) ([1.9.0](https://radicle.dev/2026/05/19/radicle-1.9.0.html)). [shipped]
- Blocking got teeth in 1.7.0: `rad block` now rejects connections, not just refs ([1.7.0](https://radicle.dev/2026/03/18/radicle-1.7.0.html)). [shipped]

## 8. Adoption & health, 2026

- **Scale (self-reported, April 2026)**: "almost 8000 repositories and more than 600 nodes online on a weekly basis" on team-operated public seeds (a subset of the network); **~12 people** across protocol/CLI/TUI/web/ops/content; codebase ~4 years old, problem worked on 6+ years ([FAQ](https://radicle.dev/faq)). Consistent with the disclosure scan (7,090 repos on iris in March 2026) and 1.10.0's "several thousand repositories". [shipped]
- Cadence is healthy: 1.6.0 (Jan), 1.7.0/1.7.1 (Mar), 1.8.0 (Mar), 1.9.0/1.9.1 (May), 1.10.0 (Aug 2026); Radicle Desktop GUI shipped June 2025; Radicle 2.0 development underway; ~11–16 contributors per release ([homepage updates list](https://radicle.dev/)). [shipped]
- **Funding**: grants from **Radworks** (the RAD-token DAO); the FAQ now stresses "Radicle itself is a true peer-to-peer protocol and does not use or depend on any blockchain or cryptocurrency," and radicle.garden subscriptions are the new non-profit revenue path via the Better Internet Foundation (ex-Radicle Foundation) ([FAQ](https://radicle.dev/faq), [garden post](https://radicle.dev/2026/06/02/announcing-radicle-garden.html), [Radworks docs](https://docs.radworks.org/rad-token/), [Better Internet Foundation](https://betterinternet.foundation/about.html)). The visible arc: crypto-funded origins → deliberate distancing from crypto branding → conventional hosted-service sustainability. [shipped / intent]
- **What users complain about** (third-party, 2026): web interface is read-only — reporting a bug requires installing the CLI/desktop app ("Someone encountering a bug should not have to install the forge's software merely to report it"); no releases, no package registry, CI only via community projects; overall "too immature to replace GitHub for a public project" ([lalitm.com, Aug 2026](https://lalitm.com/post/github-alternatives/)). HN threads through 2025–26 echo discoverability worries ("it will be hard for people to find your project"), conceptual overhead ("too much mental gymnastics" — [HN comment](https://news.ycombinator.com/item?id=48582977)), and seeding-model rough edges ([HN thread](https://news.ycombinator.com/item?id=48147603)). Search/discovery is "basic … still a work-in-progress" per the team itself ([FAQ](https://radicle.dev/faq)). [known-limitation]

## 9. What Radicle does NOT solve (explicit)

- **Storage durability / permanence**: none. Availability = at least one online seeder; no incentive or payment layer for seeding; the answer to durability is "run/pay for an always-on node" (radicle.garden). No archival guarantee whatsoever ([FAQ](https://radicle.dev/faq), [garden post](https://radicle.dev/2026/06/02/announcing-radicle-garden.html)). This is precisely the hole EFS's on-chain + Arweave + mirror stack fills. [shipped-gap]
- **Anonymous web reading**: partially. Reading via P2P requires running a node; casual web reading goes through hosted Explorer gateways (radicle.network), which are centralized chokepoints — demonstrated by the radicle.xyz ISP-blocklisting and the team's own seed-level content blocking ([domain-move post](https://radicle.dev/2026/04/23/domain-move.html)). Tor/I2P help node operators, not browser-only readers. [shipped-gap]
- **Payments / funding rails**: none in-protocol; deliberately blockchain-free. Drips (streaming funding) is a separate Radworks project, not integrated into the forge ([FAQ](https://radicle.dev/faq), [Radworks docs](https://docs.radworks.org/rad-token/)). [shipped-gap]
- **Global human-readable naming**: none. RIDs are unmemorable URNs; node aliases are explicitly non-unique; no name registry; forking an abandoned repo mints a *new* RID that must be socially re-announced ([protocol guide](https://radicle.dev/guides/protocol), [FAQ](https://radicle.dev/faq)). EFS/ENS-style naming is complementary, not competitive. [shipped-gap]
- **Identity recovery & multi-device**: lost key = new identity; one identity per device today; group/org identities absent ([FAQ](https://radicle.dev/faq), [LWN](https://lwn.net/Articles/966869/)). [shipped-gap]
- **Deletion / moderation / legal compliance**: append-only signed history with no erasure mechanism; moderation is per-node blocking only ([LWN](https://lwn.net/Articles/966869/), [FAQ](https://radicle.dev/faq)). [shipped-gap]
- **Large binaries**: git-annex/git-lfs support only "considering" ([FAQ](https://radicle.dev/faq)). [intent]

## 10. Direct takeaways for EFS Git hosting [rec]

1. **Reuse the namespace pattern**: per-principal `refs/namespaces/<principal>` over one shared object DB is proven, Git-native, and maps cleanly onto EFS principals/actor keys; canonical refs as a *derived* function over namespaces (rules = {pattern, allowed-set, threshold}) is directly portable to an EFS lens.
2. **Anchor ref heads with total order**: the sigrefs replay incident is the cautionary tale; EFS's chain gives replay/downgrade protection natively — publish (principal, repo, sigrefs-head, seq) as signed records and the whole feature-level machinery becomes unnecessary.
3. **Expect canonical-ref stalls**: threshold quorum with divergence = explicit failure and no progress; EFS should decide up front what a wiki does when editors diverge (Radicle's answer — stall silently — is poor UX for Wikipedia-style editing).
4. **Keep governance evaluation ordered, not CRDT**: Radicle's identity-COB evaluation needed a major rework in 1.10.0 and still has an admitted order-dependent ambiguity; EFS should serialize delegate-set changes on-chain.
5. **COB-style typed DAGs work for issues/patches** and map well to EFS typed records, but plan for permanence/moderation/pruning from day one — Radicle's append-only model has no answer and third parties call it out.
6. **Gateways are the censorship surface**: Radicle's own domain got ISP-blocked over gateway-served content and the team splits "about" from "content" domains and blocks content on its own seeds. EFS's anonymous-reading story must assume gateway takedowns and make gateway replacement trivial (many independent read gateways, web3://-style zero-infra reads).
7. **Radicle's unsolved list (durability, payments, naming, recovery) is EFS's value proposition** — the two systems are more complementary than competing, and Radicle's ~8k-repo/600-node scale after 2 years post-1.0 with ~12 staff calibrates realistic adoption for sovereign forges.
