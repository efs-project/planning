# ArDrive Private Drives — The Privacy Product Experience

Lane report for the EFS Files competitive teardown. Product/UX angle only; ArFS internals covered elsewhere. All claims dated. Primary sources: the shipped app's own UI strings and code (ardriveapp/ardrive-web, `dev` branch, accessed 2026-07-29), current docs at docs.ar.io, archived help-center articles (help.ardrive.io is dead — see Findings §7), release notes, and third-party reviews.

## Summary

ArDrive's private drives are the most complete encrypted-folder experience shipped on permanent storage, and parts of it are genuinely well made: encryption is invisible in daily use, private files get encrypted thumbnails decrypted client-side, drives default to private, and the no-delete warnings are some of the bluntest copy in web3. But the privacy product is built on a single fateful decision the user makes at login — a password that "can never be changed, reset, or recovered" — presented as a routine signup step with no strength check, no forced backup, and no recovery ceremony of any kind. One password does double duty for session security and data encryption across *all* private drives; a per-drive-password retrofit (which also fixes drive keys persisting after logout) has sat unmerged since September 2025. The recovery story is "don't lose anything": lose the password → data unrecoverable; lose the wallet → data unrecoverable; and in 2025 users learned a third way to lose data — their *wallet vendor* deprecating a signing API, which forced an on-chain "Update Now!" re-keying ceremony with an open-ended deadline. Sharing a private file means pasting a bearer link containing the raw decryption key — simple, but irrevocable and re-shareable forever. "Delete" does not exist even as key destruction: keys are deterministically re-derivable, so there is no crypto-shredding story at all, only "hide." Meanwhile the help center that documented all these rules was deleted in late 2025 and the mobile app was sunset, leaving a one-sentence login warning as the entire user-facing recovery education.

## Findings

### 1. Context: who ships this today

ArDrive is alive and actively developed under the AR.IO umbrella (X handle is now "ArDrive.ar.io"; ar.io publishes an ArDrive case study). Web releases are frequent through July 2026 (v2.85.0, 2026-07-03). The mobile apps were sunset on 2025-10-30 ("we're focusing our energy on improving the web experience," X announcement 2025-10; app removed from Google Play 2025-10-08), and the Zendesk help center was removed in v2.75.0 (2025-10-31); help.ardrive.io no longer resolves (DNS NXDOMAIN, checked 2026-07-29). So the private-drive experience today is web-only, documented only in developer-oriented ArFS docs on docs.ar.io.

### 2. The setup ceremony: the fateful password is set at *login*, not at drive creation

This is the most important product fact in this lane and it is easy to miss: **the encryption password is chosen during onboarding, before the user has created anything.** When you log in with a keyfile/seed phrase (or an Ethereum/Solana wallet since v2.82), a "secure your wallet" modal asks you to create a password. The exact current copy (`secure_your_wallet_modal.dart`, dev branch, accessed 2026-07-29):

> "Please enter and confirm a password to secure your wallet. This password is used to encrypt your private files, and can never be changed, reset, or recovered. Be sure to store it somewhere safe."

Returning users see: *"We found your drives! Enter a password to encrypt your private files. This password can never be changed, reset, or recovered."* EVM/Solana users see: *"ArDrive creates a secure storage wallet linked to your Ethereum wallet. Enter a password to encrypt your private files…"*

Observations on the ceremony as the user experiences it:

- **One sentence is the entire warning.** There is no forced write-it-down step, no key-file download, no confirmation quiz, no recovery-phrase equivalent. Compare to any wallet onboarding, which makes you re-enter a seed phrase. Here the thing being created is *equally unrecoverable* and gets a line of body text.
- **No password strength enforcement.** Code inspection of the login modals found only "cannot be empty" and "passwords must match" validation — no strength meter, no minimum length (accessed 2026-07-29). For a password that is key material for permanent ciphertext, this is weak.
- **The password does double duty**, and the copy says so if you read closely: it encrypts the wallet at rest on the device *and* is entropy for private-drive keys. The (now-deleted) help article "ArDrive Password" (archived, updated 2024-07-29) was explicit: "Encrypting your wallet at rest and as also serving as entropy for encrypting Private Drives… This password cannot be reset or changed if you make a Private Drive during your session… there is no recovery mechanism. If this password is lost, you will not be able to decrypt your Private Drive data!" And, tellingly: "Accounts that don't create private Drives can use different passwords" — i.e., the password is mutable *until* your first private drive, then frozen forever. This state-dependent rule is nowhere in the current product.
- **Creating the drive itself is anticlimactic.** The New Drive dialog is a name field and a Public/Private dropdown — **defaulting to Private** (confirmed in current code: `privacy ?? DrivePrivacy.private`). Selecting Private shows only: "Private Drives offer state-of-the-art security, you control access." No password prompt (it was captured at login), no warning about password loss at the moment it becomes irreversible. Private-by-default is a good, opinionated choice; burying the irreversibility is not.
- **Wallet + password are both required.** Drive keys combine the wallet signature, the user password, and the drive ID (docs.ar.io ArFS privacy page, accessed 2026-07-29). Users are never told this dependency exists in the app itself.

### 3. One master password for everything — and the retrofit that hasn't shipped

Today's shipped model: a single profile password gates the session and derives keys for **all** private drives. Open PR #2076 ("implement per-drive password system," opened 2025-09-22, still open as of 2026-07-29) states the plan bluntly: "Users must now set individual passwords for each private drive instead of relying on a single master password," and — buried in the same PR — "Fixes security issue with drive keys persisting after logout." Two takeaways: (a) the vendor itself considers the single-master-password model a design mistake worth a breaking change; (b) as of today the shipped app has a known issue where drive keys outlive logout. Neither is communicated to users.

### 4. Day-to-day private UX: mostly invisible, which is the point — with real caveats

- **Unlock is per-session, once.** Enter the password at login; every private drive opens without further prompts. Drive keys are cached locally, encrypted under the profile cipher key (visible throughout the code, e.g. `getDriveKey(driveId, currentUser.cipherKey)`). Wrong password → "This password is incorrect." — the app validates against existing private drives, so you cannot accidentally start a divergent password on a new device if you already have private drives. Biometric unlock existed only on mobile, which is now sunset.
- **Encrypted thumbnails work.** This is genuinely better than typical web3 apps: private files get thumbnail variants that are themselves encrypted with the file key; the app downloads ciphertext and decrypts to memory client-side (`thumbnail_repository.dart`: private branch fetches cipher/IV tags and calls `downloadToMemory` with the file key; public branch just uses a gateway URL). Previews likewise decrypt in-browser. A private drive does not feel like a pile of grey lock icons.
- **Private uploads are the only size-gated path.** The upload flow runs a file-size check *only* for private uploads (`checkFilesAboveLimit` gates on `_isAPrivateUpload()`, limit currently 65 GiB). The stale UI copy is a fossil: the too-large dialog still says "ArDrive on web currently only supports file uploads smaller than 100 MiB for private drives" (public variant: "1.20 GiB") — both wildly out of date versus the archived App Limits article (updated 2024-01-02: 65 GiB direct-to-network, 10 GiB Turbo, "apply to both public and private files"). The 100 MiB string is a leftover from the era when browser-side encryption genuinely capped private uploads — evidence that private uploads historically lagged public ones badly, and that error-path copy rots.
- **Sync performance was bad until very recently.** v2.85.0 release notes (2026-07-03) admit incremental sync previously took "130 GraphQL calls / 376 seconds," now "3 calls / <1 second." Users with large drives — private drives especially, since every metadata record must be fetched and decrypted client-side before the file tree renders — sat through multi-minute spinners for years. The fix is real but recent; expect user memory of ArDrive private drives to include "slow to open."
- **Ecosystem asymmetry:** private files are invisible to the rest of the permaweb tooling (gateways, manifests, ArNS names, public preview pages all assume public data). The product handles this by simply not offering those affordances for private items. Historically private drives even broke third-party tools — ArConnect's drive picker infinite-looped on wallets with private drives until it filtered to public only (wanderwallet/Wander#21, June 2021).

### 5. Sharing a private file: a bearer key in a link, forever

The share flow for private items generates a link with the **raw key, base64, in the URL** (`link_generators.dart`): `/#/file/{id}/view?fileKey=<base64>` for files; the drive share appends `&driveKey=<base64>`. Everything rides after the `#`, so keys aren't sent to the web server on load — a sensible touch the product never explains. The share dialog's copy is admirably blunt: *"Anyone can access this private drive using the link above."*

The (archived) Drive Sharing article (updated 2023-11-04) was similarly honest: "the 'drive key' is included in the copied link. This enables someone to view the Drive without having access to your wallet, or drive password. Make sure you know & trust who you're sharing your Private Drive & Files with… It is not recommended to share Private Drives & Files on public platforms." And File Sharing (2023-06-14): recipients "will have access to the file forever… Whomever you share a link with can also share that link with others." The promised "option to limit the spread of link sharing in future versions" never shipped (checked 2026-07-29).

Product consequences the copy does *not* spell out:

- **No revocation, ever.** Not "hard to revoke" — cryptographically impossible. There is no re-key/rotate feature.
- **Sharing a drive key shares the future.** File keys derive from the drive key, so a shared drive key opens files uploaded *after* the share too. No warning mentions this.
- **Keys travel like URLs travel** — chat previews, browser history, server logs of anything that unfurls links. "Don't post it publicly" is the entire mitigation.
- **The recipient has no durable relationship to the data.** "If the recipient of this drive key loses it, they will no longer be able to access the private drive" — shared access is a string someone must file away.

### 6. The recovery story: there isn't one — and 2025 added a third failure mode

- **Lose the password:** permanent loss of all private-drive plaintext. Stated once at signup and (formerly) in a help article. No hint feature, no escrow, no social recovery, no partial recovery. The only "reset" path — forget wallet, log in again, pick a new password — is explicitly blocked once private drives exist (the app validates the password against them).
- **Lose the wallet (keyfile/seed):** same outcome, even *with* the password, since drive keys require a wallet signature. The keyfile help article: your wallet "cannot be recovered by ArDrive." No user-facing document connects "lose wallet" → "lose private drives"; users must infer it.
- **Your wallet vendor changes an API:** the failure mode nobody designs for, and it actually happened. Wander (ex-ArConnect) deprecated its `signature()` method; drive keys for Wander users were derived through it. ArFS v0.15 added a "Drive-Signature" entity to bridge old keys to new signing APIs, and the app grew an "Update Now!" banner ceremony — log in, click, sign N messages, pay nothing, hope you do it before the wallet removes the old API. The docs state: "There is, at this time, no set date for when the deprecation period will end" (docs.ar.io "Upgrading Private Drives," accessed 2026-07-29). Users who never log in during the window risk drives their wallet can no longer derive keys for. The upgrade guide's advice — "Backup your data — ensure you have access to your drive contents" before upgrading — is the closest thing to a documented recovery ceremony in the entire product, and it's really an *avoidance* ceremony.
- **No key-export-as-backup feature.** A user *can* effectively back up a drive key by saving their own private share link, but nothing frames this as backup; it's an accident of the sharing design.
- **Complaint evidence is thin — by structure, not necessarily by absence.** GitHub issues contain essentially no lockout reports (one 2021 issue mentioning passwords at all); Trustpilot had a single review; support ran through Zendesk (deleted 2025) and Discord (unsearchable). I could not verify real lockout complaints from public sources (searched 2026-07-29) — but the channels where they would have appeared no longer exist publicly. Third-party assessment concurs on the risk: CryptoAdventure's 2026 review flags that "losing keys can mean losing practical access" and calls ArDrive "not a solution for data that must be deleted."

### 7. What "delete" means for private data — and the honesty audit

- **There is no delete, and no crypto-shredding either.** The only affordance is "Hide" (files, folders, and now drives), a metadata revision that filters items from view — "Reveal hidden items" undoes it. Because drive/file keys are *deterministically re-derivable* from wallet + password + IDs, the owner cannot even destroy their own keys to render data unreadable. Key-destruction-as-erasure is not a ceremony ArDrive can offer; the product never discusses this.
- **Where the copy is honest — genuinely, unusually honest:** onboarding says "Remember: There is no delete button (for you or us)!", "Once uploaded, your data can't be removed," and even "Think twice before uploading all your teenage love poetry…". Public uploads warn: "Files uploaded here will be permanently viewable by anyone on the internet." The old help center: public "will always be public. There is no way to undo this." This is better permanence honesty than almost any competitor.
- **Where the copy oversells:** marketing strings promise "Total Privacy Control," "No one will see what you don't want them to," and docs claim "military grade (and quantum resistant) encryption." Nothing user-facing acknowledges what stays public forever about a private drive: the wallet that paid, upload timestamps, ciphertext sizes, revision cadence, drive IDs — the entire traffic-analysis surface — or that today's ciphertext is a permanent harvest-now-decrypt-later target. The deleted help center even answered "Can my private documents stay private forever?" with "Yes." The gap between "no delete button" honesty (excellent) and ciphertext-permanence honesty (absent) is the single most instructive copy lesson in this product.
- **Hiding is itself a recorded event** — a new revision written to Arweave (encrypted for private drives, public for public ones). Users are not told that "hide" leaves a permanent trace.

### 8. Documentation and support as part of the safety system — currently failing

Every rule above — password immutability, the both-keys-required model, sharing permanence — was documented in the Zendesk help center, which was deleted (v2.75.0, 2025-10-31); the domain is dead. Current docs.ar.io ArFS pages are developer-oriented and contain **no user-facing recovery guidance at all**. For a product whose worst-case outcome is irreversible loss of a user's data, the entire recovery education is now one sentence in a login modal. The mobile sunset (2025-10-30) also removed the only biometric-unlock path.

## Strengths

- **Private by default.** New drives default to Private; an opinionated, user-protective choice most storage products don't make.
- **Encryption that disappears in daily use.** One unlock per session; encrypted thumbnails and previews decrypted client-side make private drives feel like normal folders. Verified in code, not just marketing.
- **Blunt, funny, effective permanence copy** for the no-delete reality — "There is no delete button (for you or us)!" is the best line in the category.
- **Honest share-dialog copy**: "Anyone can access this private drive using the link above" tells the user exactly what a bearer link is, in nine words.
- **File-level share granularity**: sharing one file doesn't expose the drive — surfaced simply in the product ("share this file" vs "share this drive").
- **When the wallet-API crisis hit, they shipped a real migration**: a one-banner, click-and-sign upgrade ceremony rather than telling users to move data. The execution was decent even though the situation should never have been possible.
- **Keys stay client-side**: password never uploaded; share keys ride URL fragments, not query paths that hit servers.

## Weaknesses / user pain

- **A permanent, unrecoverable password created as a throwaway signup step** — no strength check, no forced backup, no rehearsal, warning buried in body text. The entire catastrophic-loss surface is delegated to one modal.
- **One master password for session + all drives**, unchangeable forever after the first private drive; the vendor's own per-drive retrofit (and a fix for keys persisting after logout) unmerged for 10+ months.
- **No recovery ceremony exists** for any failure mode: password loss, wallet loss, or wallet-API change. The Wander episode proved keys derived from wallet signatures inherit the wallet vendor's roadmap as a threat model — with an open-ended deadline users may miss.
- **Irrevocable, silently future-inclusive sharing.** Drive-key links grant access to files uploaded later; nothing can be revoked or rotated; the mitigation is "trust who you share with."
- **No deletion story for private data at all** — not even key destruction; "hide" is cosmetic and itself permanently recorded.
- **Privacy marketing overpromises** ("Total Privacy Control," private "forever") while the permanent public metadata surface goes unmentioned.
- **Years of slow sync** on large (especially private) drives, only fixed mid-2026; stale error copy (100 MiB) still shipping.
- **Safety documentation deleted**: help center gone, mobile gone, recovery rules now live nowhere a user can find them.

## Implications for the EFS file browser

1. **Separate session unlock from data-encryption secrets, and make rotation a design requirement.** ArDrive's one-password-for-everything model produced an unchangeable password and a breaking-change retrofit years later. EFS Files should never let the credential that opens the app be the credential that derives container keys, and every private container should be re-keyable (new key envelope, re-wrap, without re-uploading ciphertext).
2. **Run the key ceremony at private-folder creation, not at login — and make it a real ceremony.** The moment a user creates their first private folder is the moment to force a backup artifact (downloadable key file / recovery phrase), require acknowledgment of no-recovery, and rehearse recovery once. One sentence in a signup modal is the anti-pattern.
3. **Treat wallet-derived keys as versioned and migratable from day one.** The Wander `signature()` deprecation is a preview of EFS's own risk surface (wallet API changes, smart accounts/ERC-1271, account migration — directly relevant to the v2 native-carrier identity work). Ship key envelopes with explicit derivation versions and design the "Update Now!" re-key ceremony *before* it's an emergency; never leave the deadline open-ended.
4. **Bearer-key share links are the right floor, not the ceiling.** Copy ArDrive's honesty ("Anyone with this link…") and fragment-side key placement, but fix the two silent failures: warn that a container key includes *future* files, and prefer per-item wrapped keys so drive-wide grants are deliberate. Design revocation-by-re-key even if v1 doesn't ship it — retrofitting is what ArDrive couldn't do.
5. **Give private data an erasure story ArDrive can't have.** If EFS containers use random (non-derivable) keys wrapped to the user, key destruction becomes honest practical erasure of mirrored ciphertext — a real differentiator, with UI copy that's straight about what remains (sizes, timing, structure, on-chain records, and any plaintext ever shared).
6. **Be honest about ciphertext permanence up front.** Match ArDrive's no-delete bluntness, then exceed it: at private upload time, say plainly that encrypted bytes, sizes, and timing are public forever and that encryption is a bet against future cryptanalysis. Burying this is a trust time bomb.
7. **Encrypted previews are table stakes.** ArDrive ships client-side-decrypted thumbnails/previews for private files; a private folder in EFS Files that renders as generic lock icons will read as inferior on contact.
8. **Docs are part of the safety system.** ArDrive deleted the only pages documenting its recovery rules. EFS recovery/permanence documentation should live somewhere as permanent as the product's promises — ideally on EFS itself.
