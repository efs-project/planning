# ArDrive Teardown — Lane: Core Drive/File-Management UX (Web App)

Researched 2026-07-29. Primary sources: ardrive-web GitHub repo (code on `dev` branch, release notes through v2.85.0, issues), archived help.ardrive.io articles (the live help center is **dead** — DNS no longer resolves as of 2026-07-29; articles retrieved via Wayback Machine), ardrive.io marketing site. ArDrive web app is at v2.85.0 (2026-07-03) with v2.86.0 releasing the week of 2026-07-29.

## Summary

ArDrive's web app is a deliberately conventional "Google Drive on Arweave": multiple named drives per wallet, folders, breadcrumbs, a details panel, and a big red +NEW button. Its two genuinely distinctive UX moves are (1) blunt permanence honesty — the product literally tells users "There is no delete button (for you or us)!" and replaces delete with an on-chain "Hide" — and (2) automatic file versioning keyed on a stable File-Id, where uploading a same-named file prompts a "new version?" flow and history lives in an Activity tab. Its defining weakness is that the blockchain leaks into the file browser constantly: a three-color status dot (green/mined, orange/pending, red/failed) that has historically shown *false* failures during gateway unbundling; a local-database sync architecture so slow that a no-change sync took 130 GraphQL calls and 376 seconds until a July 2026 overhaul cut it to under a second; "Drive Not Synced" gates that block browsing; and a paid "Snapshot" feature users are nudged to buy just to make their own drives sync faster. The company (originally Permanent Data Solutions, now the AR.IO team, with ArDrive as flagship dApp) retreated to web-only in October 2025, sunsetting mobile and tearing down its Zendesk help center — the product is actively maintained but the support surface has thinned dramatically. Upload limits are generous (65 GiB/file); browser download limits are not (500 MiB on Chrome), an asymmetry the app never explains.

## Findings

### 1. Mental model: wallet → drives → folders → files

- A **drive is the top-level container**, and an account (wallet) can create unlimited drives, each independently **public or private at creation time** — privacy is a drive-level property, not per-file. "ArDrive is built around 'Drives' — permanent digital storage containers… You must create a Drive before you start uploading your files." (help: *Create New Drive*, updated 2023-05-12, via Wayback). New drives default to private.
- The sidebar lists **Personal Drives** and **Shared Drives** separately. Foreign drives are added via "Attach a Drive" — either by clicking a share link (auto-attach) or pasting a 36-char Drive ID via +NEW; the attacher can locally rename an attached drive, and drives can be detached ("Are you sure you want to detach '{driveName}'?" — app_en.arb, accessed 2026-07-29). Attaching and downloading are free.
- The **+NEW button** is the single creation hub: New Drive, New Folder, Attach Drive, Upload File(s), Upload Folder, Create Manifest, Create Snapshot (help: *The New Button*, 2023-06-14; `uploadFolder` string in app_en.arb). Note that two of the seven are power-user permaweb primitives (manifests, snapshots) sitting right next to "New Folder" — the abstraction is thin by design.
- Navigation is click-into-folder with **breadcrumbs** in the top bar (help: *New Folders*, 2023-07-17). The file list is a data table with Name / File size / Last updated columns (arb strings). No grid/gallery view strings were found in the current localization file.
- Public-drive permanence warning appears at creation: "If you select 'Public' you are giving access to all files in the Drive to everyone forever. An automatic URL will be created for this Drive and this URL cannot be deleted… Be careful! If you accidentally publish your information to a public Drive there is no delete button." (help: *Create New Drive*).

### 2. Upload UX

- Flow: pick drive → +NEW → Upload File(s)/Upload Folder → app **calculates cost and shows a confirmation modal** listing files, sizes, and one-time price before anything is sent; cancel is free (help: *Uploading Files*, updated 2023-07-19). Small files ride Turbo's free allowance and show "Cost: 0 AR — This small transaction is free thanks to Turbo"; when the allowance is exhausted the app says "Your free upload allowance has been used up, so this action now requires Credits" (app_en.arb).
- **Drag-and-drop works for multiple files but NOT folders**: the app ships the string "We do not currently support drag and drop with folders" (app_en.arb, accessed 2026-07-29). Folder upload exists only via the +NEW picker. Drag-and-drop has a long bug history (wrong content-type v2.22.1 2023-10; "Drag and drop still broken" #227 2021; crash on folder DnD #231).
- **Size limits (current code, `lib/blocs/upload/limits.dart`, dev branch 2026-07-29)**: hard per-file limit **65 GiB**, soft warning at **5 GiB** ("We do not recommend uploading items over {size} in size"), Turbo bundle cap 10 GiB, direct-to-network bundle cap 65 GiB, max 250 files per bundle. The old public help numbers (500 MB Turbo public / 100 MB private) are stale. Telling detail: a user asked "what is the maximum file size?" in GitHub issue #2098 (2025-11-25) and **never got an answer** — the real limits are only discoverable in source code.
- **Progress and resilience**: an upload progress indicator only arrived in v2.5 (2023-07-13). Docs warn "Do not leave from the uploading screen until the upload completes. If you exit the browser before it has completed your file will not be uploaded… any progress will be lost" (help: *Uploading Files*) — i.e., **no resumable uploads and no background upload**. A "Retry Failed Uploads" modal for conflicted/failed bulk uploads landed v2.51 (2024-08-26). v2.86 (in flight, PR #2161, 2026-07-04) parallelizes the upload preparation pipeline — cost estimation/hashing before upload is evidently a known bottleneck.
- **Bulk upload conflicts**: same-named files trigger a per-file conflict list ("Conflicting files:") with the choice to skip or upload as new versions (skip option since v1.10, 2022-03-22). Same-named **folders hard-fail**: "A folder with the same name already exists at this location. Please rename it and try uploading again" — no merge, no folder versioning (app_en.arb).

### 3. Versioning

- Uploading a file with the same name into the same folder **automatically creates a new version** under the same File-Id; the UI asks "A file with the same name already exists at this location. Do you want to continue and upload this file as a new version?" (app_en.arb; help: *New File Versions*, 2022-08-09). No version limits; every version stores full data (no delta).
- Version history lives in the file's **details panel → Activity tab**: a reverse-chronological list of revision events ("This file was created with the name…", renamed, moved, hidden, new version uploaded), each file revision row carrying a download/preview action menu (`details_panel.dart`, `_buildFileActivity`/`_FileRevisionOptions`, dev branch 2026-07-29).
- **No one-click restore.** You can download or preview an old revision, but there is no "make this the current version" action anywhere in code or docs — restoring means manually re-uploading the old bytes as a new version (verified by absence in `details_panel.dart` and arb strings, 2026-07-29).

### 4. Rename/move semantics and pending states

- Rename and move are **metadata-only on-chain transactions**: "A new transaction will be submitted to the Arweave network, using this new name with the file's existing data… All data stored in ArDrive is immutable… but ArDrive lets you do things like rename and move your files and folders after they have been uploaded" (help: *Rename a File or Folder*, 2023-06-14). Filename validation bans `/ \ *`.
- Bulk move exists: Ctrl/Cmd-click multi-select then "Move Items" (v1.33, 2022-10-04; arb strings). That modifier-click is essentially the app's **only keyboard affordance** (see §7).
- **Unconfirmed-transaction display is the app's oldest sore spot.** The scheme is a colored status dot per item: **green** = mined + 15 confirmations; **orange** = "in mempool or mined without enough confirmations" (up to ~30 min); **red** = failed — *or*, notoriously, "the app thinks that file failed, when really it's still unpacking at the gateway (this will be reworked for clarity by the ArDrive team in the near future)" (help: *File Upload Issues and Workarounds*, updated 2025-07-08). That is ArDrive's own documentation admitting the UI shows **false failures**. A 2021 user request for a fourth state (mined-but-unconfirmed) was declined; the same thread surfaced a bug where metadata-succeeded/data-failed uploads "show as yellow indefinitely" (issue #207).
- Pending items are functionally restricted: "The file you are trying to share is currently pending and can't be shared at this time"; creating a manifest over pending files triggers a warning (app_en.arb).
- The documented recovery path for a red dot is startlingly manual: check `arweave.net/<txid>` yourself 5–15 minutes after upload, or look your wallet up on the Viewblock block explorer; and "Using an Incognito Tab or logging out of ArDrive will clear your local cache… If you log out and back in, the files marked red will disappear" (help: *File Upload Issues and Workarounds*). Logout-as-cache-flush is a real workflow in this product.
- Only in v2.85 (2026-07-03) did tx-status queries get fixed to scope per drive owner and to stop misreporting ("Drop unscopable txs from confirmations instead of returning -1") — pending-state accuracy was still being repaired *this month*.

### 5. Sync architecture leaking into UX (the big one)

ArDrive maintains a client-side database (Drift/SQLite) of all drive metadata and syncs it from Arweave GraphQL gateways. The consequences are everywhere in the UI copy (all strings from app_en.arb, accessed 2026-07-29):

- "**Drive Not Synced** — This drive needs to be synced before you can view its contents."
- "Your drive is doing it's [sic] initial setup. This may take a few minutes. Please wait before taking any action."
- "Sync was interrupted. Your drives may not show the latest files and folders." / "{failed} of {total} drives failed to sync… Uploading files now may cause conflicts."
- A "**Deep Resync**" escape hatch: "Empty cache & resync all drives."
- **Snapshots as a paid sync accelerator**: "Snapshots help speed up the time it takes to sync your large drives. Would you like to try?" and "Your drive has grown since the last snapshot. Creating a new one will help keep sync times fast." Users pay an upload fee to write a rollup of their own drive's metadata so future syncs are tolerable.

How bad was it? The v2.85.0 release notes (2026-07-03) state that an **incremental sync with no changes took "130 GraphQL calls / 376 seconds"** before the overhaul (now 3 calls, <1s), and that a bug "was causing all drives to resync every time." v2.83 (2026-06-24) removed the "sync gate on drive open" so new drives allow immediate upload; v2.84 fixed "empty explorer state after drive attach." In other words: for years, opening the app after time away could mean minutes of spinner before your own files appeared, and the fixes landed in June–July 2026. Login+sync resiliency work is still open (PR #2162, 2026-07-05).

### 6. Search

- Search shipped **May 2024** (v2.43/2.44) — the app was four years old before you could find a file by name.
- Implementation (verified in `lib/search/domain/repository/search_repository.dart` + `drive_dao.dart`, dev, 2026-07-29): a modal that queries the **local synced database** for drive, folder, and file **names** (LIKE match, 50-result cap), across all synced drives in parallel, plus ArNS name resolution. **Name-only — no content search, no tag/metadata search, no search within old versions.** And because it queries the local DB, search only sees what has synced (see §5).

### 7. Previews, sorting, keyboard, bulk ops

- **Previews**: details panel has Preview / Details / Activity tabs (plus a Snapshots tab on drives). In-app preview supports images (thumbnails in the explorer since v2.48, 2024-06-26 — generated client-side at upload, opt-in toggle, so pre-2024 files have none), full-screen image viewing with next/prev navigation (v2.26, 2023-12), video and audio players (redesigned v2.24, 2023-11), text files capped at 25 MB (`documentPreviewMaxFileSize`, constants.dart), and even `.eml` (v2.75, 2025-10-31). Public files additionally get the "Public Preview" action, which just opens the raw `arweave.net` gateway URL in a new tab — sandboxed subdomain, shareable, embeddable; unsupported types auto-download (help: *Public Preview*, 2023-06-14). Private-file preview is in-app only.
- **Sorting/filtering**: sortable table columns (Name, File size, Last updated). No filter-by-type, no saved views found in strings or code paths.
- **Keyboard shortcuts: essentially none.** The `keyboard_handler.dart` component exists solely to track Ctrl/Cmd being held for multi-select; the only bound shortcuts are hidden dev-tools combos (Ctrl+Shift+Q). No rename-on-F2, no delete key (naturally), no navigation keys, no shortcut cheatsheet.
- **Bulk operations**: Ctrl/Cmd multi-select → bulk **move** ("Move Items") and bulk **download** ("Downloading file(s)… {n} of {total}", with skipped-files reporting; multi-download since v2.9, 2023-09). Bulk download of folders/drives exists but a code TODO ("extend to work drives and folders" in `download/limits.dart`) shows size-limit checks don't yet cover them. No bulk hide, no bulk rename.
- **Download limits are the hidden scandal** (`lib/download/limits.dart`, dev, 2026-07-29): web downloads are capped at **500 MiB on Chrome**, 2 GiB on Firefox, 1 GiB Safari (public). So the app will happily ingest a 65 GiB file it can never give back through its own UI — the user must fetch the gateway URL manually. Error copy: "The file(s) you have selected is too large to download."

### 8. Delete/trash/hide semantics and permanence honesty

- **There is no delete and no trash.** The product owns this loudly: in-app onboarding copy includes "Remember: There is no delete button (for you or us)!" and "Once uploaded, your data can't be removed" (app_en.arb); the upload flow for public drives warns "Files uploaded here will be permanently viewable by anyone on the internet. Make sure you intend on making this data public." The tone even gets playful: "Think twice before uploading all your teenage love poetry…". Marketing frames the same fact positively ("Store your data securely for at least 200 years, without the fear of deletion").
- **Hide is the delete substitute** (shipped ~2023, help article *Hiding Files from your Drive*, updated 2024-02-02): three-dots menu → Hide on any file/folder (and now drives too, per `hide_bloc.dart` supporting DriveEntity hide — the 2024 help article's "Drives cannot be hidden" is stale). A drive-level "Reveal hidden items / Conceal hidden items" toggle shows ghosted hidden entries.
- **Hiding is itself an on-chain transaction**: `hide_bloc.dart` runs the full upload-payment pipeline (free via Turbo when under the allowance) and writes a `hide`/`unhide` revision. Two honest consequences the help docs do *not* spell out: (a) hiding can in principle cost money, (b) on a public drive, a "hidden" file's data remains publicly fetchable by txid forever, and the hide event itself is publicly visible in the file's Activity history. Hidden ≠ private, and the UI does not say so.

### 9. Offline behavior, platforms, and support surface

- **No offline mode.** The web app is a Flutter SPA with a local metadata cache, but the cache is treated as disposable (logout clears it; docs recommend clearing it to fix stuck states). There's no documented offline browsing, no offline queueing of uploads. The app is installable as a PWA — that's the company's official mobile answer since it **sunset the mobile app in October 2025** ("We've made the decision to sunset the ArDrive Mobile app… we're focusing our energy on improving the web experience," @ardriveapp on X, 2025-10-10; pulled from Google Play 2025-10-08, support ended 2025-10-30, final APK archived on the permaweb). Web-only is now the strategy.
- **The help center is gone.** v2.75 (2025-10-31) release notes: "Remove Zendesk links and references." As of 2026-07-29, `help.ardrive.io` does not resolve at all, while its articles still rank in search engines; `docs.ardrive.io` redirects to AR.IO's ArFS developer docs; `ardrive.io/help` points at an app route with no readable content. **The product's entire end-user documentation corpus is effectively offline** (retrieved for this report via Wayback). For a product whose pitch is permanence, letting its own help center rot is an irony worth naming.
- **Community support on GitHub is near-zero**: the two most recent user questions (#2098 max file size, 2025-11; #2115 "What is the difference between app.ardrive.io and ardrive.net?", 2026-04) have zero replies. Development itself is vigorous (weekly-ish releases, internal PE-#### Jira tickets), but it's heads-down, not community-facing.
- Corporate context: built by Permanent Data Solutions Inc. (founded 2020, Phil Mataras; $17M raise March 2022); the team rebranded to **AR.IO**, with ArDrive as flagship dApp of the AR.IO gateway network (X handle is now "ArDrive.ar.io"). Turbo (the bundler/payment service) is also theirs, and the web app increasingly integrates AR.IO stack features (ArNS names in search, gateway switching in settings, Ethereum + Solana wallet login as of v2.82, 2026-06).

## Strengths (genuinely better than typical web3)

1. **Permanence honesty is best-in-class.** "There is no delete button (for you or us)!" is exactly the right register — repeated at drive creation, upload, and onboarding, with the public/private distinction made at a moment (drive creation) users can understand. Most web3 storage apps bury irreversibility; ArDrive leads with it.
2. **Pre-upload cost transparency.** Every mutation shows its price before you commit, cancel is free, and small transactions are labeled "free thanks to Turbo." Fiat card top-ups (Stripe) mean a normie never touches AR tokens. This is a real onboarding achievement.
3. **Automatic versioning with a stable file identity.** Same-name upload → version prompt → full history in the Activity tab, with per-revision download. The File-Id model means renames/moves/versions don't break links or identity. Solid design that consumer clouds took years to get.
4. **Mutable UX over immutable storage.** Rename, move, and hide as cheap metadata revisions demonstrate that "immutable data, mutable index" can feel like a normal file manager — the single most transferable proof-of-concept for EFS.
5. **The Activity tab doubles as an audit log** — every revision event (created, renamed, moved, hidden, new version) with timestamps, straight from chain data. Free provenance UI.
6. **They ship.** Weekly releases, honest release notes that quantify their own past failures (376s → <1s sync), and a willingness to cut losses (mobile sunset) rather than let quality diffuse.

## Weaknesses / user pain

1. **The chain leaks everywhere.** Status dots that lie (documented false "failed" reds during unbundling), pending files that can't be shared, 30-minute confirmation windows, "don't close the tab" uploads, and a recovery path that involves a block explorer. The app makes the user absorb Arweave's operational states instead of absorbing them itself.
2. **Sync-the-world architecture punished users for years.** "Drive Not Synced" gates, multi-minute no-op syncs (376s), forced resyncs, "Deep Resync" as a user-facing button, and warnings that uploading before sync completes "may cause conflicts." Worst of all, **Snapshots monetize the workaround**: users pay to make their own drives listable in reasonable time. The 2026 overhaul fixed the numbers but the architecture still requires full-drive metadata sync before browse/search.
3. **Upload/download asymmetry**: 65 GiB in, 500 MiB out (Chrome). Undocumented anywhere user-facing; the answer to "what's the max file size" exists only in source code, and the GitHub question asking it has been ignored since November 2025.
4. **Shallow file-browser ergonomics**: no keyboard shortcuts, no filter, no grid view, no folder drag-and-drop, no folder merge on conflict, no bulk rename/hide, name-only search that arrived four years into the product's life and only covers synced local data. It resembles Google Drive circa 2008.
5. **No version restore.** History is visible but read-only; recovering an old version is a manual re-upload.
6. **Hide's privacy theater is unexplained.** Hidden files on public drives remain publicly fetchable forever and the hide event is itself public, but the UI never says this. This is the one place ArDrive's otherwise excellent permanence honesty fails.
7. **Support surface collapsed.** Dead help center (still ranking in search), unanswered GitHub questions, docs migrated into a developer-oriented AR.IO site. Self-serve users troubleshooting a red status dot in 2026 land on a domain that doesn't resolve.

## Implications for the EFS file browser

1. **Own the pending lifecycle; never show false failures.** Item states (local → submitted → confirmed-on-Ethereum → mirror-propagated per carrier) must be first-class UI with per-state affordances (what you can/can't do while pending), optimistic rendering, and automatic reconciliation. ArDrive's decade of status-dot pain is the cautionary tale: a wrong "failed" is worse than a slow "pending." EFS has an advantage — Ethereum finality is faster and cleaner than Arweave mining + gateway unbundling — so lean into it.
2. **Do not require a full metadata sync before browsing.** ArDrive's local-DB-sync design generated years of "Drive Not Synced" gates and a paid workaround (Snapshots). The EFS Files app should page/stream directory listings from indexed on-chain state (SDK/lens resolution) on demand. If a local cache exists, it must be an accelerator, never a gate — and never something users manage ("Deep Resync" buttons are an admission of defeat).
3. **Copy ArDrive's permanence honesty, then finish the job.** Blunt, repeated, moment-of-risk messaging ("no delete button, for you or us") demonstrably works and fits EFS's on-chain reality. But EFS must be more precise than ArDrive in two places ArDrive fumbles: hidden ≠ private (say it in the hide dialog), and per-mirror permanence differences (an ar:// mirror is forever; other mirrors may be re-writable or losable — surface this per file, since EFS treats Arweave as one carrier among several).
4. **Stable file identity + revision model, plus the restore button ArDrive never shipped.** Same-name-upload → new version, an Activity/history tab with per-revision preview/download, and metadata-only rename/move are all validated patterns. One-click "restore as current version" (a new metadata revision pointing at old bytes — near-free) is a cheap, visible way to beat ArDrive.
5. **Table-stakes file-manager ergonomics are an open flank.** Keyboard shortcuts, filters, folder drag-and-drop, conflict merge, bulk rename, instant name search that doesn't depend on sync state — none exist in ArDrive. A web-OS file browser that just feels like Finder/Explorer would out-UX the incumbent product in this niche without touching the hard problems.
6. **Be honest about browser I/O ceilings early.** ArDrive accepts 65 GiB uploads it can't download back through Chrome (500 MiB cap) and documents none of it. EFS Files should publish its size limits in-product (upload modal and error states), engineer streaming downloads (service worker / File System Access API) before allowing large ingests, and never let the answer to "what's the max file size" live only in source code.
