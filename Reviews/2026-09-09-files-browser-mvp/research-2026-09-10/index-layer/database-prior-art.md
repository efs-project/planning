# Prior art: indexes declared after the fact, built in the background, relied upon while incomplete

Scope: primary documentation/papers fetched 2026-09-10 unless a publication date is given. Vault claims cite `file:line`. Gas figures carry MEASURED / QUOTED / ESTIMATED per the vault convention.

## 0. The one-paragraph answer

Every production system surveyed separates the index physically from base data but couples it through the write path from the moment the index is *declared*, then backfills history in the background, and exposes an explicit build state that readers consult. None lets a reader silently see a partial index as if it were whole: the planner ignores it (PostgreSQL, MySQL, MongoDB, F1/CockroachDB), the query errors (DynamoDB `CREATING`, Cassandra `IndexBuildInProgressException`), or the staleness is labelled and the reader opts in (Oracle `stale_tolerated`, Materialize timestamps, Kurrent `caughtUp`). The systems that made indexing a separate optional layer maintained by someone else (EAS `Indexer.sol`, MUD modules post-install, Elasticsearch reindex) all lost the ability to prove absence. So: a separate layer is standard; relying on it is standard *only* when the layer carries a coverage contract. The owner's v1 sort design (anyone pays to advance a shared list, with a `staleness` counter) is structurally the same as a CQRS projection with a checkpoint, and the DB world's verdict on that shape is "fine for inert readers, never for effectful ones unless they check the checkpoint."

## 1. System by system

For each: (a) how declared post hoc, (b) how populated without blocking writes, (c) what readers see mid-build, (d) completeness signal, (e) turn-off, (f) what goes wrong.

### 1.1 PostgreSQL `CREATE INDEX CONCURRENTLY` / `REINDEX CONCURRENTLY`

- (a) `CREATE INDEX CONCURRENTLY` at any time; cannot run inside a transaction block. (b) Three transactions: the index is "entered as an 'invalid' index into the system catalogs in one transaction, then two table scans occur in two more transactions. Before each table scan, the index build must wait for existing transactions that have modified the table to terminate. After the second scan, the index build must wait for any transactions that have a snapshot predating the second scan to terminate ... Then finally the index can be marked 'valid'." The catalog is a three-flag state machine in `pg_index`: `indislive` (false = being dropped, ignore for all purposes), `indisready` (true = "ready for inserts"; false = "must be ignored by INSERT/UPDATE"), `indisvalid` (true = "valid for queries"; false = "possibly incomplete: it must still be modified by INSERT/UPDATE operations, but it cannot safely be used for queries"). That is F1's delete-only / write-only / public in a single-node system, written in 2007. (c) Invalid index "will be ignored for querying purposes because it might be incomplete; however it will still consume update overhead." Unique constraints are "already being enforced against other transactions when the second table scan begins", so writers can be rejected by an index no reader can use yet. (d) `indisvalid=true`; `\d` shows `INVALID` otherwise. (e) `DROP INDEX`; `REINDEX CONCURRENTLY` builds `_ccnew`, swaps names, marks old invalid, drops it. (f) "If a problem arises while scanning the table, such as a deadlock or a uniqueness violation in a unique index, the CREATE INDEX command will fail but leave behind an 'invalid' index"; recovery is drop-and-retry. Worse: PostgreSQL 14.0–14.3 shipped an optimization that "caused CREATE INDEX ... CONCURRENTLY and REINDEX ... CONCURRENTLY to sometimes miss indexing rows that were updated during the index build" (14.4 release notes, 2022-06-16) — a *trusted* builder with a formally reasoned two-scan protocol still produced silently incomplete indexes that were marked valid.

### 1.2 MySQL / InnoDB online DDL, and gh-ost

- (a) `CREATE INDEX` / `ALTER TABLE ... ADD INDEX`, `ALGORITHM=INPLACE, LOCK=NONE`. (b) "The table remains available for read and write operations while the index is being created"; concurrent DML is recorded in a temporary "online log" and "the thread that runs the ALTER TABLE statement applies an online log of DML operations that were run concurrently"; exclusive metadata lock only briefly at start and end. (c) New index is not visible until commit; "A newly created secondary index contains only the committed data in the table at the time the CREATE INDEX or ALTER TABLE statement finishes executing." (d) Statement completion. (e) `DROP INDEX` is in-place, metadata-only, concurrent DML permitted. (f) Documented failure conditions: the online log exceeds `innodb_online_alter_log_max_size` (`DB_ONLINE_LOG_TOO_BIG`, ERROR 1799 "Please try again"); "Concurrent DML makes changes to the table that are allowed with the original table definition, but not with the new one ... The changes made by the concurrent DML take precedence, and the ALTER TABLE operation is effectively rolled back"; even a *temporary* duplicate later reverted in the log raises ERROR 1062; long transactions holding metadata locks time the DDL out; replicas replay the DDL serially, so "Long running online DDL operations can cause replication lag." gh-ost (GitHub) is the external variant: copy rows in chunks into a "ghost table" while tailing the binlog, then an atomic rename cut-over; on cut-over failure "we are naturally returning to pre-cut-over phase, where the original table is still in place and accessible." The ghost table is invisible to the application until cut-over.

### 1.3 MongoDB (same family, included because "build in the background" is its native vocabulary)

4.2+: "Index builds now obtain an exclusive lock on the collection being indexed only at the start and end of the build"; concurrent writes go to a "side writes table" drained after the collection scan; "The index is not available for queries until the build completes." 4.4+: resumable after clean shutdown from a checkpoint — but "only once"; a crash restarts from zero; replica sets need a commit quorum before the primary writes `commitIndexBuild`, and constraint violations produce `abortIndexBuild`. Abort = `dropIndex`, not `killOp`. `background: true` is now ignored.

### 1.4 F1 (Google, 2013) → CockroachDB (2015 RFC → 2021 RFC → 2023 blog) → Spanner

- **F1** (Rae et al., PVLDB 6(11), 2013): "delete-only table, column or index cannot have its key value-pairs read by user transactions. Tables can only be modified by delete operations, and indices by delete and update operations." "write-only column or index can have its key-value pairs modified by insert, delete, and update operations, but none of its pairs can be read by user transactions." Add index: absent → delete-only → write-only → database reorganization (backfill, MapReduce) → public. Drop: reverse. Invariant: "At any moment F1 servers use at most two schemas", enforced by leases; "The schema change execution process must wait at least one schema lease period before applying a new intermediate schema." The two anomalies prevented: orphan data (index entries with no row) and integrity anomaly (rows with no index entry). "A typical schema change involving no reorganization takes 10 to 20 minutes."
- **CockroachDB 2015 RFC**: `DELETE_ONLY` → `WRITE_ONLY` → `PUBLIC`; "It is invalid to jump from the DELETE_ONLY to PUBLIC state or vice versa"; backfill "when the index is in the WRITE_ONLY state and completed before moving the index to the PUBLIC state"; in the intermediate states "the column or index is not used for read operations." **2021 RFC (incremental index backfiller)** and **2023-01-19 blog**: the WRITE_ONLY-during-backfill design "violate[d] MVCC semantics" because bulk writes had to be backdated; fix = a new `BACKFILLING` state in which "foreground SQL ignores it entirely", a *temporary index* in `DELETE_AND_WRITE_ONLY` capturing concurrent writes, bulk backfill at a fixed timestamp, then a merge "in transactional batches, to avoid the potential of overwriting a newer value", with deletes preserved via a `TempIndexKV{deleted}` encoding rather than KV tombstones. **2023-11-08 blog**: "A new capability is granted only once the entire cluster is using a schema that contains all prior granted capabilities"; "valid leases are only on the two latest schema versions"; readers cannot use the index until `PUBLIC`; "you can cancel the schema change operations before they finish and the database remains completely unaltered." User docs: schema changes are background jobs (`SHOW JOBS`, pause/resume/cancel); "CockroachDB does not support schema changes within explicit transactions with full atomicity guarantees"; multi-statement DDL can leave the database "partially committed, partially aborted"; "Schema changes consume additional resources ... latency spikes can occur."
- **Spanner**: "Spanner automatically backfills ... the process runs in the background using node resources at low priority"; "Index creation can take from several minutes to many hours"; reads and writes continue; cancellation: "only indexes that are yet to be created are canceled. The indexes already created are not dropped by the cancellation." Public docs expose no state names (the F1 machinery is internal) and no explicit "index not ready" error text could be found.

### 1.5 DynamoDB Global Secondary Indexes

- (a) `UpdateTable` with `GlobalSecondaryIndexUpdates`, "only one global secondary index per UpdateTable operation"; up to 20 per table. (b) Two phases: Resource Allocation (`IndexStatus=CREATING`, `Backfilling=false`) then Backfilling (`CREATING`, `Backfilling=true`): "For each item in the table, DynamoDB determines which set of attributes to write to the index ... During the backfill phase, DynamoDB tracks the items that are being added, deleted, or updated in the table" — i.e. write-only from declaration plus backfill of history. "You are not charged for read operations from the base table to populate the global secondary index." (c) "You can't Query or Scan the index until it is ACTIVE." (d) `IndexStatus=ACTIVE`; `OnlineIndexPercentageProgress` metric. (e) `Delete` action → `DELETING`; "no effect on any read or write activity in the parent table." (f) Three documented failure shapes. Key violations: "Index key violations do not interfere with global secondary index creation. However, when the index becomes ACTIVE, the violating keys are not present in the index" — an ACTIVE index can be silently incomplete; AWS ships a separate Violation Detector tool. During backfill, "some writes of violating items might succeed while others are rejected." Backpressure inversion: "If you perform heavy write activity on the table, but a global secondary index on that table has insufficient write capacity, the write activity on the table will be throttled" — index maintenance can fail base writes. Steady state is eventually consistent with no bound: "Changes to the table data are propagated to the global secondary indexes within a fraction of a second, under normal conditions. However, in some unlikely failure scenarios, longer propagation delays might occur. Because of this, your applications need to anticipate and handle situations where a query on a global secondary index returns results that are not up to date." Also sparse by construction: an item lacking the index key attribute "is not propagated to the index", so the index answers "has attribute X = V", never "does not have X."

### 1.6 Cassandra 2i / SASI / SAI

- (a) `CREATE INDEX` any time; "If data already exists for the column, it will be indexed asynchronously. After the index is created, new data for the column is indexed automatically at insertion time." (b) Per-node local build from SSTables; new writes indexed via memtable. (c) Query during build fails: `IndexNotAvailableException: The secondary index '...' is not yet available` (CASSANDRA-15162, 2019-06-14, closed *Invalid* = expected behaviour). Cassandra 5.1 (CASSANDRA-20402, committed 2024-12-05) splits this: "Throw new IndexBuildInProgressException when queries fail during index build, instead of IndexNotAvailableException", raised when `Index.Status.FULL_REBUILD_STARTED` is seen, so clients can tell "temporarily building" from "broken." (d) `system_views.indexes` with `is_queryable` and `is_building` (SAI FAQ); "each node propagates its own local index status to peers via gossip" so coordinators avoid replicas with failed indexes. (e) `DROP INDEX`; `nodetool rebuild_index` = "A full rebuild of native secondary indexes for a given table." (f) A node restarted mid-build has a half-built index that must be rebuilt by hand; the index status is per node, so the same query can succeed on one coordinator and fail on another. SASI: apache.org docs describe it as SSTable/compaction-time indexing; the "deprecated in 5.0, removal in 6.0" claim surfaced only in a search-result summary of third-party pages and could not be verified against apache.org — treat as unconfirmed. SAI (5.0, blog 2023-11-14) is the replacement and builds on existing SSTables.

### 1.7 Elasticsearch reindex + alias swap

- (a) Create a new index (mappings are not copied: "Mappings, shard counts, and replicas, for example, must be configured ahead of time"), `_reindex` into it. (b) Reads via scroll: "The results that are returned from a scroll request reflect the state of the data stream or index at the time that the initial search request was made, like a snapshot in time. Subsequent changes to documents ... will only affect later search requests"; sliced reindex: "Each sub-request gets a slightly different snapshot of the source." So writes after the start are *not* captured — the application must dual-write or re-run with `version_type: external` ("preserve the version from the source, create any documents that are missing, and update any documents that have an older version in the destination"). (c) Readers keep hitting the old index via the alias; the new index is invisible until the swap. (d) Task API counts; then an atomic alias action: "the logs alias has no downtime and never points to both streams at the same time." (e) Point the alias back; delete the index. (f) "When a reindex fails, completes with failures in the response, or returns 404 and cannot be tracked further, partial data might have been written to the destination index"; retries need `conflicts=proceed` "as the destination index could be left in a partial state." Aliases give atomic *cut-over*, not completeness; completeness is the operator's problem.

### 1.8 Materialized views and incremental view maintenance

- **PostgreSQL `REFRESH MATERIALIZED VIEW CONCURRENTLY`**: requires "at least one UNIQUE index on the materialized view which uses only column names and includes all rows"; "can only be used when the materialized view is already populated"; `WITH NO DATA` leaves it "in an unscannable state" (queries error rather than return empty — the correct rendering of UNKNOWN). Implementation (`matview.c`, `refresh_by_match_merge`): new data into a temp table, "a full outer join against the old version of the data, producing 'diff' results", then "set-based DELETE and INSERT operations against the materialized view", all "under cover of an ExclusiveLock" (not AccessExclusive, so SELECTs proceed). Fails if "new data for materialized view contains duplicate rows without any null columns." Staleness is not tracked; the user schedules refreshes.
- **pg_ivm (IMMV)**: "views are updated in the same transaction that its base table is modified" via AFTER triggers; "ExclusiveLock is held on an IMMV immediately after a base table is modified" so "Incremental updates of a view are basically performed sequentially even with concurrent transactions"; `refresh_immv(..., with_data=false)` disables maintenance for bulk loads. Restricted SQL subset (no window functions, HAVING, ORDER BY, LIMIT, set operations, DISTINCT ON, user-defined aggregates).
- **Oracle**: `ALL_MVIEWS.STALENESS` ∈ {`FRESH`, `STALE` ("If the materialized view was FRESH before it became STALE, then it is a read-consistent view of a former state of its masters"), `UNUSABLE` ("not a read-consistent view of its masters from any point in time"), `UNKNOWN`, `NEEDS_COMPILE`, `UNDEFINED`, `IMPORT`}; refresh method `COMPLETE`/`FAST`/`FORCE`/`NEVER`. The optimizer's use of stale views is a session/system knob: `QUERY_REWRITE_INTEGRITY = enforced | trusted | stale_tolerated`, the last meaning "Materialized views are eligible for rewrite even if they are known to be inconsistent with the underlying detail data." This is the cleanest prior art for *declared* tolerance of unsynced indexes: the reader, not the index, opts in.
- **Materialize**: every read "served at a timestamp" with "results are exactly correct as of that timestamp" (never a partially applied update); isolation `strict serializable` / `serializable` / `bounded staleness <duration>` (errors if the bound cannot be met). Completeness of a new index/view is explicit: `mz_hydration_statuses.hydrated` ("Whether the object is hydrated on the replica"), `mz_compute_operator_hydration_statuses` (per operator "completed its initial snapshot processing"), `mz_materialization_lag` (`local_lag`, `global_lag`, `slowest_*_input_id`), `mz_frontiers` (`read_frontier` "earliest timestamp at which the output is still readable", `write_frontier` "next timestamp at which the output may change").
- **DBToaster** (Koch et al., PVLDB 5(10) 2012; VLDBJ 2014): "recursive finite differencing technique which materializes a query and a set of its higher-order deltas as views. These views support each other's incremental maintenance ... tens of thousands of complete view refreshes per second." Freshness by construction (every update applied); no notion of a background build — the view is defined before data flows.
- **Noria** (Gjengset et al., OSDI 2018): adding a query to a live dataflow plans transitions "reusing operators and state of existing expressions where possible. It then incrementally applies these changes to the data-flow"; partial state: "Partial-state operators start out empty and are gradually and lazily populated by upqueries" (a read miss triggers a recursive fill from ancestors; eviction under memory pressure); where an upquery would need a full scan "Noria disables partial state for that operator." Consistency is eventual: "if writes quiesce, all external views eventually hold results that are the same as if the queries had been executed directly against the base table data." Noria is the read-time analog of the beacon-deposit pattern in the vault (`gas-engineering-2026-09-10.md:222-248`): don't maintain what readers can recompute; let the first reader pay.

### 1.9 Event sourcing / CQRS read-model rebuilds

- **Marten async daemon**: projections consume the event sequence in order and track a "high water mark", "the highest event sequence guaranteed to be safely processed in order"; gaps from rolled-back appends are waited on then skipped and recorded in `mt_high_water_skips`; delivery is at-least-once, so "Projections must handle idempotent updates"; `WaitForNonStaleProjectionDataAsync()` = "Wait until the async daemon has completely caught up with the currently known high water mark." Rebuild = truncate and replay ("insert-only" after teardown); zero-downtime rebuild = bump `ProjectionVersion` so the new version writes to *separate tables* and catches up while the old version serves, then switch (`GateSideEffectsBehindPriorVersion` stops replay from re-firing side effects).
- **Axon Framework**: position = `TrackingToken` in a `TokenStore`; "we recommend using a token store that stores tokens in the same database as to where the event handlers update the view models" (atomic checkpoint + projection); replay = shut down, `resetTokens()`, `@ResetHandler` clears the model, handlers can ask `ReplayStatus.isReplay()` to suppress side effects; "Event handlers must be idempotent."
- **Kurrent (EventStoreDB) catch-up subscriptions**: `fromStart()` / `fromEnd()` / `fromRevision(n)` / `fromPosition(prepare, commit)`; "The positions provided to the subscriptions are exclusive"; the client "store[s] the current position of the subscription somewhere, and then use it to restore the subscription"; `onCaughtUp()` fires "when transitioning from catching up to live mode." The checkpoint is the reader's own responsibility.
- **DBLog (Netflix, arXiv 2010.12597, 2020-10-23) / Debezium incremental snapshots (blog 2021-10-07)**: the chunked-backfill-under-live-writes algorithm. Motivation: "The near-impossibility of adding of additional tables to the captured tables list, if existing data must be streamed"; snapshots could not be paused/resumed and blocked streaming. Method: chunks by primary key; write a low-watermark signal, select the chunk into a buffer, write a high-watermark signal; while tailing the log, "any transaction log changes for keys already buffered cause those snapshot entries to be discarded, ensuring streamed changes take precedence"; remaining rows are emitted as read events. Triggered ad hoc on a running connector via a signal table; progress (table list, max key, last-sent key) is stored in offsets so it resumes after crashes. This is the closest published analog to "anyone triggers a chunk of backfill later, while writes continue, and the result is still consistent."

### 1.11 On-chain analogs already in the vault, plus one

- v1 `efs.sorts`: "Sorts are lazily populated: items are inserted one batch at a time by any caller, who pays the gas" (`contracts/specs/07-Sort-Overlay-Architecture.md:5`); "Anyone can advance the shared sorted list" (`:11`); frontier = `_lastProcessedIndex` (`:26`), advance must be contiguous or revert `StaleStartIndex` (`:99`); staleness = `kernelCount - lastProcessedIndex` (`:169-179`); "Fabricated UIDs rejected — processItems validates each item against the kernel via getChildAt" (`:289`); SDK mirror in `Designs/sdk-architecture.md:583-641`. That is a CQRS projection with an on-chain checkpoint and on-chain validation of each projected entry — the builder supplies gas and hints, never facts.
- EAS `Indexer.sol`: opt-in, permissionless, never prunes, ignores revocation; "A reader can prove existence from it but never absence" (`Reviews/2026-09-09-files-browser-mvp/research-2026-09-10/indexing.md:60`, `:23`, `:88`). MUD `KeysInTable`/`KeysWithValue`: "only records written after installation" (`research-2026-09-10/mud.md:90`), +110–128k per write MEASURED, replaced by hand-maintained tables in production (`indexing-and-state-2026-09-10.md:278-282`).
- EFS v1 ADR-0008's write-time qualifying-folder index had "Sticky semantics: a folder that once contained matching content stays in the qualifying index even if all content is removed" (`contracts/docs/adr/0008-...md:57`) and was removed; ADR-0066 separates "discovery" from "placement" so permissionless `index()` cannot forge presence (`0066-...md:28-42`). Both are the EAS-Indexer failure in EFS's own history.
- New: Uniswap v3 `Oracle.sol` — "Anyone can pay the SSTOREs to increase the maximum length of the oracle array"; `grow()` writes a placeholder in each slot "to prevent fresh SSTOREs in swaps" and the pool grows into `observationCardinalityNext` lazily on the next write; `observe()` reverts `'OLD'` for times before the oldest stored observation. This is a permissionless, content-free, gas-only contribution to an index-shaped structure: the builder cannot lie because the builder writes nothing semantic, and readers get a hard revert, not empty, outside coverage.

## 2. What every system does the same way

1. **Write-path coupling from declaration.** Postgres `indisready`, F1 write-only, Cockroach `DELETE_AND_WRITE_ONLY` (via a temp index), DynamoDB "tracks the items that are being added, deleted, or updated" during backfill, Cassandra "new data ... indexed automatically at insertion time", MongoDB side-writes table, InnoDB online log. The backfill only ever has to cover history up to the declaration point; everything after is caught live. The two exceptions — Elasticsearch reindex and EAS Indexer — are exactly the two that cannot guarantee completeness.
2. **A three-state life cycle, always.** absent → maintained-but-unreadable → readable (and the reverse to drop). No system lets the readable state precede full coverage without labelling it (Oracle `STALE`, Materialize lag).
3. **Completeness is a scalar readers can compare.** `indisvalid`, `IndexStatus`, `is_queryable`, `hydrated`/`write_frontier`, the projection high-water mark, `lastProcessedIndex`. The reader's job is to compare it with the base's position (Marten "caught up with the currently known high water mark"; v1 `kernelCount - lastProcessedIndex`).
4. **UNKNOWN is rendered as an error or as "use the base", never as empty.** Postgres planner skips invalid indexes; DynamoDB refuses Query on `CREATING`; Cassandra throws; Materialize refuses to serve an unhydrated object; Postgres `WITH NO DATA` views are "unscannable." This is the same rule the vault names as the dominant EFS bug class (`indexing-and-state-2026-09-10.md` §0-§3 framing; `tag-system-2026-09-10.md:257-276`).
5. **Failure = drop and retry, with leftovers.** Postgres invalid index "still consume[s] update overhead"; Elasticsearch "partial data might have been written"; Spanner cancellation keeps already-created indexes; MongoDB resumes from checkpoint once, then restarts. Nobody repairs in place.
6. **Backfill is chunked, resumable and reconciled against live writes** by snapshot timestamp (Cockroach), side log (InnoDB, MongoDB), or watermarks (DBLog/Debezium). Chunking exists because the builder can crash and the base keeps moving.
7. **Turn-off is cheap in the metadata and expensive in the data.** DynamoDB `DELETING` "no effect on any read or write activity"; F1 public → write-only → delete-only → absent so no server ever reads a half-dropped index.
8. **Even trusted builders get this wrong.** PostgreSQL 14.0–14.3 marked incomplete indexes valid; DynamoDB `ACTIVE` indexes silently omit key-violating items; InnoDB rolls the whole ALTER back on a transient duplicate.

## 3. Transferable principles (with the EFS mapping)

1. **Declare late, maintain from the declaration ordinal, backfill only the past.** A family declared at global admission ordinal `N_decl` is hooked into the write path from that admission on (F1 write-only). The ledger *is* the delta log: no side-writes table, no online-log overflow, no watermark reconciliation, because admissions are totally ordered and immutable. Backfill covers `[0, N_decl)` only. This is the F1/DynamoDB/Cassandra shape and it is *simpler* on an append-only ledger than in any surveyed system.
2. **Carry an explicit coverage frontier per index, keyed where the ordinal lives.** EFS already has the per-(principal, directory) kind-10 ordinal (`indexing-and-state-2026-09-10.md:94-120`), so the frontier is per scope key: `(declaredAt, backfillFrontier, retiredAt)`. Complete ⇔ `backfillFrontier == declaredAt`. Readers read two slots (≈4,200 gas cold, QUOTED schedule) and know coverage exactly. This is Marten's high-water mark, Materialize's `write_frontier`, v1's `lastProcessedIndex`. Per-scope, not global: the vault already warns to "avoid global head slots" for EIP-7928 parallelism (`indexing-and-state-2026-09-10.md:363-366`).
3. **Advance the frontier only contiguously, and only by on-chain derivation.** v1 `StaleStartIndex` (`07-Sort-Overlay-Architecture.md:99`) and `getChildAt` validation (`:289`) already do this; Liquity hints and Uniswap `grow()` are the same discipline. The untrusted builder contributes gas and hints; the contract derives every entry from kernel state. Trust collapses to *completeness* (did the builder stop early?), which the frontier answers, not *correctness*.
4. **Make index writes idempotent (set semantics).** Bitmaps over ordinals are idempotent: setting a bit twice is one bit, and a rebind after `N_decl` that flips deltas against an un-backfilled position still converges when the backfill later ORs in the pre-`N_decl` state, *provided* the backfill derives from the binding's current record, not the historical one. Append-only id lists are not idempotent (double-append) — the reason DynamoDB/MongoDB/Debezium need reconciliation machinery and the reason ADR-0009 append-only arrays cannot be safely backfilled (`contracts/docs/agent-workflow.md:261,267`). The Tier-1 "never backfill" rule is a consequence of the shape, not a law; a family with a validity frontier and set-semantics writes is backfillable by design.
5. **Render UNKNOWN as revert, not empty; give inert readers an opt-in.** Contract-facing getters take the frontier into account and revert (`'INCOMPLETE'`, like Uniswap `'OLD'`, Cassandra `IndexBuildInProgress`) when the requested range exceeds coverage; a separate `*Tolerated` view returns `(result, coverage)` for clients and off-chain readers — Oracle's `enforced` vs `stale_tolerated`. The consumer-tournament verdict (effectful consumers must pin; `indexing-and-state-2026-09-10.md:224`) says effectful contracts get only the reverting path.
6. **Turn-off = close the coverage interval, never delete.** `retiredAt` ordinal: coverage becomes `[0, retiredAt)`, the write hook stops (removing per-write cost), and readers treat the family as historical. Storage stays (EIP-3529 refunds are capped at gas_used/5, QUOTED in `research-2026-09-10/indexing.md:9`, and Etched index shapes cannot be compacted). This is F1's public→write-only→absent path with the final step omitted. Design the retire flag in from the start: Postgres shows what an un-retirable invalid index costs ("still consume update overhead") — on-chain that cost is paid by every writer forever.
7. **Budget backfill by the transaction cap, and prefer read-bound structures.** EIP-7825 caps execution at 16,777,216. ESTIMATED per backfilled entry for a bitmap family: cold read of the binding head 2,100 + 2–4 record slots 4,200–8,400 + first bit in a word 5,000 (rewrite) or 22,100 (fresh; 110,020 under EIP-8037) + 100 per further bit in the same word in the same tx ⇒ ≈6.5–11k per entry, read-dominated ⇒ ≈1,500–2,500 entries per transaction today, and nearly unchanged under Glamsterdam because a fresh 256-bit word amortises to ≈430 per entry. An id-per-entry backfill is 22,100 → 110,020 per entry ⇒ ≈750 → ≈150 entries per transaction. Backfill economics alone rule out id-lists for post-hoc families.
8. **Bring-your-own-checkpoint for off-chain readers; on-chain checkpoint for contracts.** Kurrent and Axon make the *reader* own the position; the web client with no Graph does the same by pinning `blockTag` and comparing the scope count before/after (`research-2026-09-10/indexing.md:141`). Contracts cannot, so the frontier must live on-chain (principle 2).
9. **Reindex-and-swap becomes "new family + default pointer."** Elasticsearch aliases, gh-ost cut-over and Marten `ProjectionVersion` all build v2 beside v1 and flip a pointer. On EFS a v2 family is a new key namespace (cheap to declare) plus a per-directory `defaultSort`/default-family pointer, which the sort overlay already has (`Designs/sdk-architecture.md:599-600`). The old family is retired (principle 6), not dropped.
10. **Don't maintain what readers can recompute; let the first reader memoise.** Beacon-deposit lazy root (`gas-engineering-2026-09-10.md:222-248`), Noria upqueries, Uniswap observations. Aggregates (`count`, `live`, `last`) belong to read-time or to a permissionless "poke", not to every write.

## 4. What does NOT transfer to an append-only, immutable-record ledger with an untrusted gas-paying builder

- **Delete-only states and the two-version lease.** F1/Cockroach need them because servers adopt schema versions asynchronously and could write index entries the deleter never sees. A single contract's state transitions atomically per block; there is no schema skew, so `DELETE_ONLY` and lease waits have no counterpart. What *does* remain is the mutable-binding delete side: an index keyed on binding position must clear bits on rebind from the declaration ordinal on (`indexing-and-state-2026-09-10.md:180-187`).
- **Snapshot + side-log + merge (InnoDB online log, MongoDB side writes, Cockroach temporary index, DBLog watermarks).** All exist to reconcile a moving base with a backfill that reads at a different time. The ledger's total order removes the problem; importing this machinery would be pure overhead.
- **Trusted-builder assumptions.** Every DB backfill is executed by the DBMS. On EFS the builder may be anyone. The only workable substitute is on-chain derivation of each entry from kernel state (v1 `processItems`), which bounds what a post-hoc family can contain: predicates computable from record fields and bindings in bounded gas. Families that need off-chain input (ranking, full-text, cross-lens folds over open attester sets) cannot be permissionlessly backfilled; they need a proof-carrying path (Brevis-style, `research-2026-09-10/indexing.md:80`) or stay off-chain.
- **Free or low-priority background capacity.** DynamoDB "You are not charged for read operations ... to populate the global secondary index"; Spanner "at low priority." Blockspace has no priority lane and no free reads inside a transaction; backfill competes with users and is capped per transaction (principle 7). Also: two builders racing on the same scope waste the loser's gas on a `StaleStartIndex` revert — v1 accepted this; a chunk-claim or per-word partition would reduce it but adds state.
- **Eventual consistency tolerated by all readers (DynamoDB GSI, Noria, Cassandra 2i).** Acceptable there because application code re-checks the base. An MMORPG contract acting on a stale or partial index is the "silent absence" defect by definition; only inert readers may take the `stale_tolerated` path.
- **Drop-and-retry recovery.** No `DROP INDEX`: a failed or abandoned family's storage persists and, without a retire flag, its write hook keeps charging writers. Every family must be born with `retiredAt`.
- **Uniqueness/constraint enforcement during build** (Postgres unique-while-invalid, InnoDB duplicate rollback, DynamoDB key-violation rejection). Records are content-addressed and immutable; there is no constraint an index could newly impose on base writes, and the mandatory-indexing ruling (`Designs/efsv2/owner-rulings.md:59-60`) forbids an index from refusing an admission. A post-hoc family must therefore be *total* over its declared predicate or explicitly sparse (DynamoDB-style "only items with attribute X"), and its docs must say which.
- **Cross-node status divergence** (Cassandra per-node `is_queryable`, MongoDB commit quorum) — irrelevant; the chain is one replica.

## 5. Direct answers to the owner's four asks

- *Separate layer you can still rely on?* Yes; that is every DB's architecture. Reliance comes from (i) write-path coupling from declaration, (ii) an on-chain coverage frontier, (iii) reverting outside coverage. Without (ii)+(iii) it is EAS Indexer: provable existence, unprovable absence.
- *Add indexes later and populate in the background?* Standard (Postgres CIC 2007, DynamoDB GSI, F1 2013, Cassandra). On EFS it is *easier* than in any of them because the ledger is the log; the cost is the backfill pass the D-D amendment already prices as "a paid pass over every record" (`tag-system-2026-09-10.md:244,272-273`), which principle 7 bounds at ≈1,500–2,500 entries per transaction for bitmap families (ESTIMATED).
- *Turn indexes off?* Not scary if `retiredAt` exists from day one; scary only as storage reclamation, which is off the table anyway.
- *Push-back on the v1 sort-style shared-cost build?* The shape is sound and matches CQRS projections and DBLog exactly. The three things that made it "complex" in v1 — client-computed hints, `StaleStartIndex` races, per-lens filtering of a shared list — come from *sorting*, not from *indexing*: bitmap families need no hints (derivation is deterministic), tolerate duplicate work (idempotent), and are per-principal by construction (`indexing-and-state-2026-09-10.md:114-120`). "Unsynced indexes are untrustworthy" is true only when the reader cannot see the sync point; with the frontier exposed and the getter reverting past it, an unsynced index is exactly as trustworthy as a synced one over the range it claims.
