**State growth per admission is unchanged** (the same slots are written). The candidate keeps the cache bytes byte-identical and immutable but stores them as the runtime code of a small inert contract (one `STOP` byte, then the cache), deployed once at type admission by the pinned `PreparationHelper` from its own account, and loads them with `EXTCODECOPY`. The stored type row keeps its three head slots; the ~70 data slots per type disappear. No identity, authorization, validation, index, binding, history or view changes.

**Why the helper deploys, not the kernel.** The first version created the code from the kernel's own context. That consumed the Core proxy's first nonce during construction-time `initialize`, and the deployment controller predicts the ProxyAdmin address from exactly that nonce — genesis reverted (`FixtureDeployment.deployPair` called `owner()` on my cache contract). Proxy tooling relies on a proxy's nonce sequence; the kernel must never `CREATE` in the Core's context. Deploying from the pinned helper's account keeps the trust model (the helper already produces the bytes) and leaves the Core's nonce alone.

**Size.** `UpgradeAdmissionLibrary` (which inlines the kernel) is 24,565 bytes, 11 under EIP-170 (control: 24,533, 43 under). The margin was bought with the single type load per leaf, the two literal hashes, reading the journal value in place, and one revert site. Codex's stated prerequisite for any further kernel feature — module decomposition — stands; this candidate does not deliver headroom.

## 7. Changed assumptions (must be read before adopting)

1. **A type's cache is at most 24,575 bytes** (EIP-170 minus the STOP prefix; 65,535 under EIP-7954 if adopted). The reader's old bound was 131,072. Every real cache is 1,248–2,784 bytes; the largest legal schema (64 fields, 16 roles, 8 indexes, 32 constraints, long descriptors) could exceed the new bound — such a group is refused at admission with `HelperDeploy()`, not silently.
2. **Type admission performs a contract creation** (from the helper's account, inert code beginning with `STOP`). Environments that forbid `CREATE` from the helper, or count deployed contracts, must know. Orphaned caches from a reverted admission cannot occur: the deploy happens inside the replay that lands the row, so a revert unwinds both.
3. **The stored type layout changed** (slot p+2 is a pointer, not a bytes head). A populated Store cannot be upgraded onto this kernel without migrating every type row; only fresh genesis is safe. The prototype's worlds are disposable; a migration step belongs to the same follow-up Codex listed for K10's populated-layout migration.
4. **The helper contract has a state-changing function** (`deployCache`, public, inert). Its codehash changes with the source, as any helper change does; pinning is unaffected. Anyone may call it — it is an SSTORE2-style public factory of code that can never execute.
5. **Off-chain readers that read type rows through `typeRow(bytes32)` are unaffected** (state-reader.mjs, upgrade-reader.mjs, point-reads/admitted-body tests: verified by the c0-core node tests). A reader that derives the cache from raw storage slots (`eth_getStorageAt`) must follow the pointer with `eth_getCode` and drop the first byte; the index-layer lab's `lab-slots.mjs` and this folder's `slots.mjs` label the head slot accordingly.
6. **Glamsterdam (EIP-8037/8038, QUOTED):** `EXTCODECOPY`/`EXTCODESIZE` gain one extra `WARM_ACCESS` (100) and cold account access rises 2,600 → 3,000, so the per-type load becomes ≈3,200 instead of ≈2,700 — still against 39–87 cold slots at 2,100 each, which the schedule leaves unchanged. Declaring a type: code deposit 200 → 1,530 per byte plus `CREATE_ACCESS` 12,000 and a new-account 183,600 in state-gas, i.e. ≈4.5 M for BindingSet/1 (2,784 bytes) versus ≈9.6 M for 87 fresh slots at 110,020 — cheaper on both schedules.

## 8. Remaining bottleneck and open items

* **Remaining bottleneck of an admission** after this change (steady tag 2,503,133): FRESH slots 1,149,400 (46% of the receipt; 56 slots, all rows/indexes/mirrors) and the journal's interpreter plumbing ≈815,000 (33%). The next avoidable item is no longer a read: it is the per-record fixed cost of the kind-3 "record occurrences" family (60,000 per new record for a list that holds one entry) and the ordinal mirrors — both policy, not representation.
* **Reads:** `_readBasis()` never touched the cache (the recon confirmed it: four external calls, six cold account accesses, the 21-word execution set) — the round-1 point-read finding (~120k per read) is untouched by this change and remains the browsing bottleneck. `getTypeSchema`, the one checked reader that walks the cache, drops from cold storage words to code words (§5).
* **Size margin** 11 bytes: decomposition before any further kernel feature (Codex's follow-up).
* **Not measured:** a type-declaration transaction on the routed path (the fixture admits the 9-type extended group through `lab.publish` before the router exists; its receipt is not captured by the harness) — the per-type cost is ESTIMATED from the schedule in §7.6 and should be captured when the group-admission op is added to the harness sequences.
* **Disk:** the host's data volume hit 100% during this work; ~900 MB of git-ignored, regenerable trace archives (index-layer lab, gas-2026-09-10) were deleted to finish. Their sha256s remain in the respective `index.json`.
