## Evidence and intended behavior

The [[files-withdrawal-probe-plan-20260914|three characterization tests]] actually
pass at frozen input `e2b63fd09ed5acf0f9581f58b32497f4ea7f913197c18f9b4fdf19983ba5a407`.
They confirm that count0 retained Records remain admissible parents and that
withdrawal changes neither their bytes nor selected HEAD/path/tag Bindings.
The Files reader nevertheless reports E_PROFILE, including for entire folders
and conflicts. Bob's REUSE then restores readability without undoing Alice's
withdrawal. Preserve that pre-fix evidence and commit before editing expectations.

The intended ordinary reader returns the exact selected, retained, valid
revision. Current occurrence maintenance is a separate fact. A count measures
active occurrences, **not distinct maintainers, replicas or trusted authors**.
Removing this false profile-integrity gate keeps current counts, withdrawal
evidence, full state-readable bodies and authored selection intact. It changes
neither Core WITHDRAW nor application revocation/removal. This follows existing
draft retained-read semantics and does not require waiving an owner requirement.

## Completion and remaining product choice

Retained well-formed contents no longer poison a folder simply because active
occurrences reach zero; Bob cannot toggle Alice's display by maintaining a copy.
Counts and attributed withdrawal evidence stay available through existing Core
reads. Combining any maintenance fact with a result requires the same basis and
correct Record/author scope; no separated unqualified boolean is introduced.

An explicit maintenance-filtered view or advanced placement-claim withdrawal
that permits Lens fallthrough is a different product policy, still unimplemented
in this compact prototype. It is not smuggled into this bug fix. No universal
display policy, privacy guarantee or permanent protocol choice is adopted.
