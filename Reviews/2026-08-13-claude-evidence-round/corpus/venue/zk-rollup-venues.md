## 0. Headline: Polygon zkEVM is dead — verified

**Polygon zkEVM Mainnet Beta was shut down on 2026-07-01.** This is not a wind-down-in-progress; the chain is off.

- `documented` — Polygon Labs announced the sunset 2025-06-11: *"The zkEVM sequencer will run for the next 12 months, with forced transactions permanently enabled so users can exit at any time."* The same post warns *"unsophisticated users should exit before the sequencer stops running"* because using forced transactions is expected to be difficult, and says Polygon "will not support new EIPs" and internal service targets are lowered. [forum.polygon.technology/t/sunsetting-polygon-zkevm-mainnet-beta-in-2026/21020](https://forum.polygon.technology/t/sunsetting-polygon-zkevm-mainnet-beta-in-2026/21020)
- `reported` — *"Polygon Labs shut down the Polygon zkEVM network on July 1, 2026."* Mainnet and Cardona testnet endpoints both dead. [alchemy.com/docs/reference/polygon-zkevm-deprecation-notice](https://www.alchemy.com/docs/reference/polygon-zkevm-deprecation-notice)
- `reported` — sequencer offline 2026-07-01, chain halted; exit snapshot taken, wallet (EOA) balances auto-migrated to Ethereum L1 and claimable via a dedicated interface; **funds locked in L2 DeFi contracts cannot be auto-migrated and risk being inaccessible**; unclaimed assets deemed abandoned after **2027-12-31**. CEO Marc Boiron: team *"actually stopped work on the zkEVM Mainnet Beta a year and a half ago."* [cryptotimes.io/2026/07/01/polygon-shuts-down-its-once-flagship-250m-zkevm-on-july-1](https://www.cryptotimes.io/2026/07/01/polygon-shuts-down-its-once-flagship-250m-zkevm-on-july-1/)
- `observed` — **`docs.polygon.technology/sitemap.xml` contains zero URLs matching "zkevm"**. The entire zkEVM documentation set has been removed from Polygon's docs site; only AggLayer/pessimistic-proof pages remain. Checked 2026-08-12.
- `observed` — Polygon zkEVM does not appear in L2BEAT's rollup summary or risk tables (23 rollups listed, not among them). [l2beat.com/scaling/summary](https://l2beat.com/scaling/summary), [l2beat.com/scaling/risk](https://l2beat.com/scaling/risk)

**The pre-death degradation matters more than the death itself.** Seven months before shutdown, the security model was silently gutted:

- `documented` — L2BEAT config milestone: **"Migration to Pessimistic Proofs", 2025-12-03 — *"Polygon zkEVM stops validating the full L2 state and moves to bridge accounting proofs."*** [raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/projects/polygonzkevm/polygonzkevm.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/projects/polygonzkevm/polygonzkevm.ts)
- `documented` — L2BEAT's AggLayer template, pessimistic variant: `stateValidation: STATE_NONE` — *"Currently the system permits invalid state roots"*; DA: *"Transaction data is kept off-chain. Bridge accounting is protected by pessimistic proofs while L2 state transitions are not proven"*; `sequencerFailure: no mechanism (forced batch disallowed)`; `proposerFailure: cannot withdraw`; exit window: zero. [templates/agglayer.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/templates/agglayer.ts)
- `documented` — L2BEAT tracked state updates via `verifyBatchesTrustedAggregator` (selector `0x1489ed10`) — a named **trusted aggregator** role. (same polygonzkevm.ts)

For a durability question, this is the full failure trajectory in one venue: validity proofs → bridge-accounting-only proofs → DA moved off-chain → sequencer off → docs deleted → contracts permanently frozen with an EOA-only claims path and a 2027 abandonment deadline. Contract-resident data (which is what an attestation/registry filesystem *is*) had no migration path at all.

## 1. Linea

**1. Censorship resistance** — `reported` Single trusted sequencer operated by Consensys. L2BEAT: *"Only a trusted sequencer is allowed to submit transaction batches"*; users can be censored *"if the operator refuses to include their transactions."* No permissionless sequencing. [l2beat.com/scaling/projects/linea](https://l2beat.com/scaling/projects/linea)

**2. Force inclusion / escape hatch — NONE LIVE.**
- `documented` L2BEAT config for Linea uses `FORCE_TRANSACTIONS.SEQUENCER_NO_MECHANISM` and risk value **"No mechanism"** = *"There is no mechanism to have transactions be included if the sequencer is down or censoring."* [projects/linea/linea.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/projects/linea/linea.ts), [common/riskView.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/common/riskView.ts)
- `documented` Linea's **own** docs carry a forced-transactions design page banner: ***"🚧 Forced transactions are not yet live. This documentation describes the intended design."*** Mechanism as designed: `ForcedTransactionGateway` on L1, `submitForcedTransaction(forcedTransactionStruct, lastFinalizedStateStruct, {value})`, fixed fee readable as `forcedTransactionFeeInWei` on `LineaRollup`, rolling hash committing to the ordered sequence, and an `AddressFilter` check. [docs.linea.build/protocol/forced-transactions](https://docs.linea.build/protocol/forced-transactions), [docs.linea.build/protocol/how-to/forced-transactions](https://docs.linea.build/protocol/how-to/forced-transactions)
- **Critical, `documented`:** even the *intended* design is not an L1 escape hatch — *"the sequencer is still required to produce blocks and process them. What they bypass is the normal L2 RPC submission path."* It fails exactly when you need it (dead/hostile sequencer).
- `documented` Only fallback: **after 6 months with no finalized blocks the Operator role becomes public**, "theoretically allowing anyone to post data / propose state"; L2BEAT's exit-mechanism note says users can exit *"eventually, after 6 months of inactivity from the centralized Operator"* by replacing the Operator. Named delay window constant: `unknown` (I could not retrieve the on-chain constant name/value; L2BEAT states it as 6 months).
- Has anyone invoked it: `unknown`.

**3. Sequencing** — `documented` Soft finality ≈ **1 second**; docs assert the transaction *"will not be removed or reordered by Linea"* (a trust statement about a single operator, not a protocol guarantee). Hard finality = ZK proof verified on L1 + L1 finalized (~12.8 min): **median ≈ 2 hours**, target <30 min, *"should never exceed 16 hours under normal operating conditions."* [docs.linea.build/network/overview/transaction-finality](https://docs.linea.build/network/overview/transaction-finality)

**4. Finality / proving** — `reported` Validity proofs (SNARK, **requires trusted setup**), execution delay 0. `documented` Proof system covers 100% of the zkEVM since 2024-06-09 (L2BEAT milestone). Proving/proposing is **whitelisted**: risk value `PROPOSER_CANNOT_WITHDRAW` = *"Only the whitelisted proposers can publish state roots on L1, so in the event of failure the withdrawals are frozen."* Prover source published: yes (L2BEAT stage check `proverSourcePublished: true`). Proving latency: see median 2h above.

**5. Data availability** — `reported` **Onchain, and unusually for a zk rollup, full transaction data rather than state diffs.** `documented` Blobs since 2024-03-26 ("Linea starts publishing data to blobs"). No validium mode for Linea mainnet found.

**6. State availability / reconstructability — best-documented of the four.** `documented` Linea ships a supported recovery path: **Linea Besu with the State Recovery plugin + Shomei state manager**, which *"Decompresses the blob data; Replays the transactions in the execution client"* from *"finalized blobs from L1"*, so that *"any entity could then resume transaction sequencing, confident that state was resuming from the correct point."* Requirements: Besu synced from genesis in `FULL` sync / `BONSAI` storage, an L1 RPC, and a **Blobscan endpoint** for blob data; documented start block 9572301 on Sepolia, **mainnet start block "TBC"**. No Linea-hosted service required. [docs.linea.build/network/overview/recoverable-state](https://docs.linea.build/network/overview/recoverable-state), [docs.linea.build/network/how-to/recover-state](https://docs.linea.build/network/how-to/recover-state)
- `inferred` Caveat for decades: the pipeline reads blobs via a **third-party blob archive**; Ethereum consensus clients prune blobs (~18 days), so multi-decade reconstructability rests on archival services, not on L1 itself.

**7. L2BEAT stage** — `observed` **Stage 0** ([l2beat.com/scaling/summary](https://l2beat.com/scaling/summary)). `documented` Specific blockers from the config checklist: `usersHave7DaysToExit: false`, `usersCanExitWithoutCooperation: false`, `principle: false`, `securityCouncilProperlySetUp: false` with reason ***"Security Council members are not publicly known"***, `verifierContractsReproducible: false`. Stage 2: `delayWith30DExitWindow: false`.

**8. Upgradeability — instant.** `reported` L2BEAT: *"Funds can be stolen if a contract receives a malicious code upgrade. **There is a 0s delay on code upgrades**"*; Exit window: **"None"** — *"There is no window for users to exit in case of an unwanted upgrade."* [l2beat.com/scaling/projects/linea](https://l2beat.com/scaling/projects/linea), [l2beat.com/scaling/risk](https://l2beat.com/scaling/risk). `documented` Linea's own docs: *"Upgrading the system requires signatures from both the Linea Operational Safe and the Linea Security Council Safe multisignature accounts."* [docs.linea.build/protocol/architecture/smart-contracts](https://docs.linea.build/protocol/architecture/smart-contracts). Council composition: not public (per L2BEAT). `reported` A roadmap phase reportedly plans to retain a **6-of-8 threshold for immediate upgrades** while diversifying membership, and to add "censorship-resistant withdrawals" in a later phase — I could not load the roadmap page itself (404 on `docs.linea.build/architecture/overview/decentralization-roadmap`), so treat as unverified.

**Contradiction to flag (Linea):** L2BEAT's config file models Linea with `CONTRACTS.UPGRADE_WITH_DELAY_RISK(timelockDelay)` where `timelockDelay = Timelock.getMinDelay()`, implying a timelock — while the **rendered** L2BEAT page reports that delay as **0s** and the exit window as None. Reconciliation: the timelock contract exists but its current `getMinDelay()` is 0. Also: Linea's docs publish a full forced-transactions spec that a casual reader could mistake for a live escape hatch; it is explicitly not live, and by design does not survive sequencer failure.

## 2. Scroll

**1. Censorship resistance** — `documented` *"Scroll L2 operates a centralized sequencer that accepts transactions and generates new L2 blocks."* [docs.l2beat.com/code_walkthroughs/scroll/sequencing.html](https://docs.l2beat.com/code_walkthroughs/scroll/sequencing.html). `documented` Two sequencer addresses in L2BEAT discovery: `0x054a47B9E2a22aF6c0CE55020238C8FEcd7d334B`, `0xE514A8aE91d164C6Fb48a7DE336e10C34AF4e858`.

**2. Force inclusion / escape hatch — the strongest of the four on paper, but its parameters are owner-mutable.**
- `documented` **Enforced transactions**: user calls `sendTransaction(...)` on the `EnforcedTxGateway` from L1 (EOA or signature-relay variant); *"a user can initiate an L2 transaction directly from their wallet via L1, allowing them to withdraw tokens or call other contracts on L2 even if the sequencer is unresponsive"*; L2 sender identity is preserved. [docs.scroll.io/en/developers/l1-and-l2-bridging/enforced-transactions](https://docs.scroll.io/en/developers/l1-and-l2-bridging/enforced-transactions/)
- `documented` **Enforced batch mode / permissionless batch submission**: `commitAndFinalizeBatch` checks two conditions — *"No batch has been finalized for `maxDelayEnterEnforcedMode` seconds [or] No message has been included for `maxDelayMessageQueue` seconds."* Once active, *"only batches with proofs can be submitted until the owner (Scroll Security Council) explicitly disables enforced mode"* and *"the designated Sequencer can't commit or finalize batches anymore."* Queue messages *"cannot be skipped or dropped."* [docs.l2beat.com/code_walkthroughs/scroll/sequencing.html](https://docs.l2beat.com/code_walkthroughs/scroll/sequencing.html), [docs.l2beat.com/code_walkthroughs/scroll/admin_ops.html](https://docs.l2beat.com/code_walkthroughs/scroll/admin_ops.html)
- **Named constants:** `maxDelayEnterEnforcedMode`, `maxDelayMessageQueue`, stored in `SystemConfig.enforcedBatchParameters`. `documented` Both are **`uint24` seconds and settable only by the contract owner via `updateEnforcedBatchParameters` (`onlyOwner`)** — no hard MIN/MAX bounds in the source. [SystemConfig.sol](https://raw.githubusercontent.com/scroll-tech/scroll-contracts/main/src/L1/system-contract/SystemConfig.sol). **Value: `reported` 7 days each** — L2BEAT's Scroll page reportedly states the mechanism activates if an L1 message or a batch has not been finalized for more than 7 days; I could **not** re-verify this verbatim (page truncates on fetch) — see "could not verify".
- Works with a dead sequencer: `documented` yes, that is its stated purpose. Has anyone demonstrably invoked it on mainnet: `unknown`.
- **Durability caveat, `inferred` from `documented` facts:** the escape-hatch window is a mutable parameter owned by the same 3-of-4 multisig that has a 0-second emergency upgrade path (see 8), and the owner can also *disable* enforced mode once triggered.

**3. Sequencing** — soft-confirmation semantics and preconfirmation reorg risk: `unknown` (not stated in the pages I read).

**4. Finality / proving** — `documented` Two-phase: `commitBatchWithBlobProof` (DA), then `finalizeBatchWithProof` (verification). Every batch is finalized with a validity proof; the coordinator dispatches to *"a randomly selected zkEVM prover"* and *"a randomly selected aggregator prover"* — i.e. **permissioned prover set in normal operation**, permissionless only in enforced mode. [docs.scroll.io/en/technology/chain/rollup](https://docs.scroll.io/en/technology/chain/rollup/). `reported` L2BEAT: "Validity proofs (ST, SN)" (STARKs wrapped in SNARKs), **executionDelay 0**; proposer failure = "Self propose" (*"users can leverage the source available prover to submit proofs to the L1 bridge"*); `proverSourcePublished: true`, `programHashesReproducible: true`, `verifierContractsReproducible: true`. Proving latency: `unknown`.
- `documented` **Verifier incident history** (L2BEAT config): 2024-07-05 *55 batches reverted* (compression bug); 2025-05-26 emergency plonky3 fix; 2025-08-09 emergency verifier fix; **2026-02-23 emergency verifier bug (guest prover program flaw)**; 2026-06-26 OpenVM 1.6.0 verifier swap at index 9 (*"programs reproduced but the verifier not yet regenerated"*).

**5. Data availability** — `documented` **Blobs, carrying transaction data** (`blobVersionedHash` in the batch header; `commitBatchWithBlobProof`); state root/withdraw root are posted only at finalize. `reported` L2BEAT: `DATA_ON_CHAIN` = *"All of the data needed for proof construction is published on Ethereum L1"* (not state-diff-only). No validium mode for Scroll mainnet found.

**6. State reconstructability** — `inferred` Full transaction data on L1 blobs means state is in principle replayable by an independent party. **I found no documented, supported reconstruction tool** analogous to Linea's Besu recovery plugin — `unknown`. Same blob-retention caveat as Linea.

**7. L2BEAT stage — regressed from Stage 1 to Stage 0 in June 2026.** `documented` verbatim from L2BEAT config:
> `securityCouncilProperlySetUp: { satisfied: false, message: 'On 2026-06-01, Scroll replaced its independent 9-of-12 Security Council with a 3-of-4 multisig of Scroll team members (ScrollAdminMultisig, 0xcca54B...). The new entity does not meet the size or organisational-diversity requirements of a Security Council.' }`

Also failing: `usersHave7DaysToExit: false`, `usersCanExitWithoutCooperation: false`. Stage 0 requirements all satisfied. [projects/scroll/scroll.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/projects/scroll/scroll.ts); `observed` Stage 0 on [l2beat.com/scaling/summary](https://l2beat.com/scaling/summary). Prior state: `reported` Scroll reached Stage 1 with the Euclid upgrade (announced April 2025), which introduced enforced transactions, permissionless batch submission, and *"The Security Council, an independent body of 12 reputable members, forming a 9/12 multisig"* [docs.scroll.io/en/technology/overview/scroll-upgrades/euclid-upgrade](https://docs.scroll.io/en/technology/overview/scroll-upgrades/euclid-upgrade/).

**8. Upgradeability — effectively instant, held by 3 of 4 team signers.** `documented` L2BEAT config: `upgradesAdmin = { upgradableBy: [{ name: 'ScrollAdminMultisig', delay: 'no' }] }`. Timelock minimum delays from L2BEAT's diff history: **TimelockSCEmergency = 0s, TimelockEmergency = 0s, TimelockFast = 1d, TimelockSCSlow = 3d**. Transition dates: 2026-06-01 (*"All Security Council permissions ... transferred to ScrollAdminMultisig"*), completed 2026-06-16 (*"ScrollAdminMultisig now controls the `scMinorityNoDelay` path (used to unpause core contracts via the PauseController)"*). [projects/scroll/diffHistory.md](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/projects/scroll/diffHistory.md). `reported` Exit window: **None** ([l2beat.com/scaling/risk](https://l2beat.com/scaling/risk)). `reported` Rationale for dissolution, proposed 2026-04-13: *"the move follows a review of the council's cost relative to its usage, concluding that maintaining the structure is no longer justified"* [ambcrypto.com](https://ambcrypto.com/scroll-proposes-governance-overhaul-dissolving-security-council-amid-decentralization-concerns/), [cryptopolitan.com](https://www.cryptopolitan.com/scroll-criticism-dissolve-security-council/).

**Contradiction to flag (Scroll):** Scroll's own docs still describe the Security Council as *"an independent body of 12 reputable members, forming a 9/12 multisig"* and say enforced mode is disabled by *"the owner (Scroll Security Council)"* — but that body was dissolved on 2026-06-01 and its powers now sit with a 3-of-4 team multisig. Venue docs are stale relative to on-chain reality; L2BEAT's discovery caught it.

## 3. zkSync Era

**1. Censorship resistance** — `reported` Single sequencer; L2BEAT sequencerFailure = **"Enqueue via L1"**. No permissionless sequencing.

**2. Force inclusion / escape hatch — this is the sharpest doc-vs-L2BEAT contradiction in the set.**
- `documented` (venue) ZKsync docs: users *"have the option to force the inclusion of their transactions by submitting them through L1"*, and the priority queue *"will always be available as an escape-hatch mechanism (even if a centralized or decentralized sequencer is employed), to protect users against censorship by a malicious sequencer."* [docs.zksync.io/zksync-protocol/era-vm/transactions/transaction-lifecycle](https://docs.zksync.io/zksync-protocol/era-vm/transactions/transaction-lifecycle)
- `documented` (L2BEAT) The classification assigned is `SEQUENCER_ENQUEUE_VIA('L1')`, defined verbatim as: ***"Users can submit transactions to an L1 queue, but can't force them. The sequencers cannot selectively skip transactions but can stop processing the queue entirely."*** [common/riskView.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/common/riskView.ts)
- `documented` L2BEAT's ZK Stack template additionally notes: users can force any transaction via L1 through the priority queue, but **"operator may filter via `TransactionFilterer` without delay."** [templates/zkStack.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/templates/zkStack.ts)
- **Net:** no all-or-nothing forced inclusion with a deadline. There is no named force-inclusion expiry constant. Ordering fairness is preserved (no selective skipping) but liveness is not guaranteed, and an address filter can exclude a specific caller with no delay. Anyone demonstrably invoked it: `unknown`.
- `documented` Proposer failure = `PROPOSER_WHITELIST_GOVERNANCE`, rendered as **"Replace proposer"** — recovery is a *governance action*, not a user action.

**3. Sequencing** — `documented` Four states: **Pending → Included** (*"Added to a block, but the block's batch is not yet committed"*) **→ Verified → Failed**; sequencer gives soft confirmations, and *"transactions are treated with instant confirmation for user convenience."* Whether an Included-but-uncommitted transaction can be reorged: **not stated** — `unknown`.

**4. Finality / proving** — `documented` Batch formation "a few minutes" → commit → **proof generation "typically takes about an hour"** → proof submission → **execution with "a delay of approximately 3 hours"**; total ≈ 3 hours. [docs.zksync.io/zksync-protocol/rollup/finality](https://docs.zksync.io/zksync-protocol/rollup/finality). `documented` The delay *"has been reduced from 21 hours to a 3 hour minimum"*, exists so there is *"plenty of time to detect an exploit, investigate, and freeze the protocol via governance"*, and **"the ZKsync team controls a Validator role restricted through an intermediate smart contract with a time lock"** — i.e. **whitelisted proposer/validator**. Changing the delay requires a governance proposal. [docs.zksync.io/zksync-protocol/security/withdrawal-delay](https://docs.zksync.io/zksync-protocol/security/withdrawal-delay). `reported` L2BEAT: "Validity proofs (ST, SN)" with **3h execution delay**.

**5. Data availability — state diffs, not transactions.** `documented` *"Instead of submitting detailed transaction data, ZKsync Chains focuses on posting **state diffs** to L1."* Pubdata = compressed state diffs + L2→L1 logs/messages + published bytecodes + bytecode hashes. Validium option exists at the ZK Stack level: *"When a chain opts not to post its data on-chain, it operates under a model known as a validium"* (Era mainnet itself is a rollup). [docs.zksync.io/zksync-protocol/rollup/data-availability](https://docs.zksync.io/zksync-protocol/rollup/data-availability). `reported` L2BEAT: `DATA_ON_CHAIN_STATE_DIFFS` = **"Onchain (SD)"**. `documented` Blobs since March 2024 ("ZKsync Era starts publishing data to blobs").

**6. State reconstructability** — `documented` (venue) *"the entire Layer 2 (L2) state can be reconstructed from the data submitted to Ethereum's Layer 1 (L1)."* `observed` A working open-source reconstructor exists: **`eqlabs/zksync-state-reconstruct`** — rebuilds L2 state from genesis using commit blocks published on L1 via an Ethereum JSON-RPC endpoint, and validates by comparing local state roots against published ones; supports snapshot checkpointing. [github.com/eqlabs/zksync-state-reconstruct](https://raw.githubusercontent.com/eqlabs/zksync-state-reconstruct/main/README.md). A Matter-Labs-maintained equivalent at `matter-labs/state-reconstruct` returned **404** — `unknown` whether an official tool is currently maintained.
- **State-diff DA consequence, `inferred`:** state diffs let you rebuild *current state*, not *transaction history*. For a filesystem whose semantics are event/attestation-based (logs, calldata, per-write provenance), the historical write log is not reconstructable from L1 alone if all operators disappear — only the final storage image is. This is a materially different guarantee from Linea's and Scroll's full-transaction DA.

**7. L2BEAT stage** — `observed` **Stage 0** ([l2beat.com/scaling/summary](https://l2beat.com/scaling/summary)). `documented` blockers from the ZK Stack template checklist: `principle: false`, **`usersHave7DaysToExit: false`**, **`usersCanExitWithoutCooperation: false`**; `securityCouncilProperlySetUp: true` (so the council is *not* the blocker here, unlike Linea/Scroll); `delayWith30DExitWindow: false`. [templates/zkStack.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/templates/zkStack.ts)

**8. Upgradeability — the most structured governance of the four, but with a no-delay emergency path.** `documented` Security Council **8/8** for upgrade approval; Guardians **7/9** (onchain veto, offchain legal veto, fallback approval, emergency co-signing; veto extension 6/9); ZK Foundation multisig required as emergency co-signer. Freeze powers: **soft freeze 5/8, hard freeze 6/8**. Normal upgrade path ≈ **7 days**; guardian fallback ≈ **8–9 days**; exit window ≈ **6 days**. Composed as `upgradeDelayWithScApprovalS = protTlMinDelayS + executionDelayS + legalVetoStandardS + upgradeDelayPeriodS`, plus an `upgradeDelayNoScS` emergency path without Security Council approval. Token governance: proposal threshold 1,000,000 ZK, quorum 3,000,000 ZK. [projects/zksync2/zksync2.ts](https://raw.githubusercontent.com/l2beat/l2beat/main/packages/config/src/projects/zksync2/zksync2.ts). `reported` L2BEAT risk table renders this as exit window **"Emergency: None; Regular: 4d 3h"** ([l2beat.com/scaling/risk](https://l2beat.com/scaling/risk)).

**Contradiction to flag (zkSync):** (a) docs call the priority queue a permanent *"escape-hatch"* against a malicious sequencer; L2BEAT's own definition of the assigned category says users *"can't force them"* and the sequencer *"can stop processing the queue entirely"*, with an operator-controlled `TransactionFilterer` acting without delay. (b) The venue's config-derived "exit window ≈ 6 days" / "normal upgrade ~7 days" does not match the rendered "Regular: 4d 3h" — these are different compositions of the same constants; the rendered figure is the one L2BEAT scores against the 7-day Stage 1 threshold, and it fails.

## Cross-cutting observations (evidence, not recommendation)

- `observed` **All three surviving venues are Stage 0**, and two of them are Stage 0 *because of the security council specifically*. None of the four ever offered a ≥7-day exit window on the upgrade path.
- `documented` **Two of three surviving venues can be upgraded with zero delay** (Linea 0s; Scroll 0s via a 3-of-4 team multisig). zkSync is the only one with a material normal-path delay, and it retains a no-delay emergency path.
- `documented` **Scroll's trajectory in 2026 is downward**: Stage 1 (Apr 2025) → independent 9-of-12 council dissolved (proposed 2026-04-13, executed 2026-06-01, completed 2026-06-16) → Stage 0. The stated reason was council cost.
- `documented` **Escape-hatch parameters are themselves upgradeable** by the same keys that can upgrade the contracts (Scroll's `updateEnforcedBatchParameters` is `onlyOwner`; the owner can also disable enforced mode after it triggers).
- `inferred` **Blob-based DA + decades**: Linea's documented recovery path requires a Blobscan endpoint; Scroll and zkSync also publish to blobs. Ethereum does not retain blobs indefinitely, so multi-decade reconstructability for all three depends on third-party blob archives rather than on L1 state.
- `documented` **Polygon zkEVM's end state is the reference failure case**: EOA balances were snapshotted and made claimable on L1; **contract-resident state had no migration path**, and unclaimed assets are declared abandoned after 2027-12-31.

## What I could not verify

1. **Scroll's actual `maxDelayEnterEnforcedMode` / `maxDelayMessageQueue` values.** Reported as 7 days each (attributed to the L2BEAT Scroll page), but that page truncates on every fetch attempt and the values are on-chain discovery outputs absent from the source files I could read. The type is `uint24` seconds and the setter is `onlyOwner`.
2. **Whether any user has ever actually exercised force inclusion / enforced transactions on Scroll mainnet, or the priority-queue escape path on zkSync Era.** No transaction-level evidence found; search budget exhausted before I could check explorers.
3. **Linea's mainnet state-recovery start block** — docs say Sepolia block 9572301 and mainnet "TBC", so the mainnet recovery path is documented but not fully parameterized.
4. **Linea's decentralization roadmap page** — `docs.linea.build/architecture/overview/decentralization-roadmap` returned 404 and the current sitemap contains no "decentralization" or "roadmap" URL. The 6-of-8 immediate-upgrade threshold and "censorship-resistant withdrawals" phase are `reported` from search summaries only.
5. **Linea's named force-inclusion deadline constant.** The design doc mentions a "guaranteed processing deadline on the L2" but names no constant or duration.
6. **Whether an officially maintained Matter Labs state-reconstruction tool exists** (`matter-labs/state-reconstruct` → 404). Only the third-party `eqlabs` implementation was confirmed.
7. **Scroll and zkSync preconfirmation/reorg semantics** — neither venue's docs that I read state whether a soft-confirmed transaction can be reorged before L1 commit.

9. **Polygon zkEVM's L2BEAT project page content and archived status** — the page truncated on all three attempts; Polygon zkEVM appeared in neither the rollup summary/risk tables nor the (possibly truncated) archived listing I retrieved.
10. **Exact blob retention window on Ethereum** — I did not verify the current retention constant from a primary source this session; the reconstructability caveat above is `inferred`.
