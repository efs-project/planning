## 2. Lane question 1 — What is the current Files model, and which parts are candidate / adopted / July evidence?

### The model (all from `hierarchical-files-and-folders.md`)

- **Objects.** A file or directory is one `ObjectGenesis/1 {publisher, salt, meaning}` Record whose `meaning` is `FILES_FILE_1` or `FILES_DIRECTORY_1`; a node is valid once a deterministic publisher-charter Binding at `PositionKey(PURPOSE_OBJECT_CHARTER_V1, ObjectId, 1)` is `BOUND` to that Record (§3.1 lines 356-409). "Changing FILE to DIRECTORY creates a new Object" (line 378) — there is no file/directory hybrid.
- **Names as Bindings.** Each child name is a Principal-qualified Binding at `PositionKey(PURPOSE_FILES_NAME_SLOT_V1, D, nameRole(N))` whose target must be a RECORD leaf-0 `DirectoryEntry/1 {parent,name,child,mountOverride?}` or `DirectoryWhiteout/1 {parent,name}` (§3.2, §4.1). Whiteout = `MASKED` with no lower-tier fallthrough; tombstone = "that Principal makes no claim" → fallthrough (Decision summary #3, lines 55-57).
- **Plans (Lenses) are mount-local.** `MountDescriptor/1 {rootNode, profileId, configRef}`; the public profile's `PublicFilesMountConfig/1 {namespacePlan?, contentPlan, metadataPlan?, propertyProfile?}` separates who controls names from who controls a file's current revision; Plans carry an exact `purposeAndScope = H(DOM_PLAN_PURPOSE, purposeTag, H(DOM_FILES_PLAN_SCOPE, filesProfileId, rootNode))` (§3.4 lines 494-567). `FilesRouteConfig/1` binds Realm, root Mount, profile, basis mode, completeness policy, freshness policy, and an optional `writeRouter` + codehash (§3.5).
- **Revisions.** `FileRevision/1 {node, content: ChunkTree/1, mediaType, charset?, executableHint, parents[≤8]}`; currentness only via the file-head Binding at `(PURPOSE_FILES_REVISION_HEAD_V1, F, FILE_REVISION_ROLE_V1)` (§3.3, §4.1). Identity separation: "File Object / FileRevision / ChunkTree / Locator … Locators never become content identity" (§7.1 lines 1031-1041).
- **Canonical names/URLs.** `FilesName/1` = 1–255 UTF-8 bytes after NFC, Unicode 17.0.0 pin, byte-exact case-sensitive equality, no folding (§2.1 lines 130-153). Canonical serializer emits RFC 3986 unreserved bytes directly, everything else uppercase `%HH`; no reserved path prefix; the only reserved query key is `efs-control` (§2.2). One convergent parser pipeline (§2.3).
- **Resolver.** Point lookup is B0 Plan evaluation over Binding heads with a closed outcome table (§4.2 lines 632-656); complete listing needs the proposed `BindingScope` (§5); results use a closed registry (`PRESENT_FILE` … `UNSUPPORTED_HOST_PATH`, §9 lines 1489-1509) with HTTP, POSIX, and WinFsp mappings; "The SDK, Web Client, OS, and mounts share one resolver core. An adapter may not invent a different logical tree to suit its host" (§1.2 lines 118-119).
- **Views/citations.** `FilesView` pins chain/Core/Realm/route/mount/profile/blockNumber/blockHash/stateRoot/executingRevisionId/admissionHigh/admissionBasisRevisionId; snapshots are "block-hash-pinned Realm views, never arbitrary mid-envelope admission prefixes" (Decision #8; §6.1).
- **Mutation.** Operation table §8.1 (create file = ObjectGenesis + charter bind + ChunkTree + FileRevision + DirectoryEntry + file-head bind + name-slot bind; create dir = ObjectGenesis + charter bind + DirectoryEntry + name-slot bind; edit = ChunkTree + FileRevision + file-head CAS rebind). Certified `O_EXCL`/`NOREPLACE`/rename needs the non-Core `FilesRouter` plus `RoutedAdmissionIntent/1` (§8.2).

## 4. Lane question 3 — How does the three-host mount requirement map onto the Files model, and who owns the native adapters?

**Mapping.** The mount doc's platform-neutral core (§4 lines 303-314: `mount/lookup/open_dir/read_dir/get_attributes/open_file/read/list_metadata/close`) maps onto the hierarchical doc's point lookup (§4.2), `BindingScope` listing (§5.3), open-handle pinning of `(FilesView, effectiveMount, File Object, FileRevision, ChunkTree)` (§7.3 line 1082), verified range acquisition (§7.3), result→errno/NTSTATUS tables (§9 lines 1561-1578), `CommonHostAlias/1` + `DirectoryProjectionV1` + `HostFileId` (§10), and the daemon control protocol + fixed `user.efs.*` diagnostics + `FilesPropertyProfile/1` (§10, §10.1). The mount doc's open questions at lines 674-690 are partly answered by the hierarchical doc without the mount doc saying so: file/dir hybrid (line 676) → "Changing FILE to DIRECTORY creates a new Object" (§3.1); `~efs` control entry vs leading-`~` rejection (line 684) → no reserved path prefix, `~efs~` is an *alias* prefix and control lives on a socket/named pipe "never injected as a child" (§2.2 line 208-209, §10 lines 1704-1708, 1778-1779); mount generation identity (line 677) → `FilesView` (§6.1). The July mount doc still assumes leading `~` is rejected by the canonical grammar (fs-pass-synthesis C2 "leading `0x7E`"); the hierarchical grammar does not reject `~` (§2.1 reject list lines 136-143) and instead aliases names beginning `~efs~`.

**Requirement vs candidate scope.** The mount doc §10 (lines 522-552) wants a "Durable—not Etched—portable read-only profile" and says "Do **not** freeze: FUSE itself … one daemon implementation … one local database … one cache layout". The hierarchical doc freezes daemon-facing bytes: the control-frame codec (`u32be frameLen || u8 version …`, kinds `0x01..0xff`, `HostDirectoryCursorV1`, lines 1709-1768) and says "`HostEntryMetadataV1`, row, result/reason, and xattr value binary widths are minted in the same cross-platform IDL/vector bundle before any adapter claims parity" (1766-1768). That is more than the ruling asks for (ruling line 109: "exact adapters, versions, packaging, licensing, and support floors remain evidence-driven Durable choices").

**Ownership.** `Designs/web-client-os/README.md` line 7 lists "@os-drives-pm boundary review (2026-08-14)"; its Ownership table line 413: "OS Drives owns native handles, host aliases, projection behavior, errors, metadata projection, daemons, packaging, and three-host validation"; direction #11 (78-80) names a future `drive` repo; `mvp-and-acceptance.md` lines 449 and 853 and `web-platform-standards-and-forward-profile.md` line 266 defer to "the OS Drives lane/PM". The hierarchical doc header line 5: "Proposed new repos: core, os, drive". **No design folder, README, inbox, or rulings file exists for OS Drives** (`find Designs -iname '*drive*'` returns nothing; the only hit vault-wide is `Reviews/2026-07-29-ardrive-teardown-corpus`). The host-projection design that the OS Drives lane is said to own lives in `hierarchical-files-and-folders.md` §10, and Stage A's traceability defers exact enumeration and the whole three-host interface to a "mount lane" that has no artifact.

## 5. Lane question 4 — Where do large-file bytes live now; does any current doc put durable data in EIP-4844 blobs?

**Current model.** `system-constitution.md` §"Files, bytes, and large content" (222-237): "A Locator or URL is a claim about where bytes may be found, not content identity … Content identity is independent of storage provider. Locators are plural." `hierarchical-files-and-folders.md` §7.1: `ChunkTree Record = exact byte commitment and range geometry; Locator Record = authored claim about where committed bytes may be`; §7.3 acquisition verifies every chunk against the ChunkTree root before releasing bytes. B0 `chapters/b0-content-locators.md` §10.1 (lines 845-872) grades custody by class: 5 `STATE_PERMANENT` (contract-readable Realm state), 4 `ENDOWED_PERMANENT` (Arweave-class), 3 `CHAIN_HISTORY` ("bytes rode a chain's history/DA, archival-grade"), 2 `FUNDED_PINNED`, 1 `BEST_EFFORT`, 0 `EPHEMERAL`; state-tier custody (SSTORE2-shaped, `CHUNK_SIZE_STATE = 20,480`) is an "optional venue module, §11" (line 757), and `CHUNK_SIZE_DEFAULT` (256 KiB) "cannot reach state-tier custody" (line 767); 50 GiB "honest … posture is durable off-chain custody with graded evidence" (774-776).
