## 1. Headline

The four web-client-os documents are the most internally coherent product set in the vault: one layered module graph, a route-shaped guest boot, one requirement ledger (WCOS-R1…R67), one staged roadmap (Slices A–E) and a very long acceptance list. Their problem is not incoherence but *scope inflation and unrecorded authority*: the set carries 28 owner directions that live only in its own README (not in the append-only ruling ledger), it defines the MVP as "guest read + official basic File Browser writes" while the Core set still lists "writes or read-only + Arcade view?" as open, and its acceptance list mixes true MVP fixtures (cold guest read, three write journeys) with fixtures that belong to Slices D–E (Service-Worker generations, agent mandates, 64-Principal contract measurement, air-gapped reproducible builds). Everything the write journey needs from below — a deployed Core candidate, a chosen publication/admission signing arm, a byte carrier with clean-browser read-back, and a v2 SDK — is acknowledged as proposal-only and is not owned by anyone as an MVP deliverable.

## 3. Q1 — The MVP exactly as `mvp-and-acceptance.md` defines it, and what it needs that nobody has designed

### 3.1 Definition (cited)

- **Outcome** (`mvp-and-acceptance.md` §Outcome): "an official, static, self-hostable File Browser with two deliberately different entry paths: 1. a very fast unauthenticated read path for public file and folder links; and 2. an explicit promotion into a basic write-capable File Browser for creating folders, creating files from local bytes, and publishing a new immutable revision of a controlled file." A disposable empty-directory fixture "is evidence toward the MVP, not a substitute for it."
- **Required guest behaviour** (§Scope floor): open a deep link with explicit chain namespace, Core address/deployment/profile, Realm, "without touching a wallet provider"; parse route into separate fields (Realm descriptor + basis, route config, root Mount, `namespacePlan`, `contentPlan`, optional `metadataPlan`, path); resolve stable Directory/File; list "completely at one basis or say exactly why completeness cannot be established"; resolve exact `FileRevision`; retrieve bytes via untrusted Locators, reject corruption, fall back; render safely; expose provenance.
- **Required write behaviour** (§Scope floor): `New folder`, `New file`/upload, `Publish revision` "only after the user explicitly asks to write"; lazy-load "wallet connector, identity/controller resolver, action planner, signer ceremony, submitter, and optional content publisher"; uniform `PrincipalId` with separate `actualSignerAccount`; pin Realm/parent/Mount/Plans/Binding heads; preview in trusted System Chrome; "Under the current candidate, sign the authored `PublicationEnvelope` and the Realm-bound `AdmissionIntent` separately"; submit; per-effect status ladder; success only via canonical Reader Kernel read-back; reopen from a clean browser.
- **Deferred** (§Deliberately deferred): rename/move/copy/delete, multi-select, sharing, collaboration, editor; multi-Principal write policy; offline authoring, SW dependence, durable custody; package install, third-party Views, full Shell, Arcade Play, native mounts, private folders, default Commons; profile Try/Adopt/Fork/Activate; ERC-1271 (EOA-only adapter reports `ERC1271_UNSUPPORTED`).
- **User journeys** (§User journeys table): guest opens folder; guest opens file; user creates folder; user creates file; user publishes revision; authorized agent performs same write.
- **Candidate operation units** (§Operation sequence): Create directory = `ObjectGenesis + publisher-charter bind + DirectoryEntry + name-slot bind`; Create file adds `ChunkTree + initial FileRevision + file-head bind`; Publish revision = `ChunkTree + FileRevision + file-head CAS rebind`. These mirror `Designs/efsv2/hierarchical-files-and-folders.md` §8.1 table exactly.
- **Adapter label** (§Operation sequence): `writeProfile = EXPERIMENTAL_DIRECT_CORE / protocolConformance = false / filesPreconditionCertified = false`; "A later FilesRouter/certifier is a candidate mechanism, not an MVP assumption."
- **Performance budgets** (§Provisional performance budgets): ingress ≤15 KiB; guest-critical executable ≤250 KiB (250–400 dated exception; >400 fails); viewer closure ≤1.2 MiB; resolving frame ≤500 ms warm / ≤1.5 s cold "on the reference mid-tier device"; useful listing ≤3 s under the source envelope; parse/compile ≤150 ms; long tasks none >50 ms, cumulative ≤150 ms; ≤2 avoidable waterfalls; 0 unrequested OS/write/package/agent bytes. Source envelope: 10 Mbps / 80 ms RTT, static TTFB ≤300 ms, RPC TTFB ≤600 ms, carrier TTFB ≤600 ms, one directory page, ≤512 KiB content.
- **Acceptance sections**: A cold guest/exactness (9 boxes), B carrier/presentation safety (4), C official writes (13), D usability/global/accessibility (9), E agent parity (4), F performance/dependency hygiene (12), G static/installed/offline (21), H forward system-profile non-regression (8, "architecture fixture"), I Type/Data-ABI boundary (10, "design-only prerequisite"), J direct-App non-regression (5).
- **Definition of done** (§Honest definition of done): "The MVP itself is done only when all required acceptance fixtures pass from reproducible exact sources, measured performance reports are attached, protocol/profile labels match demonstrated conformance, and independent reviewers reproduce both the cold guest link and official write journeys." It does not say which sections are "required".
- Roadmap (`product-constitution-and-roadmap.md` §Staged roadmap): Slice A guest fixture → Slice B `New folder` on "one same-Realm, single-Principal development fixture" starting with an empty directory → Slice C `New file`/`Publish revision` "after one explicit content carrier, Locator, commitment, cleanup boundary, and verified read-back profile passes" → "This slice, together with A and B, is the MVP floor."

## 5. Q3 — Are the budgets measurable? Is the guidance gate reasonable?

**Budgets.** Half are measurable now, half are not:
- Measurable, device-independent: ingress ≤15 KiB, executable ≤250/400 KiB, viewer ≤1.2 MiB, ≤2 waterfalls, exactly 0 unrequested bytes/requests (`mvp-and-acceptance.md` §Provisional performance budgets rows 1–3, 8–9). These can gate CI from day one.
- Not measurable as written: every time budget names "the reference mid-tier device" which is nowhere defined; the doc itself says "The first experiment must select the normative device/browser/route/source matrix and replace these numbers. Until then, a missing measurement fails the evidence gate" — a gate that cannot pass until an unassigned selection is made. The selection is an open question in three places (`README.md` §Open questions box 1 "on an agreed mid-tier phone, desktop, static host, IPFS gateway, and qualifying Realm fixture"; `product-constitution-and-roadmap.md` §Open questions last box; `mvp-and-acceptance.md` §Open questions box 6) with no owner. The source envelope's "each fixed Realm/RPC response TTFB ≤600 ms" and "one directory page" presume a deployed Core and a page ABI that do not exist (§3.2).
- Also the "host fixture": acceptance G box 1 names "ordinary static host, qualifying stable IPFS/DNSLink origin, CID-subdomain, local loopback"; the budgets say "static-host response included" — but no concrete host/gateway is fixed, so cold-frame numbers are not reproducible across runs.

**Guidance gate.** `README.md` §Mandatory modern-Web guidance gate + direction 24 + WCOS-R65 + `technology-foundation.md` §Required contribution trace (six steps per change, independent reviewer) + §Reproducible repository boundary (guidance lock, standards-evidence lock/closure, feature-policy ledger, browser-profile ledger, evidence receipts, CI `verify:web-evidence` that requires "either a receipt or explicit `NO_WEB_SURFACE_CHANGE` for every changed Web-surface path"). `README.md` §Current work sequence step 2 requires all of this "Before any authorized Web experiment or implementation", and only "Protocol-only work is exempt". The motivating risk (README: coding models "can lag newly Baseline web-platform features") is real but small relative to the MVP's actual risks (no Core, no carrier, no SDK). For a disposable bring-up fixture this is process overhead that would front-load weeks of ledger/lock infrastructure before the first byte of guest-read code. Judgement: **DIRECTION over-scoped for the first build**; keep it as the product-code gate, exempt disposable experiments/fixtures explicitly. Secondary defect: the Paul Irish `modern-css` reference has no resolved redistribution licence (README lines 279–283) yet is a named consultation input.
