# R15 — EFS 1.5 historical EAS-bridge evidence and the v2→1.5 deep dive

**Lane:** R15-efs15-evidence · **Reviewer date:** 2026-09-02 · **Vault:** the planning vault (read-only)

## Headline

`Designs/efs15/` and the 2026-08-07 v2→1.5 review corpus are a one-day contraction exercise (2026-08-07) that James superseded the next day (`Decisions.md` 2026-08-08; `Designs/efsv2/owner-rulings.md` §2026-08-12). All three efs15 files carry explicit supersession banners and `#status/superseded`/`#status/reference`; the two Reviews files are history-by-design (`Reviews/README.md` line 3: "point-in-time outputs — reference them as history"). The set is internally consistent (byte counts, word counts, and bounds check out) and is the vault's most concrete mechanism-level evidence for identity, typed schemas, admission, receipt folding, and honest reads. Its requirement-level content was carried into `Designs/efsv2/system-constitution.md` almost entirely; its mechanism-level lessons (the two-fold state machine, the three-level idempotency fold, the bounded-module discipline, the golden/failure vector categories) were carried nowhere — the Stage A carry-in register has zero efs15 imports. The only live document still treating a v1-bridge mechanism as current is `Designs/sdk-v1-bridge-v2-compat-asks.md` (`#status/review`, asks v2 to commit a v1→v2 identity mapping), which the retirement scanner cannot see because its phrases do not match any cleared row.

## Q4 — What in `efs-id-1-candidate.md` is reusable evidence for Stage B, and what must not be reused

**Reusable (mechanism-agnostic evidence, no bytes):**
1. The **golden/failure suite categories** (§"Required golden and failure suite", ~40 bullets): pairwise domain distinctness; root/`/Arcade`/`/Arcade/`/case/repeated-separator; URL encoded-slash/percent/double-decoding rejection; two full-width principals sharing the low 160 bits derive different IDs; zero-salt reject; ID invariance under chain/schema/resolver/time/receipt; descriptor byte-exactness, name-word padding, version endianness, reserved-name rejection; `W64` overflow; `int256.min/max` two's-complement parity; role-transplant distinctness; raw receipt UID disguised as target rejects; receipt aggregation across retries; PIN A→B→A and TAG 1→2→1; delayed-retry rejection; no resurrection; expired head no fallback; parent-first batch success vs shuffled failure vs full rollback; enumerable-state reconstruction equals point and enumeration views; two-language differential fuzz; successor-domain coexistence. Stage A `vectors-and-falsifiers.md` (GV-1..18, 14 CF) does not cite this list; it should be diffed against it.
2. The **two-fold state machine** (§"Receipt aggregation and slot resolution"): aggregation by identity vs resolution by stored realm-local `admissionOrdinal`; `SlotState = {slotRevision, headSemanticEdgeId, activationOrdinal, canonicalReceiptRef, createdFromSlotRevision}`; the three-branch `expectedSlotRevision` fold (new activation / idempotent duplicate / stale-conflict fail); "at most one state-changing activation per SlotId" per write plan; only the canonical receipt is the liveness witness. This is the only worked CAS/no-resurrection state machine in the vault and maps directly onto `core-architecture-candidate.md` line 449's open checkbox.
3. The **three-level idempotency fold** ("RecordVersion, binding-record pair, then receipts — is the at-least-once boundary"): module side effects run once per `(BindingVersionId, RecordVersionId)`, indexes once per RecordVersion, receipts attach provenance only; `BindingRecordEvidence` vs `ReceiptEvidence` so a duplicate never appears "evaluated at a later block".
4. The **bounded-module discipline**: `staticcall` validator vs guarded stateful policy; fixed gas cap; fixed 32-byte assembly return buffer with `returndatasize() == 32`; magic-word acceptance; codehash recheck on every admission; and the honest limit "codehash proves only the directly called contract's outer runtime … `validatorValid` is an admission result at the recorded realm/block basis, not timeless portable validity."
5. **Acyclic identity layering**: ShapeId covers codec + ordered field name/type only; TypeId adds publisher/name/version/shape/reference declarations; FieldRoleId derived only after TypeId (prevents the cycle); reserved-alias name rejection.
6. The **name-grammar rejection vectors** and URL-adapter rules (§"Canonical shared-name/path candidate") — still valid tests for the `FILES_ROUTER_ASCII_NAME_V1` arm in `hierarchical-files-and-folders.md` §2.1.
7. **Dynamic-payload pre-decode bounds** (TAGDEF 160–192 bytes before `abi.decode`) as a generic hostile-input lesson.
8. Arcade GameProject/GameRelease/ArtifactManifest separation and "no objectively global canonical GameId" (§"Exact typed record/version identity", §"Content and artifact separation").

**Must not be reused (changed preimages / dead carrier):**
- Every printable domain string in §"Candidate constants" (`efs.id.tagdef.v1` … `efs.binding.profile.record-nonrevocable.eas-abi1.v1`, `efs.claimrole.*`, `efs.objectkind.*`, `efs.state.binding-record.v1`) and every smoke vector in §"Provisional smoke vectors" (e.g. `ROOT_TAGDEF_ID 0x431596ef…`, `TagDefId("/Arcade/") 0xae27eb48…`, `DataId 0x71fcaec6…`, `TypeId 0xdd9fca83…`). `efs15/README.md` rule 2 is explicit; the 2.0 preimages differ (no `easAttester`-derived principal, no EAS origin words, different word lists), so the same strings would mean two layouts — the exact hazard the candidate itself flags ("the same `*.v1` domain may never mean two layouts", §Standing).
