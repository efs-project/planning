## 0. Headline

The Type layer of EFS 2.0 currently exists as **two proposals on two different arms** plus one product adapter that tries to stay arm-neutral. `Designs/efsv2/layered-type-system-and-data-abi.md` (2026-08-14, zero reviews recorded) is the README's declared "current Type-system proposal" and argues for Architecture C (SemanticSpec + LogicalShape + Representation + Views + separate QueryProfiles). `Designs/efsv2/hierarchical-files-and-folders.md` (2026-08-14, three reviews) — the document the write-capable File Browser MVP is built on — is written entirely against the Stage A **B0 bundled arm** (`TypeSchemaId`, MC/1, `KIND_BINDING_SCOPE` "to a successor B0 Codex") and never mentions the layered proposal. The owner has explicitly **not** chosen an arm (`owner-rulings.md` 2026-08-12 "50-year bakeoff question"; `web-client-os/README.md` direction 12 "latest owner response was not interpretable"). The 2026-07-15 on-chain rulings are faithfully carried by `system-constitution.md` and by the Stage A B0 index chapter, but not by the layered proposal, and their cost has never been measured: no gas snapshot exists, no EFS 2.0 code exists, and EIP-8037's ~4.9× storage repricing is acknowledged only inside the 2026-08-13 evidence-round corpus, never in `Designs/`. The July codex/ID/handoff docs are correctly demoted by the README evidence map but still self-describe as "Etched" / "authoritative" / "frozen" with no superseded banner, and one `#status/review` SDK doc still asks v2 for v1→v2 identity mapping after the 2026-08-08 no-compatibility ruling.

Maturity of this set: **draft-unreviewed** for the Type proposal; **draft-reviewed** for Files; **historical-evidence** for everything July.

## 2. Lane question 1 — what exactly is the current Type-system proposal, and what does it leave open?

### 2.1 The layered exact Type / Data ABI (Architecture C), as written

Source: `Designs/efsv2/layered-type-system-and-data-abi.md`.

- **Identity layers** (§"Recommended layered model", lines 233–426): `SemanticSpecId = H(DOM_SEMANTIC_SPEC, specCodecVersion, qualificationMode, optionalQualifier, normativeSpecClosureHash)` (240–265); `LogicalShapeId = H(DOM_LOGICAL_SHAPE, shapeCodecVersion, canonicalShapeBytes)` with permanent numeric field/variant keys (266–285); `RepresentationId = H(DOM_REPRESENTATION, …, LogicalShapeId, canonicalRepresentationBytes)` (286–304); `ViewRevision`/`ViewBinding` (305–340); `TypeRevisionId = H(DOM_TYPE_REVISION, typeCodecVersion, SemanticSpecId, LogicalShapeId, RepresentationId, intrinsicConstraintBytes, typedReferenceRoleBytes, canonicalViewBindingBytes)` (341–376); `RecordId = H(DOM_RECORD, TypeRevisionId, H(canonicalBody))` (377–385); `QueryProfileId = H(DOM_QUERY_PROFILE, queryCodecVersion, TypeRevisionId, canonicalIndexSpecs)` (386–405); experimental `ViewQueryProfileId` (406–426).
- **Views** are "a small, nominal, immutable contract-facing interface… closer to a WIT interface or a precisely specified ERC" (307–309). ViewBinding v1 has "no arithmetic, string parsing, numeric coercion, branching, dereferencing, callbacks, recursive mapping search, or composition" (331–335).
- **Aliases**: Files paths/catalogs are "a catalog and namespace layer… a path must not be the Type's canonical identity" (705–769); `/types` is "a useful client projection, not a reserved Files prefix" (761–764).
- **Contract consumption modes** (443–489): `EXACT`, `PINNED_VIEW_SET`, `SEMANTIC_VIEW` ("the principal immutable-hyperstructure extension seam", 464), `LENS_CURATED_VIEW`.
- **Validation grades** (428–441): well-formed, Type-valid, View-projectable, Realm-admitted, currently effective, endorsed — "Only the first three can be portable structural results."
- **Compatibility algebra** (518–549) and **evolution table** (551–569).
- **Physical EVM arms** (940–1000): M monolith, D immutable Diamond/facet router, C narrow state-owning contracts; all modular arms need `ExecutionManifestId`s (992–1000).

### 2.2 Experiment targets versus recommendations

The document is explicit about which is which:

- **Recommendation**: "use C as the written Stage B comparison target while retaining A as the control. Reject C if the View or profile machinery cannot be kept small…" (§"C — layered exact Type plus bounded Views — recommended", 215–217). B is "reject as the canonical identity model" (192–193); D is "Reject for Core execution" (230–231).
- **Experiment targets, not adopted**: every formula ("define conceptual separation, not final bytes or names", 235–236); ViewQueryProfile ("This is an experiment arm, not a pre-adopted Core index or final identity", 425–426); the responsibility-boundary table ("the table is not an adoption of every candidate mechanism", 928–930); the physical arms (T5); in-Type vs detached View bindings (T2/T3, 367–372); representation arm (T1/T2); raw Type enumerability (T4/T6/T9); sealed carrier (T7). "No result may set `protocolConformance=true`" (1104).
- **Open questions** (1291–1317): nine, each mapped to T-experiments; "None of these is an immediate owner decision."
- **Authority**: "It does **not** adopt protocol bytes… or close V2-E4, V2-E8, or V2-F1" (43–44). README line 79–80: "It is a review/experiment target, not an adopted Type system or frozen byte format."

### 2.3 What it leaves open (beyond its own list)

1. **The name of the central object.** The README (lines 71–72) says "`TypeSchema` is the current plain-language name; older files call similar concepts `TypeRevision`", and `core-architecture-candidate.md` line 68 introduces `TypeSchema` as the "Working replacement for the confusing name `TypeRevision`". The layered proposal (newer, 2026-08-14) uses `TypeRevisionId` as its exact-Type identifier throughout (lines 200, 344, 380, 392, 450, 774, 1006) and the web-client-os packet propagates `EfsTypeRevision`/`TypeRevisionId` (`type-data-abi-boundary-pressure.md` lines 81, 491). `hierarchical-files-and-folders.md` uses `TypeSchemaId` (lines 369, 603, 1814). See F1.
2. **QueryProfile grammar.** `canonicalIndexSpecs` (line 393) is never enumerated. The only closed grammar in the vault is B0's `IndexSpec{indexKind ∈ {SCALAR_EQ, REF_BACKLINK, DIGEST_EQ}, target}` with `MAX_INDEX_SPECS = 8` (`Reviews/2026-08-13-efs2-stage-a-corpus/chapters/b0-indexes.md` lines 1052–1055).
3. **Realm activation of a QueryProfile** ("A Realm activates a bounded profile with explicit start, backfill, active/pending generation, coverage, and basis", 397–399) — no ABI, no authority (who may activate; whether the Type author, a Realm operator, or anyone), no cost model.
4. **Type publication operation.** "Registration verifies that each mapped field exists…" (331) and "Permissionless Type publication" (Goal 7, 62–63) — but the document never says through which Core operation a Type/View/QueryProfile enters a Realm. Stage A answers this for B0 (SR-17: "TypeSchemas enter state as Records of the bootstrap meta-Type through ordinary admission", `b0-overview.md` lines 468–480), which is not adopted into `Designs/`.
5. **The on-chain obligations** (revocation-aware counts, digest lookup, author enumeration, spine/no-elision) — absent from the layered doc entirely; grep for `revocation|current count|contentHash|digest lookup|author enumeration` returns nothing relevant (only lines 188, 497, 591, 663, 883, 1216 in other senses). See F4.
