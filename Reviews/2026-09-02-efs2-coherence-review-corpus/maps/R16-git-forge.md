### Q3 — Does the ref-transaction fold require a Core primitive the candidate lacks? Is the gap acknowledged?

The fold requires: (i) a global admission order at one venue (B0 has it: Realm `admissionOrdinal`); (ii) *no* CAS at admission (B0 does the opposite); (iii) a first-authoritative-admission/one-shot rule with primary vs supplemental receipts (B0 has nonce-domain replay rejection instead — `b0-authorship-envelope.md` §2 and FX-GIT adversarial (i) "replayed push intent … MUST-FAIL nonce/consumption", `harness-and-fixtures.md` line 826); (iv) cross-author enumeration indexes over a shared key (B0 has typed backlink/Type indexes; per-ref Binding keys are per-Principal, `harness-and-fixtures.md` line 798); (v) a lens-family typed read profile (not inherited).

So the fold does not need a primitive B0 *lacks*; rather, B0 already supplies **admission-time** atomic multi-ref CAS: "The Git push semantic unit — its `GitPushTransaction/1` Record plus the declared ref-head Binding updates — is `MUST_FIT_ATOMIC`… It is never retried as separate ref updates" (`harness-and-fixtures.md` lines 842–845); races → `ErrCasPredecessor` whole-call revert (`b0-binding.md` §3.5). The July concern that "admission confluence forbids state-dependent rejection" is simply gone from the constitution: "Mutable state uses explicit predecessor/CAS rules where races matter" (`system-constitution.md` lines 153–156) and "Git multi-ref and similar all-or-nothing meaning lives in one typed transaction Record or an explicit bounded profile rule" (lines 160–162).

What B0's design does **not** yet cover from the corpus's replay analysis: the relayer-subset case (`txnRoot`/`refCount` → `TRUNCATED-TXN`) is addressed by B0's all-or-revert + `leafMask` subset admission semantics only if a Git push unit is never subset-admissible — `MUST_FIT_ATOMIC` asserts that, but the "late first admission of a stale signed envelope" case (`state-model.md` §4 replay (b)) maps onto `expectedRevision` mismatch + `notAfter` expiry; the ABA case maps onto `predecessor OCCREF` + monotone revision (`b0-binding.md` lines 559–563: "Revisions only increment"). ### Q6 — Does the wiki-first workload conflict/overlap with the write-capable File Browser MVP?

**Overlap, substantially.** The File Browser MVP is "creating folders, creating files from local bytes, and publishing a new immutable revision of a controlled file" (`Designs/web-client-os/mvp-and-acceptance.md` lines 15–19) via `Publish revision = ChunkTree + FileRevision + file-head CAS rebind` (lines 238–243); `hierarchical-files-and-folders.md` §3.3 `FileRevision/1` carries `parents array(max=8)` — "one is an ordinary edit; two through eight represent a merge" (lines 446–462) — i.e. Files already has a revision DAG with merges, immutable revisions, per-name Bindings (rename-stable identity), and Binding history. The wiki verbs (`wiki-and-collab.md` §1) map: Publish → FileRevision + head CAS; History → Binding history / `parents` walk; Restore → a new FileRevision with old content (matches B0 "no resurrection", `b0-binding.md` §3.4); page identity across renames → stable File Object + per-name Binding (which is why `hierarchical-files-and-folders.md` line 9 explicitly *supersedes* "redirect/moved-to", i.e. corpus P-G6). Trace T1 (trusted maintainer publishes one page) and T4 (one atomic multi-page edit) are expressible as one `MUST_FIT_ATOMIC` envelope of Binding leaves without Git.

What Files/MVP lacks that the wiki asks for: Propose (proposal objects), Compare (diff UI), edit summaries (FileRevision/1 has no note field; Stage A's `WikiPageRev/1` does), 3-way merge conflict UI, offline batching — and the MVP defers exactly "collaboration, conflict merge, and a rich document editor" (`mvp-and-acceptance.md` lines 86–87). What Git-native uniquely adds: stock `git clone/fetch` interop and packfile delta efficiency — neither is a wiki reader/editor need.

**One slice can serve both**: a Markdown file in the write-capable File Browser with History/Compare/Restore over `FileRevision/1` is the wiki's T1/T4/T8 with zero Git machinery, and it is the EFS-native arm of the fork `@git-forge` was to decide. The Git-native profile then becomes a separate interop workload (FX-GIT / `CV-GIT-STOCK`) rather than the product's revision engine. Doing both as two different revision engines for the same Markdown file is the conflict; it is exactly what Stage A's FX-GIT currently does (Git objects *and* `WikiPageRev/1` chains for the same page bytes, `harness-and-fixtures.md` lines 796–799). → F3, F6, F7.
