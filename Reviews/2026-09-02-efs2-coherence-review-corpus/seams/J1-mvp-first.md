# J1 — MVP-first engineering lead: can two or three engineers ship a write-capable File Browser on Sepolia from this design surface?

Judge: J1-mvp-first · Date: 2026-09-02 · Vault the planning vault read-only. Inputs: all 22 Phase 1 reader maps (R1–R20 incl. R7a/b, R11a/b) and the core documents named in the task, read directly. Where I re-checked a citation myself it is marked **(verified)**; everything else cites the map that verified it.

## 0. The one-paragraph answer

The direction is right and the algebra is buildable. Record ≠ Occurrence ≠ Admission ≠ Binding ≠ Plan, a standalone Core per EVM Realm, a guest-first File Browser that promotes into basic writes, honest `UNKNOWN` — a small team can implement that on Sepolia behind adapters starting this month. What stops them is not the design's soundness; it is that the surface *reserves seams instead of choosing* on the six things a write-capable File Browser needs (complete listing, write ceremony, byte carrier, Principal shape, Type vocabulary, three unminted constants), piles an OS-scale acceptance list onto a three-operation product, and has no process bucket for the one decision that would start work. Nobody has written the sentence "build the B0 arm only, in this repo, against this Realm, with these labels". Until someone does, the 9-cell bakeoff, the layered Type arm, the FilesRouter, the KEL seam and the modern-Web guidance gate will keep absorbing the engineering attention the MVP needs. Verdict: **mostly-right-but-overscoped**.

## 1. Is the direction right? Which parts.

**Right, and I would build on it today (with the caveats in §4):**

- *Standalone Core in one EVM Realm; Commons optional; guest reader first.* `Designs/efsv2/owner-rulings.md` §2026-08-12 ("A Realm or fresh L3 must be useful to contracts and direct clients without Commons, a canonical EFS chain, or EFS OS"; "A direct guest File Browser path is required") **(verified)**. This is the right shape for a small team: one contract deployment, one static site, no service.
- *The five-way separation and the one write entrypoint.* `Designs/efsv2/core-architecture-candidate.md` §"Candidate in one picture" (`RecordId` / `OccurrenceRef` / `Admission` / `Binding head` / `Lens result`) **(verified)**; Stage A SR-12 `publish(envelopeBytes, principal, intentBytes, intentWitness)` as the sole Core write entrypoint (`Reviews/2026-08-13-efs2-stage-a-corpus/chapters/b0-overview.md` SR-12) **(verified)**. R7a §3 checked every cross-chapter ID preimage and found one consistent object model. That is enough to code against.
- *The Files object shape.* `ObjectGenesis/1` + charter Binding, `DirectoryEntry/1`/`DirectoryWhiteout/1` as Binding targets, `FileRevision/1` + `ChunkTree/1` with a file-head Binding (`Designs/efsv2/hierarchical-files-and-folders.md` §3, §4.1, §8.1; R3 §11 "solid now"). The MVP's three operations map onto these exactly (`Designs/web-client-os/mvp-and-acceptance.md` §"Operation sequence", the `Create directory / Create file / Publish revision` units) **(verified)**.
- *The write-capable MVP itself.* Owner direction 2 (`Designs/web-client-os/README.md` §Direct owner direction item 2) **(verified)** is the correct call for a team that must "debug the evolving contracts": a read-only product would give the Core no pressure. The `EXPERIMENTAL_DIRECT_CORE / protocolConformance=false / filesPreconditionCertified=false` labelling discipline (`mvp-and-acceptance.md` §"Operation sequence") **(verified)** is exactly how a disposable first build should be honest.
- *The result law.* `ResourceOutcome<T>` / `ByteOutcome` / `PlanOutcome` and the client outcome words `NO_TRANSPORT … UNKNOWN … ABSENT` (`mvp-and-acceptance.md` §Invariants item 6; R10 §3 "genuinely arm-neutral") — this is the most reusable thing the client set produced and it depends on no open bakeoff.

**Right in intent, wrong in execution (the over-scoping):**

- The Files draft, the Type draft, the Stage A corpus and the web-client-os set each keep both arms of every fork alive "for the bakeoff" (`core-architecture-candidate.md` §"Alternatives in the bakeoff", eight rows; `bakeoff-spec.md` 9 cells; `layered-type-system-and-data-abi.md` T1–T9; `hierarchical-files-and-folders.md` "experiment arms" banner). For a freeze that is fine; for an MVP it is the enemy. R6 §5 shows four of nine bakeoff cells answer questions no owner gate asks, and the two gates that matter for a product (V2-E2 Lens, V2-E5 Realm) are not cells at all.
- `mvp-and-acceptance.md` is 930 lines of which the write path is ~80 (R11b F14); sections G8–21, H, I, J are Service-Worker generations, a thousand-module profile, a Wasm/WIT worker and a Type-evolution matrix. "The MVP itself is done only when all required acceptance fixtures pass" (`mvp-and-acceptance.md` §"Honest definition of done") **(verified)** never says which sections are required.
- The modern-Web guidance gate (`Designs/web-client-os/README.md` §"Mandatory modern-Web guidance gate"; §"Current work sequence" step 2 "Before any authorized Web experiment or implementation…") **(verified)** front-loads a ledger schema and CI gate before the first line of guest-read code. Direction 24 is one sentence; the elaboration is agent-authored (R10 F7).

**Wrong, and I would refuse to read it on the MVP path:** the 9-cell bakeoff beyond B0; the layered Type arm's Views/QueryProfile/ViewQueryProfile machinery; `VerifierVM/1` (R7a F17); the FilesRouter/`RoutedAdmissionIntent` certification lane; the three-host mount adapters; the Arcade product framing; the Git-backed wiki; the App Store's 1,034-line architecture; the Media set. All of these are correctly labelled "not MVP" somewhere in their own docs; none of them is fenced off in the one place an engineer starts.

## 4. What is solid enough to build on now

Behind adapters, as disposable code labelled `protocolConformance=false`:

- **IDs and codec.** SR-1 domain discipline, the closed `DOM_*` table, `RecordId = H(dom, typeSchemaId, keccak256(body))`, `PositionKey`/`BindingKey`, `PrincipalId` (`b0-encoding-and-ids.md` §1, §4; R7a §13 "solid"). MC/1 packed codec + `validateBody` (R7a).
- **Envelope + intent.** `PublicationEnvelope/1` fields, chain-free EIP-712 digest, `EnvelopeId`; `AdmissionIntent/1` digest with `expectedRevisions[]` and 2-D nonce lanes (`b0-authorship-envelope.md` §2, §5; R7a).
- **Binding state machine.** T1–T9, CAS pair, no-resurrection via the `OccStatus` overlay, tombstone-never-revert (`b0-binding.md` §3–§6; R7b §10). This is the only worked CAS machine in the vault that survives the reset; the efs15 `SlotState` fold is its precedent (R15 §Q4).
- **Point resolution.** `ResolutionPlan/1` frame, `EXACT | PRIORITY_FIRST_PRESENT | THRESHOLD(k)`, risk-bearer view/state ABI split, `LENS-NEG-1` (`b0-lens.md` §3, §6–§8). 64 direct probes ≈ 0.55M gas cold — well under 1% of the EIP-7825 cap (R20 §4). A 1-Principal Plan is all the MVP needs.
- **Files shape.** `ObjectGenesis` meanings, `DirectoryEntry`/`FileRevision`/`ChunkTree`, `FilesName/1` grammar and the URL serializer/parser as pure client code, the result registry and `UNKNOWN ≠ ENOENT` (`hierarchical-files-and-folders.md` §2.1–2.3, §3, §4.2, §9; R3 §11).
- **Exact bytes.** `ChunkTree/1` + `verifyChunk`, `ByteDigest/1`, `Locator/1`, the no-blob-custody posture (`b0-content-locators.md` §1, §3–§5; R7b §10).
- **Client laws.** `BootRoute` split and `GuestRead → FilesWrite` promotion; Reader Kernel package boundaries; "no guest-critical module imports an explicit-phase module"; the `ResourceOutcome` law; zero-wallet-on-guest fixtures A1–A3; the `EXPERIMENTAL_DIRECT_CORE` triple label; device-independent byte budgets (R8 §12, R9 §12, R10 §11).
- **Rulings that are attributed, dated and unambiguous.** 2026-08-08 greenfield; 2026-08-12 boundary; 2026-07-15 items 12/17/18 (mandatory indexing, full-body spine, no elision); 2026-07-22 three-host mount as a *later* gate (R19 §12).
