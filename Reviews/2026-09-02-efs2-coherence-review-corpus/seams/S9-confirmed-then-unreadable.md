# S9 — "Confirmed, then unreadable" and the "chains don't die" ruling, tested against the design

**Lane:** S9-confirmed-then-unreadable · **Reviewer date:** 2026-09-02 · **Vault:** the planning vault (read-only)
**Seam:** the evidence round's cross-domain failure class (`Reviews/2026-08-13-claude-evidence-round/README.md` §Cross-domain signal) × the 2026-07-10 owner ruling (`Designs/efsv2/owner-rulings.md` §2026-07-10) × the 2026-08-12 constitution's reconstruction promise (`Designs/efsv2/system-constitution.md` §Honest reads and reconstruction) × the Sepolia MVP (`Designs/web-client-os/mvp-and-acceptance.md`).
**Verdict:** **strained.** The vocabulary is right and shared (`UNKNOWN` is never absence; honest completeness; Locators are claims, not custody). What is not there is the thing the evidence round said to test: "an independent implementation can reconstruct useful state and exact content **from the dependencies each Realm explicitly promises**" (evidence README §Cross-domain signal, lines 75–77). The design promises reconstruction "from the declared Realm state and byte carriers" (constitution lines 214–216) but *declares* only those two of the eight dependencies a reader actually needs a year after a Sepolia write; the first venue is a testnet whose deprecation path is designed nowhere; and the one ruling that would make the assumption honest per Realm (Stage A spine-edit A2) is unadopted.

Maps read first: R18, R1, R7a, R7b, R3, R8, R19. Every claim below was re-checked against the source file named; "inference" is marked.

## 1. The failure shape, defined from the evidence

The round's own definition (`Reviews/2026-08-13-claude-evidence-round/README.md` lines 59–61): "bytes, chain state, or commitments survived while normal discovery, reconstruction, RPC, explorer, index, or runtime paths failed." **Precise definition for this lane.** A write is *confirmed* when its transaction is included and its commitment (RecordId / receipt / versioned hash) is verifiable from chain data. It is *unreadable* when a reader who holds the exact link cannot obtain a `FOUND`/verified-bytes result because one link in the reader's dependency chain has failed *and that link was never recorded as a declared dependency with a reconstruction path*: (a) a queryable endpoint for the Realm at a usable basis, (b) the Realm's live state (as opposed to history), (c) the descriptor that names the Realm, (d) the spec/ABI/Type semantics that give state bytes meaning, (e) an index that makes the item discoverable without already knowing its key, (f) the byte carrier, (g) an executable client. The evidence shows each of (a)–(g) failing on its own while the commitment survives. The design's job is therefore not "assume none fail" (the 2026-07-10 posture) and not "hedge everything" (the July posture) but *declare which of (a)–(g) each Realm/Record promises, and test reconstruction with the rest disabled*.

## 3. The 2026-07-10 ruling versus the 2026-08-12 constitution

**Are they consistent?** Yes — but only because both assume the Realm lives. The ruling: "assume a blockchain persists indefinitely and stays queryable … DROP … any 'graded/UNKNOWN after the home chain is gone' language … NET effect: 'home-chain-authoritative + home chain always queryable'" (`owner-rulings.md` lines 11–16). The constitution: "A second implementation can reconstruct … from the declared Realm state and byte carriers without an EFS-operated service" (lines 214–216) and the "Independent rebuild" trace (line 306) "reconstruct from Realm state plus declared byte carriers". Reconstruction *from the Realm's own state* is only possible while that state is queryable; the constitution therefore relies on the ruling rather than hedging it. Stage A says so: QR-1 "extends the 2026-07-10 owner ruling … from the home-chain frame to a per-Realm qualifying assumption" (`b0-realm-admission.md` lines 383–387) and §8.2 "this walk reconstructs state at the basis the RPC serves … Reconstructing a *past* snapshot needs archive state — a bonus … never claimed" (lines 1821–1824).

The inconsistency is between the ruling's **premise** and the 2026-08-12 **scope**: the ruling's payoff was a single always-queryable *home chain* (line 16); 2026-08-12 removes any home chain ("does not … revive a global home chain", line 187) and makes "a qualifying EVM Realm" — any fresh L3 — the unit. The ruling was never re-scoped; the spine is silent (grep `persist|queryable|dies|dead-chain` over `system-constitution.md`/`core-architecture-candidate.md`: 0). Stage A's A2 proposes the re-scope and says it is "the sole owner-routed scope proposal; Stage A does not ask for adoption now" (`proposed-spine-edits.md` lines 166–168).

**Does the evidence round undermine the ruling?** For the Realm class the design advertises, yes. `commons-realm-venue-matrix.md` §1 item 7 (line 36): "The 'chains don't die' ruling (2026-07-10) is safe for L1, arguable for the top L2s, and empirically false for L3s"; §6 Q3 (line 167): "retained, scoped, or retired? … A scoped version — 'assume L1 and top-tier L2s persist; treat L3s as mortal'". `CORRECTIONS.md` line 19 qualifies the L3 mortality *rate* ("archived is not synonymous with dead"), not the picture. The July A-1 row already wrote the reopen condition: "A chosen venue loses independent queryability, affordable inclusion, or reliable state" (`assumptions-and-requirements.md` line 244; the file is bannered pre-greenfield evidence, lines 10–15) — Goerli and Holesky meet it (`l1-incidents-and-dead-data.md` §B6). The evidence README routes the question to V2-E5/V2-E7 (lines 210–212); those gate texts (`owner-decision-inbox.md` lines 47–68, reconciled 2026-08-12) do not mention the assumption.

**Is the ruling still cited as in force?** Yes, in five places outside the silent spine:
- `Designs/efsv2/owner-rulings.md` §2026-07-10 — unretired; `Retirements.md` has no row (per R19 §3).
- `Reviews/2026-08-13-efs2-stage-a-corpus/chapters/b0-content-locators.md` lines 1113–1114: "a qualifying Realm is assumed persistent and queryable [OWNER RULING — chains-don't-die, owner-rulings 2026-07-10, VERIFIED …]".
- `…/chapters/b0-realm-admission.md` lines 383–387 (QR-1) and `…/chapters/traceability.md` lines 432–433 ("OR-1 carries the historical chains-don't-die DROP/KEEP ruling while leaving its per-Realm extension explicitly unadopted as A2").
- `Reviews/2026-08-07-efs-git-corpus/requirements-ledger.md` line 11: "A-1 | Chains persist and stay queryable | owner-rulings 2026-07-10 | no dead-chain machinery in the Git profile; authority reads are definite".
- `Reviews/2026-07-29-virtual-os-museum-deep-dive.md` line 48 uses the "chains-don't-die ruling" as an EFS *survivability differentiator* — the opposite of what the evidence supports for testnets/L3s.
Historical (bannered) carriers: `Designs/efsv2/human-overview.md` line 390; `assumptions-and-requirements.md` line 244.

**Is Sepolia an honest first venue for anything "durable"?** As a *development* venue, yes: it is alive (`l1-incidents-and-dead-data.md` line 172, block 11,477,826 on 2026-08-13), it is the only testnet with era1 + beacon archives in the community registry (lines 176–177), and every current doc scopes it as "first development Commons … not a permanent or canonical venue" (`Designs/efsv2/README.md` line 9; `web-client-os/README.md` lines 75–77; `product-constitution-and-roadmap.md` lines 309–311; `mvp-and-acceptance.md` lines 862–866). For anything labelled durable, no: the testnet cadence is Ropsten (2022) → Goerli (EOL 2024, explorer 522, 0/8 RPCs) → Holesky (announced 2025-09-01, frozen ~2026-06-03, one endpoint) (§B6 table lines 137–143, 149–170); "none of these announcements says anything about preserving data" (line 145); Sepolia's validator permissioning is "unresolved" (`CORRECTIONS.md` line 27); and, per Stage A's own rule, persistence is asserted by the Realm's *operator* — EFS is not Sepolia's operator. **Does the design say what happens to Sepolia data when Sepolia is deprecated?** No — see F3.
