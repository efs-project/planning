## 0. Verdict: STRAINED

The seam is not broken because the constitution and Stage A B0 *do* supply one coherent mechanism for the constitution's Git trace — `GitPushTransaction/1` + per-ref Binding CAS in one `MUST_FIT_ATOMIC` envelope — and the 2026-08-07 forge-expressibility obligation *is* honoured at specification level by Stage A's FX-GIT. It is strained because (a) the entire Git corpus is written against a superseded kernel and nothing marks it so; (b) the corpus's `GIT-REF/1` fold and B0's admission CAS are two different mechanisms that never cite each other; (c) B0's Binding is Principal-scoped, so the Stage A fixture's two-contributor race is impossible under B0's own key formula and the multi-maintainer canonical head — the exact problem the fold existed to solve — is unaddressed; (d) the same Markdown page has three revision models (Git-native BLOB, `WikiPageRev/1`, `FileRevision/1`) in three documents that never cross-reference; (e) the owner packet GD-1…GD-5 vanished with no disposition; and (f) no `Designs/git-forge/` exists while three neighbour sets and Stage A delegate to it. For the *MVP* (single-Principal write-capable File Browser) the seam holds. For the flagship git-forge workload it does not yet.

## 2. Q2 — Same mechanism or two?

**Two different mechanisms, and B0's is the one the constitution already prefers.**

- Corpus: "Git's compare-and-swap… **cannot be an admission rule** — and must not become one" (`state-model.md` §4 "The problem", line 72); "CAS as a deterministic read rule, not an admission rule" (line 101); losing transactions are "recorded-but-inapplicable: permanently visible evidence, never silently discarded" (101); atomicity via `txnRoot`/`refCount` completeness as an *applicability precondition* (99); ordering via P-1 ordinals at one `authorityHome` (100).
- Constitution: "Mutable state uses explicit predecessor/CAS rules where races matter" (`system-constitution.md` 153–156); "Git multi-ref and similar all-or-nothing meaning lives in one typed transaction Record or an explicit bounded profile rule" (159–162).
- B0: "Realm admission applies compare-and-set against the previous admitted Binding Occurrence/head" (`core-architecture-candidate.md` 223–228); racing writers → "the other's **entire envelope admission call reverts** with `ErrCasPredecessor`" (`b0-binding.md` 561–575); a reverted attempt "normally leaves no state" (`core-architecture-candidate.md` 205–207). FX-GIT: "`GitPushTransaction/1` — ONE typed Record carrying all ref updates… = the atomic multi-ref transaction Record"; per-ref Binding at `(purpose = TypeSchemaId(GitPushTransaction/1), subject = RepoId, fieldRole = H(refName))` with `expectedRevisions[]`; the unit is `MUST_FIT_ATOMIC`, "never retried as separate ref updates" (`harness-and-fixtures.md` 797–798, 842–845). Traceability C-TX-4 and AT-9a mark this COVERED at specification level (`chapters/traceability.md` 147, 236).

Cross-citation: `GIT-REF` in the Stage A corpus = 0 hits; `B0`/`GitPushTransaction` in the git corpus = 0 hits; `GIT-REF`/"fold" in the five current efsv2 docs = 0. The only Stage A acknowledgement is generic: "Falsifier: if a fixture (Git push intake) needs author-side ordering that Binding CAS cannot express, this returns as a HYPOTHESIS revision" (`b0-authorship-envelope.md` 140–142) and open item O3 "Confirm no acceptance trace (… Git intake) needs third-party authoritative admission" (1809–1812).

**Does B0 supply ordinals and CAS heads sufficient for either?**
- For B0's own mechanism, for a **single-Principal repo**: yes at spec level (ordinal §5.3; `expectedRevisions[]` REQUIRED per Binding leaf, `b0-binding.md` 362–365; whole-call revert §3.5; `MUST_FIT_ATOMIC`).
- For a **multi-maintainer repo**: no. `BindingKey = keccak256(abi.encode(DOM_BINDING, principalId, positionKey))` (`b0-binding.md` 52); "writers cannot bind another's key" (§1.3, 135–144); "only the key owner's admitted envelopes can touch the slot" (799–800). So maintainers M1 and M2 each get their *own* `refs/heads/main` head; nothing in FX-GIT says which is canonical or how a reader selects. The corpus's fold existed precisely for this (roster-scoped union in admission order, `state-model.md` §4 line 76). Under B0 the only bounded selector is a `ResolutionPlan` over maintainers — a read-time selection after all — and no Plan is specified for FX-GIT. Managed/shared Principals are a post-MVP graduation seam (`b0-principal-authority.md` §6). → F2.
- For the corpus's fold: B0 supplies the ordinal but forbids the fold's core premise (no CAS at admission) and has no typed read-profile extension point; the fold as written cannot be built on B0 without re-adding admission-confluence, which the constitution dropped. → F1.
- The two mechanisms also differ on what a *losing* race leaves behind: corpus "conflicted publish… fees spent; content permanently public" (`wiki-and-collab.md` 26, 30) and T7/T9 displaced-history retention vs B0 revert-leaves-no-state. Nobody has decided whether "rejected attempts are evidence" is a requirement. → F7.

## 6. Findings

**F1 — UNDECIDED · blocking for any git-forge slice, important for efsv2 · owner: git-forge with efsv2.** Two incompatible mechanisms exist for the constitution's single requirement "authenticated replay-safe push/intake, atomic multi-ref semantics" (`system-constitution.md` 311; 159–162): the corpus's `GIT-REF/1` read-time fold ("CAS as a deterministic read rule, not an admission rule", `state-model.md` §4 lines 72, 101) and Stage A B0's admission-time CAS (`core-architecture-candidate.md` 223–228; `b0-binding.md` 359–365, 561–575) with `GitPushTransaction/1` + per-ref Bindings, `MUST_FIT_ATOMIC` (`harness-and-fixtures.md` 797–798, 842–845). Neither cites the other (grep: 0 both ways); `Designs/efsv2/README.md` 109 still lists the deep dive as an evidence input; the corpus carries no greenfield banner (contrast `Designs/clientv2/README.md` 8–15, `assumptions-and-requirements.md` 10). The constitution has already chosen the B0 shape; nobody has said so to the Git corpus or listed what the fold had that B0 lacks (policy epochs, roster tiers, ADVANCE/FORCE/RESTORE, `restoreOnly`, ancestry verification, displaced-closure retention — none in B0). Fix: git-forge `application-profile.md` adopts the B0 shape as the working candidate and enumerates the fold-only properties as open application-profile work; efsv2 adds one sentence to `core-architecture-candidate.md` §Record or the Git trace naming `GitPushTransaction/1` as the candidate mechanism.

**F2 — DEFECT + UNDECIDED · important · MVP-relevant only if any multi-author Files write is in scope; blocking for git-forge · owner: efsv2 (Stage A fixture) + git-forge.** B0 Binding heads are Principal-scoped: `BindingKey = keccak256(abi.encode(DOM_BINDING, principalId, positionKey))` (`b0-binding.md` 52); "writers cannot bind another's key" (§1.3, 135–144); "only the key owner's admitted envelopes can touch the slot" (799–800); `core-architecture-candidate.md` 217–224. FX-GIT's cast is "M1, M2 (maintainers, EOA), D1..D4 (contributors: 2 EOA, 1 KEY_P256, 1 ERC-1271)" (`harness-and-fixtures.md` 785–786) and its adversarial case (ii) reads "racing pushes — D1 and D2 race one ref with the same `expectedRevision`: exactly one admits, loser gets `ErrCasPredecessor`" (823–826). Two distinct Principals cannot share a BindingKey, so this race cannot occur under B0's own formula; and nothing in FX-GIT says whose Principal owns `refs/heads/main` or how a reader selects between M1's and M2's heads. Managed/shared Principals are a post-MVP "graduation seam" (`b0-principal-authority.md` §6, 1195). The multi-maintainer canonical head — the problem the corpus's fold existed to solve (`state-model.md` §4 line 76) — is therefore unaddressed in the current model. Fix: (a) rewrite adversarial (ii) as a same-Principal two-device race (nonce-lane collision) and state that the MVP repo has one publisher Principal; and (b) specify the maintainers' `ResolutionPlan` (a bounded read-time head selection) as the multi-maintainer answer, add it to FX-GIT reads, and note honestly that this is a read-time fold in B0 clothing.

**F3 — UNDECIDED · important · MVP-relevant · owner: git-forge with efsv2 (Files) and web-client-os.** The same Markdown page has three revision models: Stage A `WikiPageRev/1` chain + BLOB `GitObject/1` for the same bytes (`harness-and-fixtures.md` 496, 796, 799); Files `FileRevision/1` with merge parents (`hierarchical-files-and-folders.md` 446–462, 1142); corpus H-3 "Git is the canonical file/version history; no second per-commit EFS history — SURVIVES" (`requirements-ledger.md` 107; `state-model.md` §3). `FileRevision` in Stage A = 0; `WikiPageRev` outside Stage A = 0; the Files doc names Stage A as a dependency (line 6) yet never reconciles. `@git-forge` claimed exactly this fork (`Kanban.md` 37) and returned nothing (`agent-status.md` 2026-08-14 entry; `scripts/stale-cards.sh`: STALE, expired 2026-08-17).
