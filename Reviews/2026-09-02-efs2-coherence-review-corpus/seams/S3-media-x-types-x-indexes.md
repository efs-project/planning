# S3 — Media Library × Type system × on-chain index budget (seam report, 2026-09-02)

Lane: S3-media-x-types-x-indexes. Read-only against the planning vault. All paths repo-relative; line numbers from `cat -n`/Read on 2026-09-02. Maps consulted: R13, R2, R7b, R1 — every claim below was re-checked against the source text; where a map overstated something I say so (§2, S3-2).

**Verdict: STRAINED, not broken — and a later lane.** Both sides are draft and honestly labelled. The media query ladder is arm-neutral in wording and its Q0–Q2 rungs ride acceptance obligations the owner has already ruled. But the two mechanisms the media lane actually needs beyond the baseline — a compound key and a media tag-density row in the ONE aggregate gas bundle — are each gated on the other side (Core: "only if a workload proves it"; media: "after Stage B measures it"), nobody has written a first-order estimate of what one booru post costs to admit, EIP-8037 is invisible on both sides, and the set's own atomic object (`TagAssertion`) has two incompatible shapes in two of its documents. Nothing here blocks the write-capable File Browser MVP; everything here must be settled before V2-F2 could honestly select media.

## 3. Question 2 — Variant A or Variant B, and does the ladder survive either?

- **What media assumes.** Every media citation of an index mechanism is the B0 bundled grammar: `query-and-indexing.md` 59–64 names `SCALAR_EQ`, `REF_BACKLINK`, `DIGEST_EQ`, page ABI and cursors; `media-infrastructure.md` 111–125 maps "Exact lookup and graph navigation" to "declared equality/digest/reference/backlink indexes" and cites `b0-indexes`/`b0-content-locators` as "proposal-only engineering inputs until Stage B". `grep -n -i "QueryProfile|ViewQueryProfile|TypeRevision|Data View|layered-type|IndexProfile|TypeSchema|Variant" Designs/media-library/*.md` returns **nothing** (run 2026-09-02). The set never names either arm and never cites the README-designated current Type proposal.
- **The wording is arm-neutral.** README 78–80 "automatic indexing after a Realm admits a Type/index profile" copies the 08-12 ruling's deliberately neutral phrase (`owner-rulings.md` 203–207). So media has not *chosen* Variant A; it has *only ever seen* Variant A.
- **Does the ladder survive Variant A (B0)?** Mostly. Placement steps 2–3 (`query-and-indexing.md` 72–76) and Q0–Q2 map to B0 obligations. Two frictions: (a) "a new canonical index is a new TypeSchema [B0 spine pin]" (`b0-indexes.md` 1041–1043; candidate 294–295) means every Query-Lab iteration on "the smallest generic onchain addition" forks the `TagAssertion` Type and all subsequent RecordIds — the ladder's iterate-and-measure loop is expensive under A in exactly the churn-heavy place media wants to iterate; (b) the compound key is rejected for B0 (S3-1).
- **Does it survive Variant B/C (layered)?** In principle better: "Add index → New QueryProfile; Record identity remains; coverage begins `PARTIAL` until backfill completes" (`layered…` 561; 397–399). But media's own redesign trigger "partial coverage can masquerade as absence" (`query-and-indexing.md` 356) is precisely the C hazard the layered doc names ("A bug can make absence dishonest", 1029–1034), and MEDIA-11 / BOORU-13 (`media-infrastructure.md` 61; `booru-app.md` 91) rest on coverage honesty that under C is a state machine, not a construction property (B0 §5.2 rule 2, 1333–1341 vs F4 sketch 1918–1984). The layered doc's own media pressure test (849–858: `MediaAsset`/`ExactRepresentation` Views) never mentions tags, counts, or intersections. The only evidence that media survives arm C is `Daily Notes/agent-status.md` 236 (2026-08-22: "disposable experiment commit `e9652d3`: 14 candidate Type revisions, two bounded Views, seven exact-Type QueryProfiles … No … onchain enumeration index … resulted; View-wide enumeration remains an explicitly unmeasured in-memory exact-Type scan") — a no-remote experiment not recorded in any vault document (`ls Reviews | grep -i media` → intake only).
- **Owner position.** Not ruled (08-12 "50-year bakeoff question", 208–210; `Designs/web-client-os/README.md` direction 12, 81–84: "The Type/query-identity axis remains open. The latest owner response was not interpretable"). Category: **UNDECIDED** (S3-6). Media is not wrong to build on B0 as the control arm; it is wrong to be silent about it.

## 4. Question 3 — mandatory indexing, its cost consequence, and the missing post-write estimate

**Consistency with the ruling.** Media is consistent with 07-15 item 12 and the 08-12 restatement: `query-and-indexing.md` 37–38 ("automatically populate a Type's admitted index profile for every admitted item"), 339–340 ("Use one aggregate mandatory Type/index bundle. Do not approve an optional media index from isolated read gas while ignoring permanent writer/state costs"), README 213–216 (checklist: "Stage B measures the aggregate mandatory index bundle plus media query additions; no operation is approved from isolated happy-path gas"). The private overlay (MEDIA-07, 57: "without a Core write") is the ruling's sanctioned escape hatch ("private/local = your business", `owner-rulings.md` 62). No drift.

**What "writers pay declared fan-out" means for a booru post — and why media cannot declare its way out.** Under B0 the fan-out is dominated by the *mandatory* families, not the declared ones: per accepted leaf, 2 log slots + 1 overlay + `KIND_BY_TYPE` + `KIND_BY_RECORD` + `KIND_BY_PRINCIPAL` + (conditional) `KIND_UNIQUE_BY_TYPE` + per reference instance `KIND_TARGET` and `KIND_ROLE` (`b0-indexes.md` 738–746; `C(leaf) = 3 + 2·refInstances + valueSpecs`, 1089–1094). A `TagAssertion` with two reference roles (target, tagConcept) and no declared spec touches 8 heads. The only levers are fewer Records and fewer reference roles — not fewer `IndexSpec`s.

**Is there an estimate anywhere?** No. Media refuses to make one (363–364); V2-E4 has none; Stage A's per-write rows are "[HYPOTHESIS]" schedule arithmetic (1822–1859) and "No gas/state-growth measurement … exists" (`STATUS.md` 50–51); R2 F6 confirms the ONE gas snapshot named as "Blocker to final sign" on 2026-07-15 (`owner-rulings.md` 69) is still unproduced. The launch plan's own confidence row reads "The 10k/1m economics and latency are viable — **Unknown** — must be measured" (`Reviews/2026-07-29-target-communities/gallery-opportunity-ranking-and-launch-plan.md` 415) and its kill criterion is "if every tag assertion is economically unreasonable, the network never starts" (369).

**First-order arithmetic the set should have run (inference — derived only from B0's own [HYPOTHESIS] rows, `b0-indexes.md` 1826–1843; not a measurement):**

| Quantity | Derivation | Result |
|---|---|---|
| One `TagAssertion` leaf (2 REF roles, empty `evidenceRefs[]`, no spec) | log+overlay 66,300 + 8 heads × 13,420 | ≈ **174k gas** (B0's "typical leaf" with one spec is 187,100) |
| p50 post, 35 tags, shape 1 | 35 × 174k | ≈ **6.1M ≈ 36 %** of the 16,777,216 EIP-7825 cap, before the Post/Representation/ChunkTree/Locator/Source/Rights leaves (≈ 5–6 leaves, ≈ 0.8–1.0M) → whole post ≈ 7M ≈ 42 % in one 41-leaf Envelope |

Whole-transaction impact "must be benchmarked; L2 adoption was unverified" (same row) |

Two things follow. First, the p95 booru post is already a multi-transaction object under the *un-repriced* schedule, which changes the Slice 2 "explicit signing/admission" ceremony (`booru-app.md` 323–326) and the "Resumable signed batch ingest" requirement (launch plan 274) from nice-to-have to structural. Second, media's placement rule step 4 ("Measure the complete bundle", 77–79) is right, but a design that can do this arithmetic from published rows and declines to is not "not inventing gas limits" — it is deferring the one number that decides whether the on-chain-first ruling is affordable for this product at all. ## 6. Findings

Format: **ID — CATEGORY · owning set (neighbours) · severity · MVP-relevant?** Evidence is file:line. "Inference" is marked.

### S3-1 — UNDECIDED · efsv2 (media-library) · important · MVP-relevant only if V2-F2 selects media
**The compound key is gated circularly.** Media Q5 and candidate shape 3 rely on "one workload-proven small compound key" (`query-and-indexing.md` 99, 130); the candidate allows it "only if a workload proves it" (`core-architecture-candidate.md` 279); B0 says "Compound and alternate grammars are **[REJECTED for B0]**; adding one requires a new versioned schema grammar and a new seam resolution before vectors" (`b0-indexes.md` 1077–1079) and the encoding chapter closes the grammar at three kinds while still reserving `DOM_VK_CMPD` "compound value key" (`b0-encoding-and-ids.md` 111 vs 1510–1516 "The retired 8-byte `REF_EQ/BACKLINK/COMPOUND` form must not mint"). The only workload that would "prove it" is the media one, which is not in Stage B (S3-3), and V2-E4's text (`owner-decision-inbox.md` 40–45) does not mention compound keys. The layered proposal leaves `canonicalIndexSpecs` unspecified (386–394) so it cannot answer either. **Fix:** efsv2 states in V2-E4 whether a `(field, field)` compound `IndexSpec` is a bakeoff cell or out of scope for the freeze candidate; media either files the exact (tag × rating) trace as a candidate Stage B fixture or drops the on-chain arm of Q5 and says facets are client folds over single-key pages. Neither is an owner ask.

### S3-2 — DRIFT (internal) / UNDECIDED · media-library · important · MVP-relevant only if media selected
**The set's atomic object has two shapes, and only one of them supports the same-basis point probe it plans on.** `booru-app.md` 153–161 defines `TagAssertion(target, tagConcept, polarity = ASSERT|DENY, scope, confidence?, evidenceRefs[])`; `query-and-indexing.md` 127–128 defines candidate shape 1 as "exact author-neutral `TagAssertion(target, tag)` Record plus authored Occurrences and point-queryable liveness". Under B0 the point probe "is post P tagged B at basis H?" is a bounded page over `KIND_BY_RECORD` for the *known* RecordId with `basisOrdinal = H` (`b0-indexes.md` 412, 1159–1174, `liveAt` 554–561) — which works only if the RecordId is derivable from (P, B), i.e. the two-field shape. With six fields the client cannot mint the RecordId and must page P's `KIND_ROLE` backlink and read bodies. Separately, `polarity` inside the body means ASSERT and DENY records share the tag→assertion backlink key `pk(T, KIND_ROLE, roleOrdinal, targetKey(tag))` (415) and `liveCount` counts both; a `SCALAR_EQ` on polarity gives "all DENY assertions everywhere", not (tag, DENY) — separating them needs two Types (`TagAssert/1`, `TagDeny/1`), a compound key (S3-1), or per-item body reads. **Correction to R13 F-03(a):** B0 does provide basis-pinned membership; what it lacks is count-at-basis (2077–2080). **Fix (media):** pick one canonical assertion shape (or two Types) before the Query Lab, and say which B0 read realises the probe.

### S3-3 — MISSING · efsv2 (Stage B harness) + media-library · important · blocking for MEDIA-E2
