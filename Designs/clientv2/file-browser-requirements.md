> **What this is.** The feature bar for the Files app (the ordinary Ring-3 flagship of [[system-surfaces]] §20), derived from concrete user journeys against the best available evidence: ArDrive as the shipped competitor, mainstream drives as the expectation baseline, and the dweb graveyard as the failure catalog. Three buckets: **MATCH** (credibility floor), **DIFFER** (deliberately different, and why it's better), **SKIP** (deliberately absent, and why that's safe). It does not relitigate settled rulings (chains render as drives; lenses are the differentiator; read-only mount is a requirement; large on-chain files are first-class; public-by-default with the privacy tier owned by a separate pass; a local/chain-free mode exists), and it does not design the authority/identity model (under a hold) or the privacy tier. Where a requirement *needs* one of those passes, it says so with a `#depends-on` marker rather than designing the mechanism — and where a mainstream expectation cannot be met without them (recovery, multi-user write, embargo), the dependency is stated here so it is tracked, not silent.
>
> **Ownership discipline.** Files is an ordinary app: every power below must be expressible as a named, grantable, revocable capability per §20's constitution rule, all ceremonies and destructive-act dialogs belong to System Chrome with copy from the shared string catalog, and Files' role at every commit point is the *pre-commit* surface plus routing. Requirements that propose new named capabilities flag themselves as §20-table amendments (see Open questions).

## The journeys

Requirements below trace to these. Evidence anchors in parentheses name teardown-corpus lanes.

- **J1 — A stranger opens a link.** No wallet, no account, no install. (ArDrive's no-account shared-file page is its best surface; Skynet's dead-domain link graph is the catastrophe case. `sharing-accounts`, `dweb-alternatives`.)
- **J2 — First run to first published file.** Clean browser → look around → save → sign → share. (ArDrive: 3–6 min, $0; its landmines: checkbox backup ceremony, unrecoverable password at signup. `onboarding`.)
- **J3 — Organize.** Rename, move, multi-select, folder upload, conflicts — while some items are still pending. (ArDrive's false-failure dots and sync gates. `core-ux`.)
- **J4 — Find it again.** Search, recents, activity. (ArDrive: name-only search in year four, gated on sync. `core-ux`; Proton's honest search limits. `mainstream-baseline`.)
- **J5 — Versions.** See history, compare, restore. (ArDrive has the model, never shipped restore. `core-ux`.)
- **J6 — Share a folder; publish a folder as a site — interactively and from CI.** (ArDrive cannot share folders; GUI publishing ends in a TX-ID scavenger hunt while `permaweb-deploy` does the loop right headlessly; the immutable-versions + mutable-pointer model is the good bone. `sharing-accounts`, `publishing`.)
- **J7 — "Delete."** The user tries to make something go away. (Mainstream trash expectations vs permanence; ArDrive's unexplained hidden-≠-private. `mainstream-baseline`, `core-ux`, `takedown-decentralization`.)
- **J8 — Second device / recovery / walk away.** Same person, new machine; a lost credential; or the org dies. (ArDrive's "We found your drives!" hero moment and its 376-second shadow; Akord Weave. `onboarding`, `dweb-alternatives`.)
- **J9 — Viewer-sovereign views.** Two people look at the same path and legitimately see different winners; the user asks "why this file?" (Nobody has shipped this UI; §Lenses below draws it. `read-lens-spec`.)
- **J10 — The mount shows the same world.** Files-in-browser and the read-only host mount must agree. ([[mountable-filesystem-semantics]].)
- **J11 — An agent touches my files.** Plan → approval → receipts, through the same capabilities. ([[agent-native]]; the trifecta invariant.)
- **J12 — Big files.** Multi-GiB ingest and retrieval without lying about progress or ceilings. (ArDrive: 65 GiB in, ~500 MiB out on Chrome, undocumented. `core-ux`, [[large-file-uploads]].)
- **J13 — Steward an archive.** An institution accessions thousands of files, describes them, verifies them yearly, and hands the whole thing to a successor decades later. (The archivist persona's four uncovered workflows: verified bulk ingest, fixity audit, software-independent export, succession. `mainstream-baseline`, `dweb-alternatives`.)

## Bucket A — MATCH: the credibility floor

Missing any of these codes the product "web3 demo," not "drive" (`mainstream-baseline` Tier 1; every item also has an ArDrive-validated or ArDrive-failed precedent):

- **A1. Folder tree that feels instant — and free to organize.** Hierarchical folders; rename/move/duplicate/multi-select/breadcrumbs; star/favorites; list + grid views with sortable columns; optimistic UI over the journal for every mutation ([[persistence-and-sync]] D4 — pending truth lives in the journal, rendered as ladder chips, never as blocking spinners). *Never* a "Drive Not Synced" gate: listings stream from lens resolution + cache; the cache accelerates, never gates. **Organize economics:** everyday organize ops (rename, move, unlist) must be free to the user or covered by a visible allowance, and batched — reorganizing 50 items is one ceremony with one disclosed cost line, not 50 (ArDrive meters each metadata revision; a Dropbox native who discovers renames cost money stops organizing). The cost model itself is a protocol/sponsorship dependency — see Open questions.
- **A2. Ingest that proves itself.** Drag-and-drop upload of files *and* folders (structure-preserving), per-item progress with cancel, resumability for large files (offset-probe-then-append per [[persistence-and-sync]] D4.7), background continuation while the user navigates. Conflict flow: skip / new-version / rename, for files *and* folders (ArDrive hard-fails folder conflicts), with the new-version option stating that prior versions remain in history (B5). **Dedupe:** uploads are content-hash deduplicated against bytes already present on the selected mirrors, automatically — the cost line shows "already stored — not charged" per item (re-ingesting a 60 GiB folder with 2% churn must cost ~2%, as `permaweb-deploy` already achieves and ArDrive's GUI does not). **Bulk scale:** thousands-of-files ingests render aggregate progress with drill-down (not 10,000 rows) and one aggregated cost confirmation. **Completion receipt:** every ingest ends in an enumerated report — count, per-item digest, per-item ladder state, failures listed with one-click retry-all; optionally seeded by a client-side manifest (BagIt-compatible) so ingest verifies against a declared inventory. Silent partial ingest is the single worst archival failure; it must be structurally impossible to mistake for success.
- **A3. Previews.** Images, PDF, video (streamed), audio, text/code inline via the render service (untrusted-document lane, [[system-surfaces]] §18); thumbnail grid via the thumbnailer service; arrow-key sibling navigation. Unpreviewable types get an honest "no preview" card with type/size/provenance, not a broken pane.
- **A4. Download.** Single file; folder-as-ZIP (streamed, size-honest); every size ceiling published in-product at the point it binds (upload modal, download action). The answer to "what's the max file size" must never live only in source code (ArDrive's open unanswered issue).
- **A5. Search that never depends on sync completeness.** Instant search over names *and descriptive metadata* (B13) from the local index, clearly labeled with its coverage ("searched: names and descriptions across 3 cached locations, as of…"), falling back to venue-backed lookups with grades; discovery-sourced results additionally carry the "found by discovery, not endorsed" label ([[system-surfaces]] §19). Filters: type, date, author/persona, properties, pending-state. Content search is a labeled roadmap item, not a silent absence (§C3). The index-query power is a proposed named capability (`index.query`, scoped to granted containers) — §20 amendment, see Open questions.
- **A6. Share links a normal person can use.** One share action per item — file *and folder* — yielding an artifact that opens for a recipient with no wallet and no install into the read-only viewer (J1; the zero-install citation view of [[system-surfaces]] §The retention question). **Default artifact resolution (closing the A6/B2 tension):** the person-to-person default is a clickable https link that carries the canonical claim in its *fragment* — protocol-native in content even when the transport is https — with the bare `web3://` form one tap deeper for protocol-native contexts; the https host is visibly a disposable convenience mirror (B2). The recipient viewer offers "save to my Files" as the J1→J2 conversion path. Path Link vs Citation Link composed via the Share/Citation center (#13) with its one-line education.
- **A7. A trash affordance.** "Remove" exists in the UI, maps to the **unlist / withdraw placement** vocabulary (shared string catalog — never "hide", the ArDrive term whose hidden-≠-private confusion J7 documents), restores trivially, and routes its confirmation through the System Chrome ceremony whose copy owns the permanence boundary (B4). Users test delete on day one; silence is the worst option.
- **A8. Recents + activity.** A Recents landing surface and a per-item Activity view (creations, renames, moves, versions, share events) derived from records — ArDrive's Activity tab is the validated pattern, and for EFS it is nearly free: the records *are* the audit log. Event ordering uses the one canonical event-time mapping shared with the mount (M9). The activity-read power is a proposed named capability (`activity.read`, scoped to granted containers) — §20 amendment.
- **A9. Keyboard and accessibility.** Full keyboard operation (navigation, rename, move, select-all, open), documented shortcuts, WCAG 2.2 AA via surface mode ([[web-os-thesis]] F1 — the Shell owns real DOM, so Files is accessible by construction). ArDrive's empty accessibility tree is the cautionary null result: canvas-rendered file managers lock out screen readers entirely and degrade password managers and automation.
- **A10. Mobile-responsive web.** Files works in a phone browser (sheet-based pickers/ceremonies per [[system-surfaces]] §Mode variants). Native apps are out of scope (§C1) — but the PWA path is first-class, not a consolation FAQ (ArDrive's literal endgame).
- **A11. Cost, ceilings, and standing — disclosed where they bind.** Files owns the *pre-commit* surfaces: upload-modal ceilings, per-mirror permanence labels, itemized cost previews (network vs any service fee — never embedded; ArDrive's hidden 35% is the anti-pattern) with a fiat estimate alongside protocol units, an **estimate-cost dry-run** on any local selection (no signing, no staging; also exposed as an SDK call so scripts can budget), and a persistent per-location usage/allowance meter in the sidebar (bytes + fiat-equivalent — the quota bar is how drive users understand their standing). The commit-point itemization itself renders in the System Chrome signing ceremony (#2), from the shared string catalog; auto-refreshing quotes and "you are not charged for failed submissions" are stated there. Free-allowance state is visible before exhaustion, not after.
- **A12. First-run funnel parity.** Clean browser → first published file in under 5 minutes with $0 and no token purchase (gasless/faucet-drip lane). Education beats fire contextually per [[system-surfaces]] §First-run. Where we beat ArDrive rather than match: a real backup ceremony (verified, not a checkbox) at the *first moment something irreplaceable exists* — key/persona creation — plus the A14 audience interstitial before the first published file.
- **A13. Plain words first.** Every protocol term has a required plain-language rendering: the ladder renders as "Saving here / Saved here / Published / Confirmed" tiers, grades as "verified just now / can't check right now"-class phrases, venue/currency surfaced only when they change what the user must do. Raw vocabulary (ladder state names, grade words, venue/currency detail) is confined to detail panels and dev mode (#17). This is L1's invisible-until-it-matters principle applied to all protocol vocabulary — a Dropbox native must never meet the word "currency" in a photo's properties. (All strings from the shared catalog; Files renders, never rephrases.)
- **A14. Audience disclosure at every write commit.** Public-by-default is settled protocol posture; *undisclosed* public-by-default is a user betrayal. Every commit preview states audience in plain words ("Public: anyone on the internet can view this, indefinitely") via the chrome ceremony; the first-ever publish additionally gets an acknowledged interstitial in the A12 funnel (the Proton moment-of-impact pattern). A first-run user must be structurally unable to publish a tax return believing it private.
- **A15. No unrecoverable single secret — and a recovery path must exist.** Constraint, not mechanism: v1 must not ship any credential whose loss unrecoverably destroys access (ArDrive's password landmine; the teardown's lesson 3), and a recovery path for the primary credential must exist. The mechanism is owned by the held authority pass — `#depends-on/efsv2-authority`, see Open questions — but the Files funnel reserves the ceremony moment (A12) and the requirement stands regardless of mechanism chosen.

## Bucket B — DIFFER: deliberately different, and why it's better

- **B1. The pending ladder instead of status dots.** ArDrive's three-color dot shows documented false failures and its remediation is a block explorer. Files renders the normative ladder as per-item chips with per-state affordances (what you can do while pending), composed with read grades, in A13's plain-language rendering. A wrong "failed" is worse than a slow "pending": failure states render only on proven failure, with a retry that is a button, not a ritual. *Better because:* the states are protocol vocabulary ([[persistence-and-sync]] D4.6), deterministic claimIds make reconciliation honest, and Ethereum finality is legible in ways gateway unbundling never was.
- **B2. Protocol-native canonical links.** The canonical artifact is always the `web3://`/`#efs1.` form (A6 rules how it rides person-to-person shares); https gateway mirrors are minted as visibly secondary, labeled disposable conveniences. Link-grammar durability is a requirement on its owner: Files requires that a year-one link resolve in year ten — the grammar is owned by [[read-lens-spec]] §6.5, and if that spec guarantees less, that is a filed pressure item, not a Files invention. A dead target renders a named error ("this claim is not resolvable at this venue: …"), never a silent bounce to a welcome screen (ArDrive's live behavior; siasky.net's gambling squat is the terminal case). *Better because:* no company domain in the critical path, and rot becomes diagnosable instead of invisible.
- **B3. Sharing with revocation, expiry, and roaming — honestly scoped.** The Files surface requirements: share sheets state audience plainly (where public-chain visibility means "viewer = everyone," say so); links can carry expiry; grants are listed, severable, and re-evaluated on restore (F8); "shared with me" is persona-attached state that roams across devices (ArDrive's device-local attach has been an open gap since 2020); folder sharing ships day one. **Revocation honesty:** revocation is forward-only — it stops future resolution; it does not recall bytes or knowledge already fetched, and the UI says so. The *mechanisms* (per-item wrapped keys, container re-keying, grant records) are assumed expressible and explicitly deferred: encryption-key design belongs to the privacy pass, grant/authority semantics to the held authority pass — `#depends-on`, see Open questions. *Better because:* ArDrive structurally cannot retrofit any of this; our mutable layer can — but this doc only commits the surface, not the crypto.
- **B4. An honest deletion story, finished.** ArDrive got 80% right (blunt no-delete copy) and fumbled the rest (hidden ≠ private unexplained; hide is a potentially-paid public event). Files exposes the three distinct acts, matching §20 exactly, with all confirmation dialogs owned by the chrome ceremony and the string catalog:
  1. **Unlist / withdraw placement** — social, signed, restorable; the ceremony states per-mirror reality ("removed from your view everywhere; bytes on ar:// remain fetchable by anyone who has the pointer; this removal is itself a public record") *and* the effect on other viewers ("people you shared this with may still see it until their view refreshes; under their own lens they may keep seeing it") as checkable clauses. Where every mirror holding the bytes supports eviction, the ceremony offers actual byte removal and reports per-mirror results.
  2. **Local cache eviction** (`trash.local`) — promptless, receipted, re-fetchable by construction; carries no "delete" language at all.
  3. **Destroy local data** — the checkpoint-7 chrome ceremony, which alone owns the "only real delete" label.
  Version-granular unlist exists (B5): fixing an embarrassing photo by uploading a new version must not leave the original one click away with no recourse. Where the future privacy tier supplies random-keyed containers, key destruction becomes an honest erasure ceremony — a thing ArDrive can never offer because its keys are deterministically re-derivable. *Better because:* every clause is checkable, and the three acts can never be mistaken for one another.
- **B5. Versions forever, with the restore button.** Version history is native (immutability makes it free) and unbounded — a headline against Dropbox's 365-day enterprise tier and iCloud's nothing. One-click "restore this version" mints a new revision pointing at old bytes (near-free metadata write). Revisions can carry a typed **derived-from relation** (edit vs migration/derivative, recorded at mint time) so a 2040 re-encode of a 2026 recording is archivally distinguishable from an edit — the record semantics must be right from day one because they are immutable. Version pinning in citations rides the Citation Link. *Better because:* ArDrive proved the model and never shipped restore; mainstream drives charge for retention windows we get by construction.
- **B6. Publish-a-folder: one canonical URL, one atomic republish verb, headless by construction.** "Publish as site" is a Kernel/SDK capability that the Files GUI *wraps*: pick folder → index/fallback → one confirm → output is one canonical link. **The v1 mutable pointer is a hard requirement** — an EFS-native mutable record the publish verb repoints; without it "republish" degenerates into the TX-ID scavenger hunt this verb exists to kill, and staging channels/rollback are incoherent. (ENS naming of that pointer is the deferrable layer — Open questions.) Republish = diff-aware single action (changed bytes + pointer update in one ceremony), accepts caller-supplied provenance tags (commit hash, build id) recorded on the revision, and is invokable non-interactively — a documented CI recipe (scoped signing credential per B12, machine-readable diff/cost output) so the `git push` → deploy loop works without a human at a GUI (the publisher persona's actual workflow; `permaweb-deploy` is the bar). Immutable versions behind one mutable pointer, staging channels, and instant rollback are exposed in UI. *Better because:* the pointer lives on the same chain as the filesystem (no ArNS-style multi-chain migration risk), and the GUI and CI share one verb instead of ArDrive's GUI/CLI capability fork.
- **B7. Lenses in the file UI** — the differentiator nobody has drawn; see §Lenses below.
- **B8. Chains as drives; "This Device" as a drive.** The sidebar is locations: `This Device` (the local/chain-free mode — Tier B journal state (drafts, unsigned work) plus Tier A pinned bytes, each labeled with its own durability class per [[persistence-and-sync]] D1/D7), then per-chain drives, then attached/foreign containers. Test networks are hidden behind dev mode (#17) by default — a testnet is developer furniture, not a consumer location. A future unified cross-chain view remains possible (per the settled ruling) as a query surface over locations, not a merge that hides provenance. *Better because:* ArDrive hides its one chain badly (users absorb its physics anyway); we surface locations the way file managers always have — as disks with different properties.
- **B9. The daily-return surface.** A "changed since yesterday" home: incoming shares, activity in followed/shared folders, version events, pending-state transitions, deny-fact alerts on subscribed content. The permaweb's retention vacuum (filled by token farming) is the null result; the archive loop (save → organize → cite → share links that never rot) plus this surface is our retention bet ([[system-surfaces]] §The retention question). Powers used here are proposed named capabilities (`activity.read`, `subscriptions.read`) riding the courier's existing single-jittered-head-fetch discipline (F5) — no per-item polling; see Open questions for the load estimate. *Better because:* it exercises records we already have; no telemetry, no engagement machinery — just the filesystem's own events, rendered.
- **B10. Walk-away and succession as product features.** Two halves, deliberately separated:
  - **Read-exit (the Akord Weave lesson, shipped-not-promised):** a minimal read-only Files viewer pinned as a generation artifact, independent of our org's infrastructure, plus `.efs-bundle` export from the Sync Center and the Rescue Shell's export ceremonies. **The bundle format is exit-grade or it is lock-in with a friendly name:** publicly specified with the same durability discipline as the link grammar, plain-files-plus-manifest at its core (BagIt or BagIt-mappable, openable with an unzip tool in 2076), and inclusive of provenance records, the fixity manifest, and the identifier→path mapping. (The bundle's normative encoding is already a filed protocol gap in [[persistence-and-sync]] — this adds the archival-openness requirements to it.)
  - **Control-succession:** the harder institutional half — who publishes, unlists, and repoints in 2076 when the original steward is gone. Mechanism is `#depends-on/efsv2-authority`; what this doc commits now: a **succession packet** export (recovery material + plain-language, crypto-free instructions, generated while healthy) and the stated intent that institutional custody (multi-party or equivalent) is a supported authority configuration.
  The walkaway story is published while healthy; "the app outlives the company" is a checkable claim (content-addressed generations + provenance records), not a comparison-table row. *Better because:* ArDrive markets this and partially delivers while its help domain rots; we make it verifiable — and we answer the archivist's question ArDrive never faced.
- **B11. Agent-legible by construction.** Every Files view is a rendering of typed Kernel state agents can query through capabilities ([[system-surfaces]] §Agent lens); agent actions on files run the plan→dry-run→approve→execute→receipt pipeline with T3/T5 checkpoints human-only; agents pay through B12 grants, never ambient balance. *Better because:* nothing in the surveyed field has any agent story at all — and the trifecta invariant means "an agent organized my archive" can be safe here first.
- **B12. Scoped spend grants.** A budgeted, expiring, revocable payment credential — grantable to a CI job or an agent session — that can fund writes up to a cap, with receipts, surfaced in the Permission center. This is the one ArDrive-stack feature the teardown flagged as ahead of our design set (Turbo's credit spend-approvals); it is also the structural prerequisite for headless publish (B6) and paying agents (B11). Grant/authority mechanics `#depends-on/efsv2-authority` + [[wallet-and-actions]]; the requirement and its UI surface stand.
- **B13. Metadata, licensing, and catalogs as records.** User-authored descriptive metadata as property records on files/folders — title, description, dates, rights/consent note, arbitrary key-values, bulk-assignable across a multi-select, editable in the detail panel, indexed by A5 search. License attachment at upload/publish (CC/UDL-class choices, like ArDrive's licensing-at-upload) rides the record and displays on the A6 recipient viewer — for permanently public bytes, the license is the difference between distributable and radioactive. *Better because:* catalog entries carry signed provenance — a catalog whose every row is attributable is something no mainstream drive offers, and it makes C3's content-search deferral honest (metadata search exists).
- **B14. Stewardship: fixity audits and durability accounting.** Two verbs no consumer drive has and every institution requires:
  - **Verify collection:** a schedulable audit over any container — walk the tree, re-verify against claimed content commitments, distinguish verified / bytes-unavailable / UNKNOWN (M2 vocabulary; a cache can never prove absence), emit a signed, dated, exportable fixity report. Standard-algorithm digests (SHA-256) are exposed alongside protocol commitments so institutional tools (BagIt validators, Fixity) can cross-check — including over the J10 mount.
  - **Durability audit:** per-container bytes-at-risk accounting — per-mirror coverage, durability class (D7 vocabulary), expiry/renewal dates, projected annual cost — plus a bulk "archive this collection to permanent mirror" action with one A11-compliant total-cost confirm. The trash-restore-after-a-year question is one instance of this general rule: bytes-at-risk must be visible before they are gone.
  *Better because:* content addressing makes fixity nearly free — turning a compliance chore (NDSA-level periodic verification) into a native verb is a differentiator only this architecture gets cheaply.

## Bucket C — SKIP: deliberately absent, and why that's safe

- **C1. Native mobile/desktop apps at launch.** ArDrive's Android app earned 39 ratings in three years and died; iOS is structurally hostile to pay-per-upload (Apple IAP rejection precedent); its desktop app died in alpha. Responsive web + PWA is the evidence-backed path; wallet-browser distribution reaches mobile crypto users. Revisit on traction, not before. *Risk accepted:* "where's the app?" questions — answered in-product by the PWA install flow.
- **C2. Two-way folder sync.** No dweb drive has ever shipped it; Internxt's lossy sync client is its worst complaint source; and the read-only mount (J10) covers the browsing half without the "sync ate my files" failure class. The one-way half is not skipped but named: **R1 — watch-folder one-way publish** (recurring accession from a staging directory, per-change cost preview, B6 semantics) is a tracked roadmap item referenced from J13's accession workflow — promoted out of skip-prose so it cannot die there. The writable mount profile remains staged in [[mountable-filesystem-semantics]].
- **C3. Content search / OCR at launch.** Structurally identical to Proton's constraint (no operator to index for you) — so we do what Proton does: honest name+metadata-first search (A5, B13) with the trust-model explanation attached, and a labeled roadmap for client-side or opt-in-indexer content search. Silent absence is forbidden; the search field itself states coverage.
- **C4. Real-time co-editing, comments, presence.** Docs-suite layer, not file-browser layer (Dropbox thrives without owning an editor). Files needs awareness (who has access, what changed — A8/B9), not live cursors. Fileverse is welcome to that fight.
- **C5. Any token surface in the UI.** ArDrive added its house token as a payment method and removed it four months later; fee-free-in-house-token steering reads as what it is. EFS Files prices in bytes and fiat-equivalents; protocol economics stay behind the curtain.
- **C6. An in-app "permanent by default" write path.** Public-by-default is settled; *permanent-mirror*-by-default is not implied by it. Mirror selection carries per-mirror permanence labels (B4); archive-grade permanence (ar://) is positioned as the deliberate act for the files that deserve it — the "133 years to break even" arithmetic is ArDrive's wound, not ours to inherit.
- **C7. Infinite preview-format matrix.** Ship the A3 core set well; everything else gets the honest no-preview card. Google's 30+ formats are two decades of server-side rendering we should not chase client-side at launch.
- **C8. Multi-user-write folders ("the family folder").** The single biggest mainstream absence in this spec, named rather than silent: shared *write* — two people adding photos to one folder — is deferred to the held authority pass (`#depends-on/efsv2-authority`), and until then every share sheet says "view only for now." One scoping note for the pass: §Lenses already renders multi-claimant names, so a lens-native composition — two authors each writing their own claims into one subtree, merged by mutual trust-order entries — may deliver the *experience* of a shared folder without shared write authority; whether that composition is the v1 answer or a dead end is an open question filed below, not a design made here.
- **C9. Photo auto-backup / camera roll.** The stickiest mainstream consumer feature, explicitly skipped at launch: PWA background constraints, per-write economics, and the C1 no-native-apps posture make it dishonest to promise. Named here so the absence is a decision; revisit with R1's watch-folder machinery and the mobile posture together.

## Lenses in a file UI (J9) — the first drawing

The settled ruling: overlapping per-curator views of one shared namespace; the viewer's trust order resolves winners; ArDrive gives one canonical tree per drive — EFS's namespace is shared and viewer-sovereign. What that means concretely in Files:

- **L1. Invisible until it changes an answer.** For a solo user browsing their own container, the default view carries no lens chrome at all — it looks exactly like a normal file manager (this is F13 applied to Files, and it wins over any ambient labeling instinct: a persistent trust-flavored chip is exactly the positive-chrome habit Amendment 9 forbids). The lens indicator appears when — and only when — the lens changed something: contested resolution present, shadowing active, a non-default lens in effect, or a multi-source container.
- **L2. Contested names get a marker, not a merge.** Where the lens resolved between multiple claimants for one name (the U2 case), the item carries a small multi-claimant badge. Expanding it shows the ranked claimants — petname, grade, why-ranked ("won: position 2 in your Trust Order") — with the loser rows openable read-only. Never render a second-place claim as absence; never auto-merge.
- **L3. "Why am I seeing this?" is one click.** Every item's detail panel has a resolution row: winning author (petname + `<efs-identifier>`), lens position that decided it, venue + currency, grade chip — and the full resolution tuple: **lens id + lens revision + basis**. The full trace lives in dev mode (#17); the one-line answer lives here. This is the file-manager rendering of RR-grade honesty, and it is the feature that makes viewer-sovereignty legible instead of spooky.
- **L4. Try another lens = try another pair of glasses.** A view menu action to preview resolution through another lens position. Strictly a preview: banner-labeled, time-boxed, never persisted as the default without the Lens/Trust manager ceremony (#7 owns trust edits; Files may only *propose*). Picker labels follow #7's copy discipline and the shared string catalog — delegation-order framing, petnames, never possessive-"X's view" framing. The mental model deliberately mirrors "sort by / group by" — a read-time transform, not a different filesystem.
- **L5. Shadowing is inspectable.** A "show shadowed items" toggle (sibling of "show hidden files") reveals entries a higher-priority source is masking, ghosted, with their would-be winners. This is the UI answer to lens debugging that otherwise lands in support channels.
- **L6. Lens actions are designations.** "Prefer this author for this subtree," "pin this version," "stop showing me this claimant" — expressed from Files as *proposals* routed to the Lens/Trust manager's ceremony, receipted, revocable. Files never edits resolution truth itself ([[system-surfaces]] §20 never-list). One named carve-out is pending a layer decision: if unlist facts live in the persona's lens state (see Open questions), Remove becomes a fast-path lens ceremony — still chrome-owned, still receipted — rather than an L6 violation.
- **L7. Shared links disclose their lens assumption.** A Path Link resolves through the *recipient's* trust; the composer says so ("they may see a different version than you"); a Citation Link freezes the claim. This one line is the whole path-vs-citation education, repeated where it matters.
- **L8. Every view is mountable.** The default lens is a versioned, referencable object, and Files exposes (lens id, lens revision, basis/generation) as a visible fact (L3) and a **copyable artifact — "Mount this view"** — emitting the exact descriptor tuple a mount profile consumes ([[mountable-filesystem-semantics]] §EfsMountDescriptor). Without this, J10's "same (lens, basis) pair" is unconstructible by a user.

## Mount compatibility notes (J10)

Browser-UI choices that would make a good mount experience impossible, phrased as constraints on Files (the host layer itself is [[mountable-filesystem-semantics]]'s problem):

- **M1. One resolution semantics — over the settled projection.** Files' rendering of a given (lens revision, basis) with journal-overlay items excluded must equal the mount's projection of the same pair — same winners, same names, same shadowing. Pending/journal items are a Files-only overlay *outside* the equivalence claim, and are visibly marked as such ("not yet visible at basis N" — a consequence of the B1 ladder chip), since a read-only mount can never contain them. Files must be able to render/export exactly the settled projection on demand (the comparison artifact of acceptance test 15).
- **M2. UNKNOWN is never rendered as absence — per item *or* per listing.** Files renders "can't check" states distinctly (NO-TRANSPORT qualifier per [[persistence-and-sync]] D9); the mount maps them to transient errors, never ENOENT. Additionally, **enumeration completeness is a rendered state**: a container view is either "complete at basis N" or visibly "streaming/partial (reason)" — a partial listing may never be visually identical to a complete one, mirroring the mount's page-closure discipline (absence-by-omission is the directory-level form of the same sin).
- **M3. Names must be projection-stable.** Whatever Files displays as a name must survive the mount's portable-projection profile (collision handling, encoding). Don't invent display-name magic (emoji badges baked into names, zero-width annotations) that can't round-trip to a host filesystem.
- **M4. Open = pinned version; listings pin their generation.** Files' preview/open semantics pin the resolved object for the session (like the mount pins open handles), with an explicit "newer version available" chip. Container views likewise: a rendered listing is pinned to its generation; new state arrives via an explicit refresh affordance with a "newer state available" chip — the directory analog of the file chip, matching the mount's refresh-as-remount semantics.
- **M5. Cache keying by view identity — split by cache kind.** Resolution results (path→winner) are keyed by (canonical path, lens id + revision, basis); derived-content caches (thumbnails, previews) are keyed by content commitment alone (pure functions of bytes — keying them by path/lens defeats dedup); nothing is keyed by bare path. Aligns with the mount doc's cache-isolation rule and D5.
- **M6. Rename projects identically.** Whether a pre-move path is absent, a redirect entry, or an error at a given basis is a filesystem-profile decision ([[mountable-filesystem-semantics]] §3.3) — and Files renders exactly the profile's choice post-settlement (the optimistic window is covered by M1's pending-overlay marking). Rename is the highest-frequency mutation; without this constraint the two surfaces silently diverge on tree shape.
- **M7. No browser-only hybrids.** A DATA node with children (file-and-directory hybrid — the mount doc's critical projection problem) renders in Files using the same canonical projection the mount profile defines (single entry type or the same reversible synthetic split) — never a browser-only hybrid presentation with no host equivalent. The two documents must resolve the hybrid rule once, together.
- **M8. Fact chips have machine-readable twins.** Every fact chip Files renders (grade, contested/claimant-count, shadowed, pending-at-basis, resolution winner) has a canonical counterpart in the mount's xattr/control projection with identical vocabulary and values; losers surfaced by L2 are addressable via the control namespace under the same citation identity. Proposes `user.efs.contested` (or claimant count) for the fixed xattr set — filed toward the mount doc.
- **M9. One event-time mapping.** Recents/activity ordering (A8/B9) and the mount's synthesized mtimes derive from the same canonical event-time mapping, defined once in the filesystem profile — `find -newermt yesterday` over the mount and Files' "changed since yesterday" must agree.

## Acceptance tests

Measurable, phrased as the user's experience. (Tests 1–10 are consumer-shaped; 11–15 close the verification gaps the persona pass exposed; 16–19 are the institutional pilot set.)

1. **First file:** clean browser → first published file: **< 5 minutes, $0, no token purchase**; a verified (not checkbox) backup ceremony fired if a key was created; the user cannot reach a published file without having been shown, in plain words, who can see it (A14).
2. **Cold open:** a 10,000-entry container: first screen of listings **< 1 s warm, < 5 s cold**, streamed remainder from one declared generation (no mixed-basis pages), ending in an explicit completeness indicator; no blocking gate at any point.
3. **Stranger's link:** the artifact produced by the *default* share action, texted to a no-wallet phone: opens read-only with provenance, **zero login prompts**; a dead link renders a named error — never a welcome screen.
4. **Big-file resilience:** kill the tab mid-upload of a 5 GiB file; reopen: upload resumes from the last verified offset, correctly laddered throughout.
5. **Organize under fire:** rename + move 50 items offline, then flush through a deterministic fault-injection matrix (timeout, 5xx, partial page, stale head at defined points): instant optimistic results, correct reconciliation, **no item ever renders a failed state without a proven venue rejection**, and the whole batch costs $0 or one disclosed batch fee (A1).
6. **Restore:** any historical version restored in ≤ 2 interactions, producing a new revision without re-uploading bytes.
7. **Remove, honestly:** Remove then verify each ceremony clause: item gone from all the user's roaming views; local eviction (named as `trash.local`, not "delete") on request; per-mirror byte-removal results reported where offered; the other-viewers clause holds as stated; then **Restore** returns it with history intact. Repeat for a single version (version-granular unlist).
8. **Two viewers, two truths:** two profiles with different trust orders view the same contested path: both see their correct winner, the multi-claimant badge, and a one-click "why this file" answer (including lens id/revision + basis); neither sees the other's winner rendered as absence.
9. **Search:** a file added 10 seconds ago is found by name; a file findable only by its B13 description is found; the coverage label accurately states what was and wasn't searched.
10. **Disclosure audit:** every size ceiling and fee encountered in tests 1–9 traces to an in-product disclosure shown *before* the action bound by it (no source-code-only limits, no embedded fees).
11. **Folder share & publish:** share a folder to a no-wallet recipient (per test 3), then publish the same folder as a site reachable at one canonical URL in ≤ 4 interactions; change two files and republish: one diff-aware ceremony, unchanged bytes not re-paid (A2 dedupe), old version still addressable, rollback is one pointer action. Run the same publish headlessly via the SDK verb with a B12 scoped credential.
12. **Fresh device:** sign in on a new machine → full drive list visible **< 15 s** on a ~10k-item account (ArDrive's 376-second shadow is the anti-benchmark), private/local-only items honestly absent with stated reasons.
13. **Agent loop:** an agent session granted scoped file capabilities + a B12 budget executes a plan (organize + publish) end-to-end: dry-run honest about pending state, human checkpoint at the T3/T5 boundary, receipts queryable, kill switch severs mid-plan.
14. **Bulk verified ingest:** a 5,000-file / 30 GiB tree ingested overnight with two induced network interruptions: final receipt shows 5,000/5,000 verified with per-item digests, failures (if any) enumerated with retry-all, zero silent omissions — and the UI showed aggregate progress, not 5,000 rows, with one aggregated cost confirm.
15. **Mount equivalence:** both surfaces export the canonical manifest (rows: canonical path, logical id, content commitment, size, grade; header: lens id + revision, basis, generation) for the same descriptor tuple at a snapshot/complete basis: manifests are identical, including the rename fixture (M6) and xattr/chip agreement rows (M8) and the timestamp column (M9). A separate fault-injected run asserts UNKNOWN surfaces as transient mount errors and as visible Files states — never as not-found, in either surface.
16. **Fixity audit:** run Verify Collection over ~10k objects: signed, dated report exported; an induced corruption/bytes-unavailable case is detected and classed correctly (verified / bytes-unavailable / UNKNOWN).
17. **Exit:** export a container to `.efs-bundle`; on an air-gapped machine with no EFS software, recover every file, verify every checksum from the manifest, and read the provenance records with generic tools.
18. **Succession:** a fresh person on a fresh machine, holding only the succession packet, gains read access to the archive and can execute the packet's documented control handover to the extent the authority configuration allows (clauses beyond read `#depends-on/efsv2-authority`).
19. **Black hole:** with every org-operated domain and service unreachable, the pinned generation viewer opens a canonical `web3://` link and renders the archive read-only with provenance intact — "the app outlives the company," checked.
