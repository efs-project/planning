# EVO-100 cold-room reconstruction (stretch goal)

**DISPOSABLE** · scale-only · not production-scale evidence.

A heterogeneous 100-Type closure: 16 meaningful Types carried verbatim from the
sealed tournament corpus + 84 explicitly scale-only synthetic Types whose
members cycle through REQUIRED / OPTIONAL / LAZY_REF / CORRUPT / UNAVAILABLE /
UNSUPPORTED states. Sealed: `fixtures/evo100_closure.json`
(sha256 `1da7333a…`), field arrays `fixtures/evo100_fields.json`.

Two independent reconstructors, different runtimes, no shared code beyond the
sealed JSON and the domain-separation prose:

- Python (`fixtures/evo100.py`) — 3 cold runs, 0 network reads, 100/100 TypeIds
  recomputed from descriptor bytes alone, deterministic across runs.
- Solidity (`sut/test/Evo100.t.sol`) — 3 cold runs, 0 network reads, 100/100
  match, deterministic across runs.

**Common receipt:** both emit the identical fold
`rollup = 0xb8fe7249a387ba6af09c8dac567bd5366445bf582027970af9733019879d0fd7`
over all 100 reconstructed TypeIds (`RESULTS/evo100_receipt_{py,sol}.json`).

Caught in passing: the first run's rollups diverged because the Python fold
seeded with empty bytes while Solidity seeded with a zero word — a receipt-
encoding inconsistency, not a reconstruction failure (all 100 per-Type IDs
already matched in both). Fixed by aligning the seed; noted because it is
exactly the kind of cross-language fold ambiguity an SDK receipt spec must pin.

Scope honesty: this demonstrates cold, publisher-independent TypeId
reconstruction and cross-runtime determinism at n=100. It does not widen any
C0 limit, exercise record-body reconstruction at scale, or claim
production-scale support. The primary tournament report was complete and
committed before this ran.
